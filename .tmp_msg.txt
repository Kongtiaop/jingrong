fix(rag): BM25 索引定义修正 —— key_field 列必须出现在字段列表中

根因（临时表对照实验证明，非推断）：
  knowledge_chunk 的 BM25 索引定义为 USING bm25 (content) WITH (key_field='id')，
  key_field 指名的列**只在 WITH 中声明、未出现在字段列表里**。
  在 pg_search 0.25.6 下该形态导致**任何 INSERT 都失败**：
      asyncpg.exceptions.InternalServerError: No key field defined.
  影响所有知识库写入路径：上传接口、knowledge_worker、导入脚本。

四种候选定义实测（独立临时表，不触碰生产表）：
  A bm25 (id, content) WITH (key_field='id')   建索引OK 写入OK   <== 唯一可行
  B bm25 (content)    WITH (key_field='id')   建索引OK 写入FAIL <== 库里现有形态
  C bm25 (id, content) 无 WITH                建索引FAIL
  D bm25 (content)    无 WITH                 建索引FAIL
结论：key_field 指名的列必须出现在字段列表中。

本提交：
1. scripts/rebuild_bm25_index.py 改用定义 A（原 --apply 路径已按 A 建临时索引
   -> 写入探测 -> 仅成功才替换旧索引，失败即中止且不删原索引）
2. 新增 migrations/versions/0025_knowledge_bm25_key_field.py：
   把该索引正式纳入版本管理（此前不在 migrations/init 中，
   enable_pg_search_bm25.sql 的建索引语句被整体注释，故与扩展版本脱节无人察觉）。
   迁移幂等：已是正确形态则跳过；无 pg_search 扩展则安全跳过。

诊断过程中被证伪的三个推断（记录以避免重复走弯路）：
  - "配置是 tsvector、索引是遗留物"        -> 证伪（FULLTEXT_BACKEND=pg_search）
  - "旧版 DDL 与 0.25.6 元数据不兼容"      -> 证伪（reloptions 有 key_field 且查询可用）
  - "索引元数据陈旧，REINDEX 可修"          -> 证伪（REINDEX 成功但写入仍失败）
三次都是"听起来合理"的解释，各被一个具体探测推翻。
