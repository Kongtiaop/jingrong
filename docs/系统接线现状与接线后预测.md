# 财富管理 AI 系统：接线现状 + 未接线清单 + 接线后预测

> 目的：把整个系统"哪些已经真接上线、哪些定义了但没接、接了之后会发生什么"讲清楚。
> 依据：`app/` 与 `workers/` 实际代码 + 计划书（`docs/P0-P5_IMPLEMENTATION_PLAN.md`、`AGENT_NEXT_STEPS_AND_PROGRESS_2026-08-14.md`、`AGENT_STRATEGY_...ROADMAP_2026-08-14.md`）。
> 版本：2026-08-27

---

## 0. 一句话结论

- **"确定性执行底座"几乎全部已接线**（Agent 编排、交易、权限、RAG、受控分析、异步 Worker）。
- **"模型自由度 / 长期协作 / 恢复"这些高复杂度能力刻意未接线**（LangGraph 真图、长期记忆接入、任务分发、断点续跑、自由 NL2SQL、Milvus 生产检索）。
- **"未接线"是计划书里的明确决策，不是遗漏**——当前主线是 P2 受控分析产品化，P3 才做共享记忆，P4 才做断点续跑。答辩时可以理直气壮地说"这是阶段化交付"。

## 3. 接线后预测（重点：接上会发生什么）

> 每个都给出【接上后发生什么】【收益】【风险】【前提条件】。

### N1 LangGraph Supervisor 真图

- **接上后**：`CustomerAgentExecutionService` 这条确定性管线要么被 `graph.py` 编译出的真实 StateGraph 替换，要么作为节点之一被编排。`supervisor_node` 从"iteration_count+1"变成真实意图分发，领域 Agent 作为节点接入，`max_iterations/max_tool_calls` 才真正生效。若启用 LangGraph Checkpointer，还能得到任务级状态持久化。
- **收益**：统一 ExecutionPlan 语义、可 checkpoint、多 Agent 图结构清晰、符合简历里"基于 LangGraph 构建"的说法。
- **风险**：现在能工作的确定性管线可能被模型不确定性和 checkpoint 污染；需要把现有权限/scope/幂等校验逐点搬到图上，回归量大。
- **前提**：先给每个领域节点定义 Agent Protocol（`ports/agent.py` 已预留）、再定状态/工具/预算，最后用现有 E2E 做"图版 vs 管线版"双跑对照。
- **预测**：短期内**不建议接**——确定性管线已经交付价值且可审计；真图留给"确有跨 Agent 复杂编排 + 长时恢复"需求时再上（计划书也是这么排的）。

### N2 长期记忆链路

- **接上后**：客服转人工/投顾准备时，先把"已确认意图摘要、任务/工单状态、非敏感规则结果"写入 `CustomerMemory`；后续会话或别的 Agent 用 `load_long_term` 读取，避免重复询问。这正是 P3 MVP 要做的"工作记忆"。
- **收益**：减少跨 Agent 重复沟通；客服转人工信息完整度提升（简历"记忆孤岛"卖点落地）。
- **风险**：若读取时没重新校验 `PermissionContext` + `SubjectScope`，会**越权读到别的客户记忆**；若写入模型推理链/原始资产数据，会**复制敏感数据**。计划书明确把这两条列为 P3 否决条件。
- **前提**：统一写入/检索 API（只允许服务层写）、读时重校验权限+scope、TTL/撤销/覆盖/审计、先做"无记忆 vs 有记忆"对照评估再扩大范围。
- **预测**：接上是**明确收益**，但必须先冻结 P2 基线、定义最小 schema 再动手，且**首接场景限定"客服转人工摘要"**。

### N3 通用任务管道业务分发（runner 占位）

- **接上后**：给 `AsyncTask.task_type` 注册真实业务 handler（如"知识入库重跑""AML 补扫""报表生成"），`TaskExecutor.execute` 按类型分发，配合 attempt/重试/死信成为真正的通用长时任务执行器。
- **收益**：把现在散在各专用 worker 的长时逻辑统一进一个可审计、可重试、可死信的管道，是 P4 断点续跑的第一块基石。
- **风险**：handler 若不幂等，重试会造成重复外部写（计划书 P4 否决条件）。
- **前提**：每个 task_type 定义幂等键 + 输出引用 + 失败上限。
- **预测**：接上后系统才有"统一任务编排"这层，但目前各领域已各有专用 worker，**性价比中等**，适合 P4 前补齐。

### N4 断点续跑 / Checkpointer

- **接上后**：知识导入/AML 扫描/人工审批等待等长时流程，在 Worker 崩溃或外部等待后可从安全断点继续，不重复执行已完成步骤。
- **收益**：解决"崩溃重跑全量"；让 Agent 支持真正长时任务（简历"长时断点续跑"卖点落地）。
- **风险**：checkpoint 里若存 prompt/检索正文/业务数据会泄露；恢复前必须重新校验权限，否则旧快照可越权恢复。
- **前提**：按计划书复用 `AsyncTask + Outbox + Redis Streams + 状态机`，**不先全局上 LangGraph Checkpointer**；先选一个试点（AML 或知识导入），定快照 schema 和幂等/恢复矩阵。
- **预测**：这是**最值得做**的一块，但要在 P2 收口后、用一个真实长时流程试点推进。

### N5 Milvus 生产检索

- **接上后**：把在线检索从 pgvector 切到 Milvus（`VECTOR_STORE_BACKEND=milvus`），factory 返回 `MilvusVectorStore`。
- **收益**：大数据量下向量检索扩展性；简历"Milvus 选型"落地。
- **风险**：**当前在线是"向量+全文+权限+版本"同库 JOIN 的混合检索**，切 Milvus 后全文/权限过滤得拆到别处，架构改动大且容易退化。
- **前提**：先做 pgvector vs Milvus 的 top-K/召回/延迟对比（计划书 P5），确认收益再切。
- **预测**：**目前不建议切**——pgvector 同库 JOIN 是当前架构的优势；Milvus 保持"可配置替代后端"即可，答辩时如实说。

### N6 Redis 幂等组件

- **接上后**：给"需要快速响应缓存式幂等"的接口（如通知、重复回调）接上 `IdempotencyStore`。
- **收益**：比 DB 唯一索引更快、适合高并发去重场景。
- **风险**：Redis 无持久化，进程崩溃/故障时幂等记录可能丢失，需结合业务兜底。
- **预测**：交易链路**不该换**（DB 方案更稳），留给其他场景复用即可。

### N8 自由 NL2SQL

- **接上后**：模型直接生成 SQL 并执行。
- **收益**：分析范围广、少建模板。
- **风险（高）**：Prompt 注入、越权表字段、口径漂移、审计无法解释。计划书明确这是否决项，`nl2sql_ready=False`。
- **前提**：补齐 AST 校验、行级范围、只读执行、审计四件套后**才能考虑放开**；即使放开也建议走"模型生成结构化 IR → 服务端编译参数化 SQL"而不是直接执行模型 SQL。
- **预测**：**不要接**；保留"目录召回 + 模板执行"现状，作为差异化卖点讲反而加分。

### N10 LLM 意图回退

- **接上后**：规则低置信时用 Qwen 结构化兜底（现已是 shadow 模式代码，把开关打开）。
- **收益**：覆盖复杂自然语言（指代、否定、多意图、模糊金额）。
- **风险**：模型幻觉转执行风险；必须经 IntentPolicyResolver 单向合并 + allowlist。
- **前提**：先建复杂中文评测集（计划书 P2.1/P2.2），验证正确率/误执行率达标再默认开启。
- **预测**：**值得逐步开**，但先要评测基线；默认关闭是当前安全状态。

## 5. 给答辩/面试的建议口径

1. **主线话术**："系统已跑通 P0-P2 的确定性底座；P3 共享记忆、P4 断点续跑是有文档化计划的下一阶段，不是没做完。"——用 `NEXT_STEPS` 的排期撑腰。
2. **被问"LangGraph 呢"**："已定义 `ports/agent.py` 契约和 `SupervisorGraph` 骨架，真实执行用确定性管线保证可审计；真图是 P3/P4 演进项，避免早期引入 checkpoint 复杂度。"
3. **被问"记忆怎么没接"**："短期记忆已接入；长期记忆服务就绪，按 P3 最小工作记忆方案接，且严格限'客服转人工摘要'场景、读时重校验权限。"
4. **被问"为什么不做自由 SQL / 自由 Agent"**："金融场景下，可静态审查的模板 + 目录白名单 + 绑定参数 + 失败回滚，比模型自由生成 SQL 更可证明安全；模型只做解释，不直接执行。"
5. **被问"Milvus / Neo4j 呢"**："作为可切换后端/可选增强已留接口，当前 pgvector 同库混合检索是架构优势，Milvus 是 P5 性能对比项。"
