# 数据库设计答辩提纲（可能问到"我的设计"）

> 依据：`app/models/*.py` 真实模型（50 张表），权威文档 `docs/DATABASE_TABLE_REFERENCE.md`。
> 用法：先背"一句话总览 + 核心原则"，再按领域答高频题；被追问设计动机时引用"为什么这么做"。

---

## 一、一句话总览

> "系统以 PostgreSQL + pgvector 为唯一业务事实源，50 张表按领域分为：身份权限、客户资产、资金交易、风险AML、工单通知、客服会话、记忆、知识库RAG、数据目录NL2SQL、异步基础设施、审计。核心设计是**确定性规则写库、模型不碰库、幂等与审计贯穿**。"

## 二、核心设计原则（先背这几条）

1. **业务事实源唯一**：客户/账户/订单/资金/风评/权限/审计都只在 PostgreSQL；Redis/Milvus/MySQL 迁移库不替代。
2. **金额一律 `Numeric(18,2)`，禁 float**——杜绝浮点误差；份额 `Numeric(18,4)`。
3. **幂等靠数据库唯一索引兜底**，不靠代码判断：`orders.idempotency_key`、`notification.idempotency_key`、`async_task.idempotency_key`、`nl_draft.confirmation_token_hash` 都有唯一约束。
4. **软删除 + 审计不物理删除**：订单/产品/文档用 `deleted_at`；交易/审计/风控不物理删。
5. **UUID 主键**（String36/UUID），利于异步任务、跨服务、数据导入。
6. **状态机单一权威**：订单迁移只在 `Order.transition()`，每次迁移写 `order_status_history`。
7. **事件与业务同事务**：Outbox（`outbox_event`）与业务行一起 commit，保证"业务成功⇒事件必达"。
8. **模型不直接写库**：Agent 只通过确定性 Service 落库，金融事实不被模型覆盖。

## 四、高频面试题 + 答案

### Q1：为什么选 PostgreSQL + pgvector，而不是 MySQL 或纯 Redis？
**答**：三个理由。①**向量与业务同库同事务**——混合检索（向量+全文）和权限/版本过滤能在同一 SQL JOIN 里做，不用拆两套系统；②**数据一致性**——订单/资产/审计这些强一致数据用关系型最稳，Redis 做不了事务；③**一套运维**——少维护一个向量库。MySQL 只作为迁移验证的隔离库，不服务交易（`main.py` 明确禁止 `DATABASE_BACKEND=mysql` 服务交易路由）。

### Q2：幂等是怎么实现的？为什么用数据库唯一索引而不是代码判断？
**答**：靠**唯一部分索引**兜底。比如 `orders.idempotency_key` 有 `ux_orders_user_idempotency_key(user_id, idempotency_key)`；`create_order` 先 `get_by_idempotency` 预查（命中直接返回旧单），最坏并发下两个请求同时 miss，后插入者撞唯一索引抛 IntegrityError，映射成 `IDEMPOTENCY_CONFLICT` 409。**预查是优化路径，唯一索引才是"只成功一次"的保证**——这比"先查后写"的代码判断更防并发竞态。

### Q3：金额为什么用 Numeric 不用 float？
**答**：float 是二进制浮点，0.1+0.2≠0.3，累计会漂移；金融金额必须精确。用 `Numeric(18,2)`（定点）加 Python `Decimal` 计算，冻结/解冻/扣款一致。份额用 `Numeric(18,4)`。

### Q4：订单状态为什么单独一张 `order_status_history`？
**答**：只看当前 `status` 无法追溯"谁在何时把订单从哪移到哪"。单独历史表 + 每次 `transition()` 追加一条 (from, to, operator, note)，满足金融可审计、可排查纠纷。`transition()` 是唯一权威迁移表，非法迁移抛错。

### Q5：记忆表怎么设计的？为什么 `customer_memory` 用部分唯一索引？
**答**：`customer_memory`（记忆卡片）+ `customer_memory_event`（事件审计）。部分唯一索引 `uq_customer_memory_active_key(customer_id, key) WHERE status='active'` 保证**同一客户同一 key 只有一条 active 记忆**——这是"记忆卡片"语义的数据库层保障，避免同 key 多条互相打架。事件表记录每次 upsert，可追溯来源。记忆只存客户确认参数/偏好/非敏感事实，业务事实以业务表为准。

### Q6：RBAC 怎么建表？为什么权限分开存？
**答**：五表——`users/roles/permissions/user_roles/role_permissions`。权限码独立成表（如 `order:review`），角色通过关联表组合权限。好处：**角色代表分类、权限码代表能力、二者解耦**，改权限不动角色、新增权限不动代码；配合 `auth_seed.py` 的权限矩阵做种子装载。

### Q7：权限/数据隔离怎么落库？怎么防越权？
**答**：操作级用 RBAC 权限码；**数据级用 `customer_advisor_authorization`**——存"客户→投顾"授权记录，含 `allowed_actions/product_scope/max_amount/risk_level_ceiling` 业务边界。运行时 `SubjectScopeService` 从授权表算授权客户集合，数据分析时把 SQL 的 subject 参数**服务端改写为授权闭包**，客户传什么 id 都绕不过。权限缓存版本号（INCR）使旧缓存失效，不靠缓存判断授权。

### Q8：知识库为什么拆三张表（document/version/chunk）？版本化怎么做？
**答**：`knowledge_document`（稳定文档身份+当前版本指针）、`knowledge_document_version`（不可变版本）、`knowledge_chunk`（文本分块+pgvector 向量）。**版本化**：新版本切分/向量写入成功后，`activate_version` 把旧版本标 superseded、`current_version_id` 指向新版，检索只 JOIN 激活版本——避免半成品知识上线，旧版可回溯。chunk 级 `content_hash` 复用 embedding 省成本。

### Q9：NL2SQL 靠哪些表支撑安全？
**答**：`data_catalog_domain/table/column/relation/example_query/revision` 六表。`example_query` 存**受审 SQL 模板**（`is_approved`、`sql_template`、声明白名单、allowed_roles），`table/column` 带 `is_queryable/is_sensitive` 和向量，`revision` 做目录变更审计。运行时"目录召回 + 模板白名单 + 引用范围校验"，模型只填参数不拼 SQL。

### Q10：为什么有 `outbox_event` 和 `async_task` 两张异步表？
**答**：`outbox_event` = **事务发件箱**，与业务行同事务提交，业务成功事件必落库，`outbox_worker` 用 `FOR UPDATE SKIP_LOCKED` 认领发布到 Redis Stream；`async_task` = **后台任务追踪**，存 task_type/status/attempt/max_attempts，供重试、死信、断点恢复。前者解决"业务与事件一致"，后者解决"长任务可追踪可恢复"。

### Q11：软删除 vs 物理删除怎么权衡？
**答**：**业务主数据**（产品/文档/客户）用软删除 `deleted_at`，保留历史、可恢复、可审计；**交易/审计/资金/风控**原则上不物理删。只有纯缓存/临时数据才物理删。软删除配合唯一索引时注意（如产品重名），用部分唯一索引或唯一含 deleted_at。

## 五、可能被追问的"设计边界"（诚实版）

1. **MySQL**：只做迁移验证，未全量迁移，不是双主双写（`DECISIONS.md` 明确弃用 PG+MySQL 双主）。
2. **记忆长期链路**：表和服务已实现，但 Agent 链路只接了短期记忆，长期是 P3 计划。
3. **数据目录**：`nl2sql_ready=False`——目录+模板是现状，模型自由生成 SQL 被关闭。
4. **没有独立的向量库/图谱**：在线走 pgvector 同库；Milvus/Neo4j 是 P5 可选。

## 六、一句话收尾

> "我的数据库设计不是'存数据的表'，而是**把金融的强一致、强监察、强控制落到表结构上**——幂等靠唯一索引、状态靠历史表、权限靠授权表、异步靠 outbox、审计靠不改不删。表结构本身就承载了业务规则，而不只是存取容器。"
