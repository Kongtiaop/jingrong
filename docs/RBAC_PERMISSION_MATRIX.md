## 1. 设计原则

1. **角色不等于权限**：用户可拥有多个角色；最终授权由权限集合和数据范围共同决定。
2. **后端为最终边界**：前端菜单/按钮隐藏只改善体验，不能作为授权依据；每个受保护 API 必须执行服务端鉴权。
3. **本人、已授权、全量范围分离**：客户只能访问本人数据；投顾只能访问有效授权客户；工作人员按岗位权限访问必要范围。
4. **最小权限与职责分离**：客户资料维护、投顾建议、风险处置、交易审核、审计只读、系统管理不得用一个粗粒度权限混用。
5. **高风险操作可审计**：交易审核、交易限制、解除限制、可疑交易报告、角色权限修改必须记录审计日志；需要时追加二次确认与业务状态机约束。
6. **超级管理员例外受控**：保留超级管理员的系统维护能力，但矩阵测试中仍需验证其明确允许的行为，不能以“默认全放行”代替契约。

## 2. 角色目录

| 角色代码 | 名称 | 定位 | 当前状态 |
|---|---|---|---|
| `customer` | 普通客户 | 仅处理、查看本人金融资料与业务申请 | 已实现 |
| `customer_service` | 客服 | 客户服务、基础查询；不承担资金类高风险写操作 | 已实现，需收敛职责 |
| `customer_manager` | 客户经理 | 客户资料维护、服务工单、代客户转账申请等客户经营职责 | 已新增（P-E2），业务权限仍待拆分 |
| `advisor` | 理财顾问 | 在客户授权范围内分析画像、推荐产品、创建投顾操作草稿、发起风险复评 | 已新增（P-E2），目标权限码仍待迁移 |
| `product_manager` | 产品工作人员 | 产品、状态、适配规则、产品知识资料管理 | 已实现 |
| `risk_manager` | 风控专员 | 预警、AML 扫描、调查、风险动作、报告草稿/上报 | 已实现，需细分权限 |
| `operations` | 运营/交易运营 | 待审核业务、订单/赎回/转账审核执行、业务异常处理 | 已实现，需细分权限 |
| `auditor` | 审计人员 | 只读审计、业务、风险、权限与配置记录 | 已实现，需确保绝不具备状态变更权限 |
| `super_admin` | 超级管理员 | 用户、角色、权限、系统配置与全局治理 | 已实现 |
| `employee_pending` | 待分配员工 | 尚未授予业务权限的内部账号 | 已实现 |

### 2.1 角色迁移约束

- `customer_service` 不再兼任“客服/客户经理”；新增 `customer_manager` 后，资金和敏感客户维护类职责迁移至 `customer_manager`。
- `product_manager` 不再被用作临时投顾身份。
- `advisor_user` 仅认可 `advisor`（以及经明确约定的超级管理员），不再依赖 `advisor_staff`、`investment_advisor` 等未种子化别名。
- 历史角色兼容仅可作为短期数据迁移策略；必须记录迁移窗口和移除日期。

## 5. 当前实现盘点与差距

### 5.1 已具备

- 已有 RBAC 模型：`users`、`roles`、`permissions`、`user_roles`、`role_permissions`。
- 已有 Access Token / Refresh Token 与后端 `require_permission`、`require_staff_permission` 鉴权基础。
- 已有 7 类正式演示角色和超级管理员。
- 已对客户后台、投顾工作台、风险预警、业务操作等模块完成一轮接口/导航权限巡检。
- 已修复客户通过 `customer:read` 访问工作人员客户列表的越权问题。

### 5.2 必须修复的差距

| 编号 | 差距 | 风险 | 优先级 |
|---|---|---|---|
| RBAC-001 | 没有正式 `advisor` 角色，投顾接口依赖未种子化角色别名，且历史上复用 `product_manager` | 投顾职责与产品管理职责混乱，无法稳定测试 | P0 |
| RBAC-002 | `customer_service` 同时表示客服/客户经理 | 客服可能被赋予不应拥有的客户敏感修改、转账类职责 | P0 |
| RBAC-003 | `customer:read` 同时被客户本人和工作人员使用 | **P-E3.1 已迁移工作人员客户管理与投顾范围；客户本人专属权限码仍待后续拆分** | P0（部分完成） |
| RBAC-004 | `order:write` 同时覆盖代办、审核、执行、待办/审计查看 | **P-E3.2 已迁移主要订单/业务操作 API；旧权限仅保留兼容，`tasks` 归属仍待确认** | P0（部分完成） |
| RBAC-005 | `risk:write`、`audit:read` 混合预警查看、处理、动作和批次语义 | **P-E3.3 已迁移风险 API；旧权限保留兼容，审计专用业务范围仍待细分** | P0（部分完成） |
| RBAC-006 | 工单意图在功能设计中明确存在，但没有 `workorder:*` 权限域 | 客服、客户经理、风控、运营的工单职责不可控 | P1 |
| RBAC-007 | 当前前端可见性主要根据旧权限码和角色别名 | 新矩阵落地后菜单与后端契约可能不一致 | P1 |
| RBAC-008 | 尚无统一“角色 × API × 预期状态码”自动化矩阵 | 已有零散回归，难以防止后续权限回归 | P0 |

## 7. 测试矩阵与通过标准

每个受保护 API 至少覆盖：

| 场景 | 预期 |
|---|---|
| 未登录 | `401` |
| 有对应权限且在数据范围内 | `200/201/204` |
| 无对应权限的内部角色 | `403` |
| 客户访问工作人员接口 | `403` |
| 工作人员跨客户或投顾未授权客户 | `403`（或按接口规范统一为 `404`） |
| 审计员访问状态变更接口 | `403` |
| 超级管理员 | 根据本文档的明确授权契约通过，不以默认放行为测试依据 |
| 前端入口 | 不显示无权菜单/按钮；即使手工请求仍由后端拒绝 |

建议脚本分层：

```text
scripts/test_rbac_permission_matrix_http.py   # 总矩阵
scripts/test_role_permission_boundaries_http.py # 保留为已有重点回归
scripts/test_backoffice_role_surface_http.py    # 保留为页面/API 表面巡检
```
