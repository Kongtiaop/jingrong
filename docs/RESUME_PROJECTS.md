# 项目一：多 Agent 智能财富管理平台（主项目）

**项目时间：** 2026.07 – 至今  
**项目角色：** AI 应用开发负责人  
**技术栈：** Python、FastAPI、LangChain、LangGraph、Qwen/DashScope、PostgreSQL、pgvector、Redis/Redis Streams、Vue 3、TypeScript、SQLAlchemy、Alembic、Docker Compose、Pytest、Playwright

## 1. 项目概述

面向财富管理业务构建可控的多 Agent 平台，覆盖客户服务、客户画像与产品推荐、风险评估、经营数据分析、订单/工单查询及自然语言申购辅助等能力。

系统的核心设计不是让大模型自由决策或直接执行高风险操作，而是通过 **Supervisor 统一编排 + Agent 能力注册 + 权限/数据范围绑定 + 确定性业务规则 + 审计与人工兜底**，将 AI 限制在可解释、可验证的辅助决策范围内。客户最终仍通过风险测评、适当性、订单状态机、人工审核等确定性链路完成业务闭环。

## 3. 核心职责与技术亮点

### 3.1 多 Agent 编排与安全边界

- **设计 Supervisor + 专项 Agent 架构**：以 Supervisor 作为统一入口，按用户意图将请求分发至客服、投顾、风控、数据分析、业务等领域 Agent，避免将所有业务堆叠在单一 Chatbot 中；基于 LangGraph 构建 Agent Graph，并设置最大迭代次数、最大工具调用次数，限制 ReAct 循环失控。

- **建立 Agent Capability Registry（能力注册表）**：将可调用能力以白名单形式注册，并按用户类型、角色权限、当前客户主体、适当性状态和业务状态机限制调用范围；内部 Agent 不直接暴露给终端客户，避免模型绕过业务授权链路。

- **区分三类执行范式**：对客服等低风险、需要多轮检索的场景使用 bounded ReAct；对申购、订单、风控等高风险场景使用受控工作流；对投顾建议采用“Plan + Rules”模式，由模型组织解释、由服务端规则完成最终校验。

- **实现统一执行上下文**：将用户身份、角色、权限、授权客户范围、会话信息和业务主体注入 Agent 执行上下文；服务端而非前端或模型文本负责绑定 customer_id / subject scope，防止跨客户查询和参数篡改。

### 3.2 AI 驱动但不越权的财富业务闭环

- **实现“自然语言申购 → 订单草稿 → 预检 → 显式确认 → 幂等建单”链路**：用户可在统一 Agent 对话窗口输入申购意图；系统只生成持久化订单草稿，不直接创建订单、不冻结资金、不直接成交。后端完成产品状态、适当性、风险等级、客户范围及金额规则预检，只有在用户明确确认后才进入既有订单链路。

- **设计交易幂等与确认令牌机制**：确认令牌仅在当前草稿响应中使用，浏览器不持久化；服务端校验令牌有效性，错误令牌拒绝、重复确认返回同一订单，降低重复提交和前端重试造成的重复建单风险。

- **接入实时产品推荐能力**：将“推荐产品”从静态知识问答中剥离，改为基于实时 Product 数据、客户画像、持仓与适当性服务输出推荐结果与规则解释，避免 RAG 文档过期导致不适配推荐。

- **实现风险与适当性前置校验**：前端可提前展示产品风险等级与购买资格提示，但最终适当性判断始终由服务端完成；Agent 仅负责解释和引导，不能覆盖风险测评、客户分层和订单状态机。

### 3.3 数据、权限与合规治理

- **建设 JWT + Argon2 + RBAC 的基础认证授权体系**：通过 JWT 鉴权、Argon2 密码哈希及角色权限矩阵控制 API 和 Agent 能力访问；结合主体授权范围，实现客户经理/投顾仅能访问被授权客户的数据。

- **实现权限感知缓存策略**：使用 Redis 缓存角色权限范围内的数据目录与分析结果，并引入 `permission-context-version`。当管理员调整用户角色或角色权限时递增版本，使旧权限缓存不会在新权限上下文中被命中。

- **完善可观测与审计基础设施**：封装统一响应、异常处理、请求 Trace、限流、敏感信息脱敏和审计边界；记录 Agent 调用、工具执行、拒绝、转人工、订单草稿和确认等关键事件，便于问题回溯与合规审查。

### 3.4 异步架构与工程化交付

- **基于 Redis Streams 设计异步任务体系**：采用 Outbox + Worker 模式处理通知、知识库导入、数据目录 Embedding、客服会话超时、AML 日扫等任务，降低同步 API 对耗时操作和外部模型调用的依赖。

- **实现实时客服同步与断线补偿**：围绕客服会话设计实时消息同步、会话遗留处理、超时转人工及断线补偿策略，保证用户离线或网络中断时仍可恢复关键服务状态。

- **采用模块化单体分层**：后端划分 API、Service、Repository/Port、Infrastructure Adapter；数据库与向量库通过 Port/Adapter 隔离，当前可本地容器化演示，后续可按业务边界拆分服务。

- **建设分层、共享且可治理的 Agent Memory 架构**：在现有 Redis 会话短期记忆与 PostgreSQL 长期客户记忆基础上，设计从原始对话流水、原子记忆卡片、场景档案到稳定客户画像的 L0–L3 分层模型；通过 `private/shared/organization` 作用域控制多 Agent 共享边界，并为记忆补充来源、置信度、有效期、过期时间、冲突关系和替代关系，解决多 Agent 记忆孤岛、事实更新和可追溯问题。

- **将 Hindsight Memory 的“记忆而非聊天记录”理念融入金融场景**：把原始会话、事实抽取、情境聚合和长期画像解耦，采用“同步快速落盘 + 异步提炼/聚合”的写入方式；检索时采用当前任务/场景优先、语义与关键词混合召回、时间衰减及高风险事件强制唤醒，避免将整段历史对话直接塞入上下文造成噪声和 Token 膨胀。

- **设计记忆的时间语义与冲突消解机制**：对于偏好、已确认参数、风险提示、会话结论等可变化信息，按 `(主体, 属性, 值, 生效时间)` 形成结构化事实；新事实不直接覆盖旧记录，而是用 `valid_from/valid_to` 标记版本有效区间，并保留 `superseded_by/conflict_with` 关系与事件日志，支持审计回放、历史追溯和冲突仲裁。

- **明确“记忆、RAG 与权威业务事实”的边界**：RAG 用于检索政策、产品说明等外部知识；Memory 用于保存客户确认的偏好、上下文和任务事实；余额、持仓、风险等级、交易状态、身份、产品状态等权威金融事实始终从业务表读取，禁止由 Agent Memory 推断、覆盖或替代。

- **建设自动化验证闭环**：通过 Pytest、真实 HTTP 回归和 Playwright 浏览器 E2E 覆盖自然语言申购、推荐、权限与客服交互等关键链路；通过 Docker Compose 编排 PostgreSQL（含 pgvector）、Redis、Milvus、API 与 Worker，保证开发/演示环境一致。

## 5. 可在面试中重点展开的技术问题

1. **为什么不是一个万能 Agent？**  
   财富管理包含客服、投顾、风控、订单与数据分析等不同风险等级的任务；通过 Supervisor 分流和专项 Agent 的工具白名单，可以限制权限边界、减少提示词膨胀，并让每一类能力有独立审计与回退策略。

2. **如何避免 AI 直接执行金融交易？**  
   模型只负责识别意图、补充参数和生成解释；订单必须经过草稿、服务端预检、用户显式确认和既有订单状态机，关键校验由确定性服务完成。

3. **如何防止 Agent 越权访问客户数据？**  
   由服务端把当前用户、角色、权限和授权客户范围绑定进执行上下文；模型无法通过文本提交任意 customer_id，查询和工具调用均由后端再次校验。

4. **为什么要单独做 Memory，而不是把聊天记录向量化？**  
   聊天记录向量化只能“找相似片段”，缺少更新、冲突和时间语义。项目借鉴 Hindsight Memory 的分层思想：L0 保留原始证据，L1 保存可更新的结构化事实，L2 按投资/服务/风控等场景聚合，L3 形成稳定画像；对于新旧事实使用有效期和替代关系，而不是粗暴覆盖。

5. **Memory 为什么不能作为金融事实源？**  
   记忆属于 Agent 的辅助上下文，可能来自用户陈述或模型提炼；余额、持仓、风险等级、交易状态等必须以业务数据库和审计记录为准。该边界既保证 Agent 有连续性，也防止过期或错误记忆影响合规决策。

6. **如果用户说“我改了手机号”，Memory 与业务库不一致怎么办？**  
   这是“用户指令/陈述”与“权威业务事实”的冲突。Agent 只识别修改意图，不直接更新长期画像或业务表；系统将其路由至身份核验流程或“修改个人信息”工单。业务库成功更新后，再通过事件把已验证结果同步为权威事实；在此之前，用户陈述最多以“待验证”的短期/原子记忆存在，检索时不参与高风险决策。

# 项目二：知识底座与数据安全分析中台（RAG + 目录约束型 NL2SQL）

**项目时间：** 2026.07 – 至今  
**项目角色：** AI 应用开发负责人  
**技术栈：** Python、FastAPI、PostgreSQL、pgvector、Milvus、Redis、Qwen/DashScope、LangChain、SQLAlchemy、Docker Compose

## 1. 项目概述

为多 Agent 财富管理平台提供可控的知识问答和经营数据分析底座。项目重点解决金融场景中 RAG 的幻觉、知识过期、权限隔离、引用缺失，以及自由 NL2SQL 带来的 Prompt 注入、越权查询和高风险 SQL 执行问题。

技术路线为：**RAG 必须提供证据和降级路径；数据分析不采用自由生成 SQL，而采用“数据目录召回 + 已批准模板 SQL + 服务端授权绑定”的受控执行模型。**

## 2. RAG 核心实现与优化

- **实现版本化知识库建模**：以文档、文档版本、Chunk、向量及元数据构成知识闭环；文档重新导入时基于内容 Hash 创建版本、保留历史、激活最新版本，保证问答引用可追溯到具体资料版本。

- **实现 Chunk 去重与 Embedding 复用**：按 Chunk 内容计算 SHA-256，导入新版本时查询可复用向量，仅对新增或变更 Chunk 调用 Embedding 接口，减少重复向量化成本，并提升文档更新效率。

- **实现结构化切块与引用证据返回**：默认按约 1000 字符、120 字符重叠进行切块；检索结果包含文档 ID、版本 ID、Chunk ID、分数、标题路径、页码及元数据，回答端可向用户或审计系统展示依据。

- **实现文本 + 向量混合检索及多级降级**：正常链路优先使用 Embedding 与混合召回；Embedding 超时/失败时回退关键词检索，向量检索异常时再回退文本检索；低置信度时不强行生成答案，而是转人工或创建工单。

- **引入 Knowledge Scope 隔离知识域**：按公开客服知识、内部知识、风控资料等维度限制检索范围；明确产品推荐必须调用实时业务数据与适当性服务，而不是仅从静态产品文档生成结论。

- **构建引用约束生成链路**：Prompt 强制模型“只根据引用回答”，资料不足时明确拒答；禁止编造、收益承诺和直接交易指令，并对模型不可用、空回复和生成异常提供兜底文案。

- **设计可插拔向量库接口**：默认使用 PostgreSQL + pgvector 支撑业务检索，同时通过 VectorStore Port/Adapter 接入 Milvus，用于后续检索性能、索引策略和大规模向量数据的横向评估。

## 3. NL2SQL 安全设计与优化

- **从自由 NL2SQL 收敛为目录约束型模板执行**：不允许模型直接生成可执行 SQL；将自然语言问题路由至已经审核的示例问题/SQL 模板，通过参数提取和绑定获得最终只读查询。

- **构建企业数据目录（Data Catalog）**：维护表级、字段级、关系级和示例查询元数据，包括业务描述、数据粒度、敏感性、可查询标识、聚合能力、角色限制、别名、样例值及向量信息，为自然语言分析提供动态候选范围。

- **实现“目录召回 + 模板白名单 + 引用范围”三重校验**：先根据用户角色进行文本/向量混合召回，再校验 SQL 实际引用的表与字段是否同时处于模板声明白名单和目录候选白名单内，阻止模板被篡改、越权表字段引用和模型诱导执行。

- **实现 SQL 安全策略层**：独立 `nl2sql_policy` 纯策略模块，统一处理 SQL-shaped 输入拒绝、只读校验、固定指标路由、角色匹配、目录范围判断和参数合法性检查，供在线分析与离线评估共用，避免业务规则在多个脚本中漂移。

- **实现参数安全契约**：模板参数显式声明类型；自然语言只允许解析 `natural_language` 参数，整数、日期范围等参数必须满足边界；涉及客户主体的参数由后端授权上下文绑定，不能信任用户输入的任意 subject ID。

- **权限与缓存协同优化**：以权限指纹和 `permission-context-version` 组成缓存 Key；角色或权限变更后批量递增关联用户的版本号，避免旧缓存泄露已撤销的数据访问范围。

## 4. 简历可直接使用版本

> 负责金融 RAG 与安全数据分析底座建设：基于 FastAPI、PostgreSQL/pgvector、Qwen、Redis 实现文档版本管理、Chunk Hash 去重、Embedding 复用、混合检索、知识 Scope 隔离和引用式生成；Embedding/检索异常自动降级，低置信度转人工。针对金融数据分析摒弃自由 NL2SQL，设计“数据目录召回 + 审核 SQL 模板 + 表字段双白名单 + 服务端授权绑定”的目录约束型执行链路，并通过独立 SQL 策略层、参数安全契约和权限版本化缓存控制 Prompt 注入、越权查询与缓存泄露风险。

## 5. 可在面试中重点展开的技术问题

1. **RAG 如何减少幻觉？**  
   从“检索到内容就让模型回答”升级为“检索证据—置信度判断—引用约束生成—不足则转人工”；并将产品推荐等强实时业务数据与文档问答解耦。

2. **为什么要做 Chunk Hash 复用？**  
   文档版本更新时，大量内容通常没有变化。通过内容 Hash 复用历史向量，可避免重复调用 Embedding，降低成本并缩短导入耗时，同时仍保留每个版本的 Chunk 关系。

3. **为什么不让模型直接生成 SQL？**  
   金融数据涉及权限、敏感字段和聚合口径。自由 SQL 难以稳定验证，容易被 Prompt 注入或越权绕过；因此采用经过审核的只读模板和目录动态白名单，让模型只参与意图理解与参数补全。

- 建设更完整的 Human-in-the-loop：对大额申购、风险等级变化、异常 AML 信号和敏感数据分析引入二次认证、人工审批和升级策略。

## RAG 与检索迭代

- 升级为结构感知切块：结合文档标题层级、段落、表格、页码及章节路径构建语义 Chunk，改善制度文件和产品说明书的召回质量。
- 增加 Query Rewrite、意图路由、关键词/向量融合权重配置、Cross-Encoder Rerank 和多路召回融合，提升复杂中文问法、同义表达及长尾问题效果。
- 构建 RAG 评测集：从命中率、上下文覆盖率、引用正确率、忠实度、拒答正确率、转人工率、延迟和 Token 成本等维度评估检索与生成效果。
- 引入知识变更治理：资料有效期、审批、失效提醒、版本差异比对、敏感内容审核和按租户/部门/角色的细粒度知识权限。

## NL2SQL 与数据分析迭代

- 在现有模板执行基础上演进为**受控 SQL IR（中间表示）**：模型只生成结构化查询计划（指标、维度、筛选、时间范围），服务端从目录候选表字段编译参数化 SQL，并经过策略/人工审批后执行。
- 引入语义指标层与口径治理：将“客户数、AUM、订单量、转化率”等指标定义为统一 Metric，避免不同 Agent 或不同 SQL 模板口径不一致。
- 增加查询成本预估、行数限制、超时、脱敏列投影、审计回放和异常访问检测，进一步提升大规模数据分析场景的安全性和可运营性。
- 支持数据目录的自动 Embedding、变更检测和示例查询推荐，提升新增表/字段后的分析接入效率。
