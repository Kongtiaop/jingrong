1、记忆架构图体系，你如何应用在你的Agent中

我们的系统采用“短期会话记忆 + 客户长期记忆 + 共享工作记忆 + 业务事实/知识库”分层，而不是把所有内容直接拼接到 Prompt 中。当前已实现和规划中的应用如下：

（1）短期会话记忆：服务于当前会话的上下文连续性。CustomerServiceAgent 通过 conversation_id 关联 Redis 短期状态和 PostgreSQL 长期记录，保存最近对话摘要、澄清次数、待处理意图计划、人工交接状态和最近任务结果。它用于处理“我刚才说的那个产品”“继续刚才的查询”等连续请求，但不会被当作真实业务事实。

（2）客户长期记忆：服务于跨会话的稳定信息，例如客户明确表达的投资目标、风险偏好、资料缺口、人工确认过的客户信息等。长期记忆需要来源、确认状态、时间、作用域和可撤销能力。系统已有 CustomerMemory/MemoryService 基础，当前阶段不把模型推断直接写成客户事实。

（3）共享工作记忆：用于客服、投顾、风控、数据分析和业务 Agent 之间传递“已确认的任务上下文”，例如“客户正在咨询某产品”“客户已补充某项材料”“订单草稿待客户确认”“风险规则返回某个 rule_id”。共享工作记忆不保存模型私有推理链、完整 Prompt、原始持仓/交易敏感数据副本。后续以客服转人工摘要作为第一个 MVP 场景，并继承 permission context、subject scope、TTL 和审计。

（4）业务事实与知识库：订单、账户、持仓、风险预警、工单、产品状态等事实必须从 PostgreSQL 等权威业务表实时读取；政策、产品说明、公司业务等非结构化内容通过知识库/RAG 检索。记忆不能替代业务事实，也不能让 Agent 绕过权限直接读取数据库。

在 Agent 中的实际组合方式是：

用户请求 → Supervisor/意图规划 → 权限和 subject scope 过滤 → 读取必要的短期记忆/共享工作记忆 → 调用只读工具、RAG 或受控业务服务 → 生成带 evidence 状态的回答/草稿 → 按策略异步保存摘要和审计。

对于交易流程，记忆只保存已经确认的交易上下文和草稿引用，不保存可直接重放的敏感请求体。最终产品、金额、账户、适当性、风控和订单状态仍由确定性业务服务裁决。


2、Agent的断点续跑/断点恢复功能是如何实现的？运行状态如何完成持久化与恢复？

当前系统采取“先复用可靠任务基础设施，再为真实长时工作流增加安全快照”的渐进方案。已有 AsyncTask、OutboxEvent、Redis Streams、Worker、重试、pending/XCLAIM、幂等键和状态机能力，可支撑任务的可靠投递与失败重试。

断点恢复的最小流程是：

1. 创建 workflow_id/async_task_id，并记录 workflow_type、当前 step、任务状态和幂等键；
2. 每个业务步骤执行前检查任务是否已取消、是否过期、权限是否仍然有效；
3. 步骤执行成功后只持久化安全输出引用、完成状态、输入指纹和下一步信息；
4. Worker 崩溃、网络失败或外部人工审批等待时，任务保持可恢复状态；
5. 恢复 Worker 扫描 pending/running/waiting 状态任务，读取最后一个安全快照；
6. 恢复前重新校验 RBAC、Agent capability、subject scope 版本、业务状态和幂等条件；
7. 从未完成步骤继续，而不是重放已完成的外部写操作；
8. 恢复、重试、取消、过期和人工介入均写入审计日志。

拟采用的最小恢复快照字段为：

workflow_id、workflow_type、step_name、status、input_fingerprint、permission_context_fingerprint、subject_scope_version、completed_output_references、idempotency_key、resume_token_reference、expires_at。

当前不把“模型完整上下文、完整 Prompt、原始客户敏感数据、模型私有推理链”作为可恢复快照保存。长时场景优先选择知识导入/向量化、AML 批次扫描、人工审批等待、风险调查报告或投顾诊断草稿。


3、为什么选择Redis保存工作流状态？图的状态快照具体保存哪些内容？

Redis 适合保存工作流的短期运行态和调度态，原因是：

（1）低延迟：Agent 节点之间、Worker 与队列之间需要快速读写；
（2）天然适合 TTL：会话状态、临时锁、等待令牌和短期恢复信息可以自动过期；
（3）适合队列与事件：项目已经使用 Redis Streams，能够支持消费者组、ACK、pending、重试和 XCLAIM；
（4）适合并发控制：可用于幂等去重、分布式锁、任务租约和唤醒标记；
（5）降低数据库压力：高频中间态不需要每一步都触发重型关系数据库事务。

但 Redis 不是唯一事实来源，也不是所有快照的永久存储。当前架构建议区分：

- Redis：保存短期运行状态、队列消息、消费者 pending、租约、临时 checkpoint 索引、等待 token 和 TTL 数据；
- PostgreSQL：保存 AsyncTask、OutboxEvent、业务状态机、审计日志和需要长期追溯的安全恢复快照；
- 对象存储（后续可选）：保存较大的非敏感产物，例如报告文件、图表工件或文档中间产物，数据库只保存引用。

图的状态快照不保存模型私有思维链，而保存可安全恢复的业务状态，例如：

- workflow_id、thread_id、workflow_type；
- 当前节点/步骤、状态、重试次数、失败原因；
- 已完成步骤及其输出引用；
- 输入参数的哈希/指纹，而不是敏感原文；
- 当前 permission context、subject scope version；
- 幂等键、外部调用引用、resume token；
- 等待原因、超时时间、expires_at；
- schema/version 和审计关联 ID。


4、Checkpoint在什么时机生成？每一个节点执行结束后都会生成吗？Checkpoint数据具体存储在哪里？仅存在Redis中，还是会同时落库到关系型数据库？

需要区分“临时运行态”和“安全恢复快照”：

（1）不是每一个模型内部思考步骤都生成 checkpoint。模型私有推理链不进入 checkpoint；工具调用过程也不保存完整 Prompt 和原始敏感返回值。

（2）在当前 P4 设计中，建议在以下时机生成安全 checkpoint：

- 工作流创建后，记录初始状态；
- 一个具有业务意义的受控步骤成功完成后；
- 状态从 running 进入 waiting_external、waiting_human、paused、failed 或 cancelled 前；
- 外部写操作成功并已确认幂等结果后；
- Worker 捕获可恢复异常前；
- 人工审批或 Webhook 等外部事件唤醒前后；
- 周期性长步骤达到安全边界时。

因此答案不是“每个节点结束都保存”，而是“每个可恢复的业务边界保存”。如果未来某个 LangGraph 流程使用 Checkpointer，可以按节点边界生成，但仍需经过数据脱敏、权限绑定和 TTL 策略，不能机械保存全部状态。

（3）存储策略不是只放 Redis：

- Redis 保存短期、快速读取的运行态、队列/消费者状态、租约和临时唤醒信息；
- PostgreSQL 保存可审计、需要跨进程和长期恢复的安全快照，或至少保存 AsyncTask 与关键恢复索引；
- OutboxEvent 用于保证业务状态提交与异步事件发布的一致性；
- 大型非敏感结果保存为对象引用，不将大内容塞入 Redis 或 checkpoint。

推荐的恢复顺序是：PostgreSQL 读取权威任务和最新安全快照 → Redis 恢复调度/租约/队列上下文 → 重新鉴权和检查业务状态 → 从安全步骤继续执行。


5、意图识别具体是怎么做的？用户一句话包含多个问题/多个意图时如何处理？

当前系统采用“确定性第一轮识别 + 受控 Agent 执行”的方式，不完全依赖大模型自由分类。

CustomerIntentPlanner 会先对文本做标准化，再使用意图模式、关键词和实体提取形成 IntentPlan。当前已有的意图包括：company_info、company_business、faq、workflow、policy、risk_public、product_status、order_status、workorder_status、asset_summary、risk_restriction、product_recommendation、business_operation 和 human_handoff 等。

实体提取目前重点提取订单号、工单号、产品名称等明确标识，不凭空推断客户没有说出的产品、金额或账户。

多意图处理过程为：

1. 同一句话匹配多个意图；
2. 对重复意图去重，生成多个 IntentTask；
3. 为每个任务分配 task_id、route、confidence、priority、depends_on 和 execution_mode；
4. 根据任务依赖先后执行，例如先查订单状态，再解释订单处理流程；
5. 只读查询可以受控并行，避免互相依赖的任务并行；
6. 汇总各任务结果，保留每个任务的 evidence_status、数据和错误；
7. 某个任务参数不足时只对该任务澄清，不让整个请求无条件执行；
8. 低置信度、连续澄清失败或客户要求人工时，创建人工交接。

例如：

“帮我查订单状态、账户风险限制和资产情况”

会被拆成：order_status、risk_restriction、asset_summary 三个任务，分别路由到客户事实查询、风险查询和资产分析能力，最后由 Supervisor 汇总回答。

对于“推荐一个产品并帮我买入”这类请求，推荐和交易不是一个无条件执行动作：先进行适当性推荐和风险解释，再收集产品、金额、账户等交易参数，生成订单草稿，经过预检和用户明确确认后才创建订单。


6、怎么让模型区分主意图和次要意图？主次意图对后续路由、回答流程有什么影响？

主次意图不是让模型凭感觉决定，而是由多个信号共同决定：

- 明确的行动词：申购、赎回、转账、下单通常优先级高于查询/解释；
- 用户句子的请求顺序和语气；
- 是否存在资金、订单、风险或人工操作后果；
- 任务依赖关系：交易前需要先完成推荐/适当性和参数收集；
- 置信度与权限：高风险任务即使是次要表达，也不能被忽略；
- 明确的用户确认：不能把“顺便帮我买”当成已确认下单。

当前路由优先级中，`operation_risk` 高于 `advisor_risk`，`advisor_risk` 高于 `risk`，再高于 `analysis` 和 `customer_service`。这表示“我要推荐并下单”会进入 BusinessAgent + RiskAgent 的受控路线，但不表示立即执行。

主意图决定入口和主流程，次要意图形成依赖任务或补充回答。例如：

- 主意图是“申购”，推荐是前置任务；
- 主意图是“查询订单”，解释订单流程是依赖查询结果的后置任务；
- 主意图是“转人工”，人工交接优先，但仍保留必要的已确认上下文；
- 主意图是“查资产”，风险限制可以作为关联风险提示，但不能擅自改变查询范围。

多意图场景不会简单把所有问题拼成一段回答，而是按优先级、依赖和权限形成任务图，再汇总结果。所有高风险动作都需要单独确认，不能被一句话中的其他低风险意图“带过”。


7、路由逻辑是如何设计的？Supervisor/路由节点根据什么条件决定请求分发到哪个Agent？

我们的路由采用“能力前置过滤 → 意图识别 → 任务拆分 → 依赖排序 → Agent 白名单分发”的流程。

第一步是能力前置过滤：根据当前用户的角色、权限、Agent capability、customer scope/subject scope，计算 available_agents 和 denied_agents。普通客户不能调用内部 DataAnalysisAgent、AdminAgent 或工作人员专属能力；客户只能访问自己范围内的资产、订单、工单、风险和产品信息。

第二步是识别业务意图和执行模式：

- CustomerServiceAgent：公司信息、政策、FAQ、流程、公开风险知识、客服转人工和客户只读事实解释；
- AdvisorAgent：产品推荐、投顾准备、适当性解释和建议草稿；
- RiskAgent：风险状态解释、预警查询、风险判断和处置辅助；
- DataAnalysisAgent：内部指标、批准模板、结构化分析和图表数据；
- BusinessAgent：申购、赎回、转换、转账等业务草稿、参数收集和确认请求；
- AdminAgent：后台角色、权限和配置管理。

第三步是按执行模式约束 Agent：

- bounded_react：客服知识和只读多跳检索，限制循环次数、工具次数和工具白名单；
- controlled_workflow：交易、审批、风险处置、权限修改等高约束动作，必须走权限、参数、规则、确认、状态机、幂等和审计；
- Plan + Rules：产品推荐、适当性判断等决策辅助，模型组织证据，规则服务给出最终结果。

当前代码中的核心映射包括：

- `product_recommendation` → `advisor_risk` → AdvisorAgent + RiskAgent；
- `business_operation` → `operation_risk` → BusinessAgent + RiskAgent；
- `asset_summary` → `analysis` → DataAnalysisAgent；
- `order_status`、`workorder_status`、`product_status`、政策和 FAQ → `customer_service` → CustomerServiceAgent；
- `human_handoff` → `customer_service`，并进入人工会话状态机。

第四步是执行安全检查：权限、客户范围、参数完整性、适当性、风控、数据目录和资源成本均通过后，才允许调用对应工具或领域服务。Supervisor 可以规划和汇总，但不能绕过权限直接调用内部 Agent，也不能直接写订单、资金或风险事实。

第五步是统一输出：无论最终由客服、投顾、风控、分析还是业务 Agent 返回，都通过统一 Agent 窗口展示文本、证据、澄清、推荐卡片、订单草稿卡片或人工转接状态。推荐和下单不会跳转到独立客户侧边栏；它们在同一 AgentBubble 会话中连续完成。

总结来说，路由的核心不是“模型觉得哪个 Agent 合适”，而是：

```text
用户身份与权限
→ 可用能力白名单
→ 意图与主次任务
→ 依赖和执行模式
→ 受控 Agent/Tool
→ 规则与确认
→ 审计化结果
```

这套设计同时满足业务连续性、合规控制、可解释性和后续多 Agent 扩展要求。
