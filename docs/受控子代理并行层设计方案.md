# 受控子代理并行层设计方案

> 版本：v1.0　日期：2026-08-27
> 定位：在现有"确定性编排"之上，为**可并行、可独立、只读**的领域子任务引入真正的子代理并行；**严格场景（资金/订单/风控结论/写操作）保持确定性流程**。
> 依据：`docs/PLAN.md`（受控 Fan-out-Fan-in）、`ARCHITECTURE_DATABASE_DRAFT.md`（受控多 Agent 并行）、`DECISIONS.md`（受控并行执行→聚合回答）、`ISSUES.md`（任务级拆解/受控并行/依赖串行）；业界头部公司（Anthropic/OpenAI）报告确认"部分任务可并行、关键动作保持确定性 + 人工在环"。

---

## 1. 背景与目标

### 1.1 现状：已有"任务并行"，缺"子代理并行"

当前 `CustomerTaskExecutor`（`app/services/customer_task_executor.py:113-124`）已实现**任务级并行**：把 `IntentTask` 拆成多个确定性 handler，按 `depends_on` 拓扑、用 `asyncio.gather` + `max_parallel_tasks=4` 并发执行，再 `summarize` 拼接。

**缺的是"子代理并行"**：派多个**独立的 LLM 子代理**（每个有自己的推理循环 + 工具预算 + 只读范围）并发跑，各自返回结构化结果，由 Supervisor 用确定性规则融合。当某个领域子任务需要"独立多步分析/检索/解释"时，任务并行无法表达，只能串行，吞吐和延迟有提升空间。

### 1.2 目标

1. 让**可并行、可独立、只读**的领域分析（风控分析 + 产品分析 + 客户画像、RAG 多路评测、多角度解释）能并行执行，降低总延迟。
2. 严格场景（资金、订单、风控最终结论、任何写操作）**绝不进子代理并行**，保持确定性 Service。
3. 复用现有 harness 全部安全设施：能力注册表、ReAct 预算、SubjectScope、工具白名单、审计、降级。

---

## 2. 核心原则（一条边界）

> **"部分领域可以并行，严格场景必须确定性。"**
> 判定依据：该子任务是否会**改变业务事实 / 触发写操作 / 产出高风险结论**。
> - 会 → 走确定性流程（现状），不进子代理并行。
> - 不会（只读分析/检索/解释）→ 可进受控子代理并行。

---

## 3. 并行边界矩阵

| 子任务类别 | 可并行? | 原因 / 约束 |
|---|---|---|
| 风控事实分析（读预警/流水做分析） | ✅ 可并行 | 只读；子代理只出"分析"，不出"处置结论" |
| 产品/适当性解释、推荐说明 | ✅ 可并行 | 只读；最终适当性由 `SuitabilityService` 裁决 |
| RAG 多路检索/多问题评测 | ✅ 可并行 | 只读；天然可分片 |
| 客户画像/持仓只读分析 | ✅ 可并行 | 只读 + SubjectScope 限定 |
| **订单创建/确认/冻结** | ❌ 绝不 | 写操作，走确定性 `trading_service` |
| **资金/赎回/转账** | ❌ 绝不 | 写操作 + 幂等 + 人工 |
| **风控最终结论/限制解除** | ❌ 绝不 | 高风险，走 `risk_alert` 状态机 + 人工 |
| **任何跨库/跨客户聚合写回** | ❌ 绝不 | 权限边界 |

> 边界落库：子代理并行层只暴露**只读工具**（复用 `CustomerReadTools` 只读子集 + `DataAnalysisAgent` 只读模板/指标），写工具不注册给子代理。

---

## 4. 架构位置

```text
api/customer_service.py
 → CustomerAgentExecutionService（Supervisor）
   ├─ [现状] CustomerTaskExecutor（任务级并行，确定性 handler）
   └─ [新增] SubagentExecutor（子代理级并行，只读领域分析）
          ├─ 子代理 A（风控只读分析）
          ├─ 子代理 B（产品/适当性解释）   ← 并行，asyncio.gather
          └─ 子代理 C（RAG 检索解释）
          └─ 确定性融合（Supervisor 裁决） → 聚合回答
```

- **接入点**：`CustomerAgentExecutionService.execute` 在路由后，若某 intent 命中"可并行只读分析"类型，走 `SubagentExecutor`；否则维持现有 `CustomerTaskExecutor`。
- **不替代**：子代理并行只是 `CustomerTaskExecutor` 的**并行执行模式之一**，不推翻确定性编排主体。

## 5. 组件设计

### 5.1 SubagentExecutor（新服务 `app/services/subagent_executor.py`）

职责：接收"子任务清单"→ 并行执行受控子代理 → 确定性融合结果。

```python
async def execute(subtasks: list[SubagentTask], *, user, session) -> SubagentMergeResult:
    # 1. 前置校验：每个子任务 capability/权限/scope/只读
    # 2. 并发控制：asyncio.gather + 信号量 max_concurrent（默认 2-3）
    # 3. 每个子代理：受控 ReAct（只读工具 + 预算）→ 结构化结果
    # 4. 失败处理：子代理失败 → 降级该子任务（fallback 确定性 / 标注 partial）
    # 5. 融合：按确定性规则合并（非自由拼接）
    # 6. 审计：AuditLog(subagent.*) + save_short_term
```

### 5.2 子代理协议（扩展 `app/ports/agent.py`）

沿用现有 Agent Protocol（`name` + `async run(message, context) -> AgentResult`），新增约束：

- `SubagentTask`：`{task_id, agent_name, query, tool_whitelist, budget, scope}`。
- `SubagentResult`：`{task_id, status, summary, data, evidence, confidence, requires_confirmation}`——**结构化**，不是自由文本。
- 子代理上下文注入：user 身份、RBAC 权限、`SubjectScopeService.authorized_subject_ids`、当前 customer_id。

### 5.3 并发控制

- `max_concurrent`（默认 2-3，配置可调）用 `asyncio.Semaphore` 限制；避免无限并发打爆 Qwen API 和连接池。
- 每个子代理**独立超时**（`asyncio.wait_for`，默认 8s）+ 全局超时。
- 复用 `llm_intent_fallback_max_concurrency=4` 的并发信号量思路。

### 5.4 子代理预算（复用 ReAct 预算）

- `MAX_REACT_ITERATIONS`、`MAX_REACT_TOOL_CALLS`（现有 3/3）。
- Token/时间预算：单子代理超时 + 全局超时。
- **只读工具白名单**：只注册 `CustomerReadTools` 的只读子集 + `search_customer_knowledge` + 数据分析只读模板/指标。

### 5.5 融合（Supervisor 裁决，非自由拼接）

- 每个子代理返回结构化结果 + confidence。
- 融合规则：**确定性**——按任务类型选择合并策略（并集/最相关/冲突裁决）。
- 冲突处理：若多个子代理结论冲突，不以"多数票"直接定论；标注冲突、交人工/确定性规则裁决（呼应"高净值客户多 Agent 冲突消解"）。
- **业务事实结论一律以确定性 Service 为准**，子代理只贡献"解释/分析"。

### 5.6 审计与可观测

- `AuditLog(action="subagent.ran")`，detail 记录：子代理名、task_id、tool_call_count、`private_reasoning_logged: False`、只读标记。
- 每个子代理结果写 `CustomerMemoryEvent`（若涉记忆）或短期记忆。
- `save_short_term` 存子代理中间状态，支持追问/恢复。

### 5.7 降级（失败不中断整体）

- 子代理超时/失败 → 该子任务标 `partial` / `failed`，其余子代理结果保留。
- 若某子代理失败影响整体回答 → 降级为"确定性兜底"或"转人工"，**不让失败子代理拖垮整个请求**（复用 `CustomerRagHandoffService` 低置信转人工）。

## 6. 安全设计（每条都要落）

1. **只读强制**：子代理工具层只暴露只读工具；写操作工具不注册。
2. **权限**：每个子代理执行前校验 RBAC 权限码 + capability（复用 `agent_capabilities.py`）。
3. **数据范围**：每个子代理注入 `authorized_subject_ids`，查询硬编码 customer_id/scope。
4. **隔离**：子代理之间不共享私有推理链；只共享结构化结果。
5. **预算**：迭代/工具/超时三重上限。
6. **幂等/审计**：子代理只读不写，天然幂等；全程 AuditLog。
7. **不覆盖业务事实**：子代理结论不得写回余额/持仓/风评/订单。

---

## 7. 数据模型（可选，P2 落地）

长时/可恢复的子代理任务建议新增两表（沿用 UUID + JSONB 约定）：

- **`subagent_task`**：`id, session_id, agent_name, query, tool_whitelist_json, budget_json, scope_json, status(queued/running/success/failed/partial), started_at, finished_at`。
- **`subagent_result`**：`task_id, status, summary, data_json, evidence_json, confidence, error_message, created_at`。

> 目的：子代理并行结果可审计、可恢复（对接 P4 断点续跑），不依赖会话临时态。

## 8. 与现有 harness 的一致性（复用什么）

| 现有能力 | 复用到子代理并行 |
|---|---|
| `agent_capabilities.py` 能力注册表 | 子代理可用性前置过滤 |
| `customer_task_executor.py` ReAct 预算 | 子代理迭代/工具上限 |
| `subject_scope.py` | 子代理数据范围注入 |
| `customer_tools.py` 只读白名单 | 子代理只读工具集 |
| `data_analysis_agent.py` 只读模板/指标 | 分析型子代理 |
| `AuditLog` | 子代理全链路审计 |
| `customer_rag_handoff.py` 低置信转人工 | 子代理失败降级 |

## 9. 落地步骤

**P0（受控并行最小闭环）**
1. 定义 `SubagentTask`/`SubagentResult` Schema 与 Agent 协议扩展。
2. `SubagentExecutor` + 并发信号量 + 超时 + 审计骨架。
3. 接入 1-2 个只读分析场景（如"风控只读分析 + 产品解释"并行）。
4. 单元 + HTTP 回归（并发、超时、失败降级、权限）。

**P1（边界与评测）**
5. 并行边界矩阵固化为配置/校验（哪些 intent 可并行）。
6. 结构化融合规则 + 冲突裁决。
7. 评测集（可并行 vs 串行延迟对比、准确性不劣化）。

**P2（可恢复与扩展）**
8. `subagent_task/result` 落库 + 对接断点续跑。
9. 更多只读领域接入；监控指标（P95、子代理失败率、并发水位）。

---

## 10. 验收标准

- 可并行场景：**总延迟显著低于串行**（有压测/评测对比数据）。
- **越权/写操作 = 0**：任何资金/订单/风控结论不经子代理并行。
- 子代理失败不拖垮整体（降级路径覆盖）。
- 每个子代理结果可审计（AuditLog）、可溯源、可恢复。
- 严格场景确定性流程**行为不变**（回归测试通过）。

## 12. 与数据飞轮的协同（可选增强）

> 子代理并行负责"更快的分析"，数据飞轮（`Agent & RAG 数据飞轮`）负责"更准的分析"，两者可叠加：
- 并行子代理产生的 Bad Case → 流入飞轮的**信号（评测）**齿轮；
- 归因结果 → 更新 **Skill/记忆/配置库**（改运行时，不改代码）；
- 人机**控制**齿轮审核后再灰度/回滚，避免并行层引入的低质结果污染。

落地顺序建议：**先做子代理并行 P0（提效）+ 飞轮 Phase 0（评测可信），再考虑打通**——因为"评测可信度 > 系统复杂度"，评测信号不准时，并行/自动修复越快错得越快。
