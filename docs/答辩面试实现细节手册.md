## 0. 使用说明与总原则

1. **先记住全项目的"一句话定位"**：这是一个**模块化单体**的财富管理 Mock/MVP 系统，核心设计是——**"确定性后端规则决定业务结果（资产、权限、风控、交易），Agent 只负责理解、解释、建议"**。AI 永远不直接改钱、不绕过权限、不决定风险等级。
2. **答辩最大的加分点 = 主动讲清"哪些做了、哪些只是规划"**。评委/面试官最反感夸大；你能诚实划清"已实现 vs 规划"的边界，反而最有说服力。本手册第 7 章是自检速查表。
3. **技术栈表面不会被逐字抠，但"你怎么实现的"一定会被追问**。所以重点是理解每条能力背后的真实代码链路，而不是背技术名词。

### 全局架构速览（一句话版）

```
Vue3/TS 前端 → FastAPI(api层,只做鉴权/校验/调Service/统一响应)
  → Service 业务层(规则/事务/权限/幂等)
    → Port(接口抽象) → Repository + Infrastructure Adapter
      → PostgreSQL(+pgvector) / MySQL(迁移验证) / Redis / Milvus(可切换) / Qwen
异步侧：业务与 Outbox 同事务 → outbox_worker 搬运到 Redis Streams → 各领域 worker 消费
```

## 1. 多 Agent 编排 + 安全边界

**核心文件**：`app/services/customer_agent_execution.py`、`customer_intent.py`、`customer_task_executor.py`、`customer_tools.py`、`customer_query_router.py`、`intent_policy_resolver.py`、`llm_intent_fallback.py`、`agent_capabilities.py`、`data_analysis_agent.py`

### 1.1 真实链路（不走 LangGraph！）

> ⚠️ **最重要的诚实点**：`app/agents/graph.py` 的 docstring 自己写明是 *"P0 LangGraph wiring placeholder"*，`supervisor_node` 只做 `iteration_count+1`，`build()` 只有 START→supervisor→END，`max_iterations/max_tool_calls` 参数在节点里从没用过。真实执行是**确定性管线**。

真实链路：
```
api/customer_service.py
 → CustomerAgentExecutionService.execute(customer_agent_execution.py:125)
   → 短期记忆加载(handoff/clarification_count/pending_intent_plan)
   → 人工接管门(有客服会话则注入 active_handoff)
   → 追问上下文合并(combined_query = original_query + 本次)
   → CustomerIntentPlanner.plan 意图规划(关键词正则 _patterns)
   → LLM 影子/回退层(默认关闭)
   → route_for_plan 优先级路由
   → 澄清状态机(澄清 2 次强制转人工)
   → CustomerTaskExecutor.execute(多任务 DAG 并行)
   → summarize 汇总 + 二次转人工判定
   → bounded_react 审计 + save_short_term
```

### 1.2 能力注册表 AgentCapabilityRegistry（`agent_capabilities.py`）

- `AgentCapability` 是 `@dataclass(frozen=True)`：`code / required_roles / required_permissions_any / internal_only`。
- 注册表是**不可变元组**，共 9 项：4 个客户可见（CustomerServiceAgent、CustomerRecommendationCapability、CustomerTradeDraftCapability、CustomerRiskExplanationCapability）+ 5 个 `internal_only=True`（DataAnalysisAgent、AdvisorAgent、RiskAgent、BusinessAgent、AdminAgent）。
- `available_for(user)` **三连闸**：① `is_super_admin` 全放行；② `internal_only` 且用户是 customer → 跳过；③ `required_roles` 交集 / `required_permissions_any` 任一命中。
- 位置：`api/customer_service.py:191-193` 的 `execute_unified_agent` 做**路由前门**（决定 DataAnalysisAgent 是否可用）。运行时 `route_for_plan` 不再查注册表——注册表管"能不能进"，意图规划管"进后走哪条路"，两层职责分离。

### 1.3 安全边界

- **ReAct 预算**：`CustomerTaskExecutor` 里 `MAX_REACT_ITERATIONS=3`、`MAX_REACT_TOOL_CALLS=3`（双重上限，任一先到即停）；首轮 low_confidence 只允许**一次**查询改写。
- **工具名白名单**：`CustomerReadTools.allowed` 固定 8 个名字，白名单外直接 `tool_not_allowed`；工具门面**从不直接碰 repository**。
- **customer_id 作用域**：`CustomerQueryRouter` 每个查询都硬编码当前 customer_id 到 where 层（`WorkOrder.customer_id==`、`Order.user_id==`、`Account.user_id==`、`RiskAlert.customer_id==`、`CustomerAssetSnapshot.user_id==`、`CustomerHolding.user_id==`）。
- **交易意图永不执行**：`business_operation` 恒返回 `needs_confirmation` + `executed=False` + 页面深链。
- **LLM 防御性加固**：`intent_policy_resolver.py` 单向合并（规则置信度≥0.9 以规则为骨架；规则 T0 禁止模型把模糊查询升级为交易模板；模型永远删不掉规则的缺失字段；T3/T4 强制 `explicit_confirmation=False` 并注入 `must_not_submit_without_verified_customer_confirmation`）。
- **多意图**：`CustomerIntentPlanner` 一次产出多个 `IntentTask`，带显式 `depends_on`；`CustomerTaskExecutor` 拓扑就绪分批 `asyncio.gather`（max_parallel_tasks=4），依赖死锁标 `blocked`。

### 1.4 面试高频问答

**Q1：你们的"多 Agent 编排"在哪？graph.py 是不是没实现？**
答：P0 的真实编排不依赖 LangGraph。`graph.py` 自己标注是 placeholder，真实链路是确定性管线（`CustomerAgentExecutionService → CustomerIntentPlanner → CustomerTaskExecutor → CustomerReadTools → CustomerQueryRouter`）。这是刻意的分层：P0 用可审计的确定性代码交付价值，`app/ports/agent.py` 的 Agent Protocol 和 `AgentOrchestrator` 是为 P1/P2/P3 上真实 Supervisor 图预留的端口。

**Q2：多意图怎么拆？有依赖怎么办？会并行错乱吗？**
答：规划器一次生成多个 `IntentTask`，带显式 `depends_on`（如"查订单+查流程"时 workflow 依赖 order_status；"推荐+申购"时 business_operation 依赖 product_recommendation）。执行器是拓扑调度：每轮取依赖全部完成的 ready 任务，按 max_parallel_tasks=4 用 asyncio.gather 并行；依赖死锁把剩余任务标 blocked 防挂死。

**Q3：LLM 在意图识别里起什么作用？怎么防模型越权/幻觉变执行？**
答：默认纯规则，LLM 回退默认关闭（settings 两个开关默认 False）。开启后是"影子/回退"双模式：模型输出经 pydantic 校验 + 强制 source=llm_fallback，产出交易/草稿模板就强制无确认 + 注入 must_not_submit；`IntentPolicyResolver` 单向合并让规则永远压过模型；`_apply_structured_intent` 只接受 allowlist（默认 T1/T2/T7），交易/草稿模板永远进不了 plan。一句话：模型输出只是"建议解释"，不是执行授权。

**Q4：工具调用怎么防止越权读别人数据？**
答：三层。①名称白名单（8 个工具名，外则 tool_not_allowed）；②数据作用域（CustomerQueryRouter 每个查询硬编码 customer_id where 条件）+ route_mismatch 校验；③预算与只读（ReAct 3/3 上限、交易意图不调工具只返回确认+深链、executed 恒为 False）。

**Q5：DataAnalysisAgent 的 SQL 安全怎么做的？支持自由 SQL 吗？**
答：明确不支持自由 SQL。指标模式（5 个批准指标，SQL 代码写死）；模板模式（approved+active+角色匹配 + `validate_readonly_template` + 参数 schema 绑定 + `validate_catalog_allowlist` 双重白名单 + 外层 LIMIT 兜底 + 失败先 rollback）。详见第 4 章。

**Q6：规则意图和模型意图冲突谁说了算？**
答：规则说了算。`IntentPolicyResolver` 单向合并：规则置信度≥0.9 以规则为骨架；规则 T0 时禁止模型升级为交易模板；模型不能删规则字段；模型永远不能声称客户已确认。另有 route_mismatch 校验防"工具要的数据和意图对不上"。

## 2. 自然语言下单闭环 + 交易状态机 + 幂等

**核心文件**：`app/services/natural_language_order_draft.py`、`trading_service.py`、`suitability_service.py`、`app/api/trading.py`、`app/models/trading.py`、`app/repositories/trading.py`

### 2.1 完整闭环（四步，不是两步）

```
① NL草稿创建(不建单/不冻结) → ② 草稿确认(token,幂等建单,仍不冻结)
 → ③ 订单客户确认(冻结资金) → ④ 员工复核(执行/拒绝)
```

> ⚠️ **关键事实**：**草稿确认 ≠ 资金冻结**。`draft.confirm()` 只是用 `create_order()` 生成一条 `status=pending_confirmation` 的订单；真正扣可用余额/加冻结额发生在标准的 `confirm_order()`。

**① 草稿创建** `POST /trading/order-drafts/natural-language`（`api/trading.py:51-63`）
- 只允许 customer 角色；`UNSUPPORTED_MARKERS`（赎回/卖出/转换/转出）→ needs_clarification（MVP 仅支持申购）。
- `parse_purchase_intent()`：引号内产品名优先；金额正则 `([0-9]+(?:\.[0-9]+)?)(万|元)`，`万`×10000，用 Decimal 保精度。
- **系统从不猜测缺失参数**：缺产品/金额 → needs_clarification + missing_fields，提示"关键交易参数必须由客户明确提供，系统不会猜测"。
- 产品匹配（active + 去空格精确匹配）、金额≥minimum_amount、账户/余额、`suitability_service.recommend()` 适当性预检，全过才落草稿。
- **草稿持久化**：`confirmation_token = secrets.token_urlsafe(32)`，`expires_at = now+15min`，`version=1`；`input_fingerprint = sha256(...)`；`precheck_snapshot_json` 把预检结果整体快照留痕；**DB 只存 `confirmation_token_hash=sha256(token)`**；写 `AuditLog(action="create_draft")`。

**② 草稿确认** `POST /order-drafts/{id}/confirm`（`natural_language_order_draft.py:222-273`）
1. `SELECT...FOR UPDATE` 行锁（防并发双击）；
2. 幂等短路：`draft.order_id` 已存在 → 返回已建订单；
3. 状态守卫（必须 awaiting_user_confirmation）；
4. 过期校验（置 expired）；
5. 令牌校验：`secrets.compare_digest(sha256(token), hash)`（常量时间比较）；
6. **确认时重跑全部确定性控制（TOCTOU 防护）**；
7. 幂等键 = `payload.idempotency_key or f"nl-draft:{draft.id}:v{draft.version}"`；
8. `create_order(confirmation_mode="nl_draft")`；
9. 回写 draft.order_id / confirmed_order_created / 审计。

**③ 订单客户确认（冻结）** `confirm_order()`：订单行 FOR UPDATE → 状态校验 → 余额检查 → 风险测评 ensure_default → 客户类型门槛 + 风险等级硬校验（C1..C5=1..5，actual<required 拒绝）→ **available -= amount; frozen += amount** → pending_review。

**④ 员工复核** `review_order()`：风控闸门 `_blocking_risk_alert` → 解冻/扣款 → executing → 持仓 upsert → 幂等建 Trade → executed → 资产快照 → 幂等建 MoneyFlow → 交易后风控。

### 2.2 交易状态机（唯一权威在 `transition()`，`trading_service.py:67-83`）

```
pending_confirmation → {pending_review, cancelled}
pending_review       → {executing, rejected, cancelled}
executing            → {executed}
executed/rejected/cancelled → 终态
```

- 同状态/非法迁移抛 `TradingError`；API 层映射 409 `ORDER_STATE_CONFLICT`。
- **为什么 pending_confirmation 不能直达 executing**：资金冻结在 confirm_order，执行前放行权在员工（还有风控闸门）——"客户确认 + 员工复核"是硬性两步。
- **order_status_history**：建单写首条 + 每次 transition 追加一条 (from,to,operator,note)，按 created_at 升序返回，可审计。
- 冻结/解冻/持仓更新全程同一个 AsyncSession 事务，任一步抛错整单回滚；账户行 FOR UPDATE；金额用 Numeric(18,2)+Decimal 防浮点误差。

### 2.3 适当性 SuitabilityService（`suitability_service.py`）

- 等级数值化 `LEVEL={C1:1..C5:5}`、`RISK={R1:1..R5:5}`。
- 每产品算三门槛：`required_level = max(product.risk_level, rules.minimum_risk_level...)`；`required_investable_asset = max(minimum_amount, rules.minimum_investable_asset...)`；`required_investor_types`。
- 否决逻辑（任一不满足 matched=False）：风险等级不够 / 客户类型不符 / 可投资资产不够。
- `restricted` 只加 reason 和 warning，不直接置 matched=False；提交拦截在草稿/确认的账户级检查。
- **与下单两处衔接**：草稿预检用 recommend()；订单确认终检再独立做一次等级数值比较（两套实现互为兜底）。

### 2.4 幂等（订单用数据库，不是 Redis）

- ⚠️ 诚实点：`app/common/idempotency/store.py` 有 Redis 版 `IdempotencyStore`（`idempotency:{scope}:{sha256}`，TTL 86400s），**但订单链路没有调用它**。订单用数据库方案。
- **DB 方案**：`Order.idempotency_key` 列 + `get_by_idempotency(user_id,key)` 预查（命中即返回旧单）+ 唯一部分索引 `ux_orders_user_idempotency_key(user_id, idempotency_key) WHERE idempotency_key IS NOT NULL` 兜底。并发双写后者抛 IntegrityError → 映射 409 `IDEMPOTENCY_CONFLICT`。
- 重复 confirm 防护：FOR UPDATE + draft.order_id 短路 + 确定性幂等键，四层。
- 执行阶段 Trade/MoneyFlow 均"先查后插"防重入。

### 2.5 面试高频问答

**Q1：AI 为什么不能直接下单？**
答：`NaturalLanguageOrderDraftService` 类注释写明 "never creates an Order, freezes funds, or performs a state transition"，响应模型固定 `confirmation_required=True, executed=False`。①AI 解析有不确定性，代码用"缺字段只澄清、绝不猜测"把不确定性挡在提案层；②草稿与确认之间隔 15 分钟一次性令牌，客户确认的是快照内容；③确认时重跑校验防 TOCTOU；④即使客户确认，订单仍停 pending_review 等员工复核 + 风控闸门。所以 AI 只生成提案，资金动作永远由显式确认 + 人工复核触发。

**Q2：确认令牌怎么生成/校验/为什么不存明文？**
答：`secrets.token_urlsafe(32)`，15 分钟有效，DB 只存 sha256，明文只返回一次；校验用 `secrets.compare_digest` 常量时间比较防时序攻击；草稿按 customer_id 归属，令牌无法跨用户。

**Q3：用户连点两次确认，会建两个订单吗？**
答：不会，四层防护：FOR UPDATE 行锁、draft.order_id 幂等短路、确定性幂等键、唯一部分索引兜底（后者抛 IntegrityError→409）。

**Q4：幂等用 Redis 还是数据库？**
答：订单模块用数据库幂等。Redis 组件是通用件但交易链路未接线。防竞态关键是唯一索引保证"只成功一次"，预查只是优化路径。

**Q5：状态机有哪些状态？为什么不能直接到 executing？**
答：pending_confirmation→pending_review→executing→executed，另有 cancelled/rejected 终态。不能直达 executing 因为要过"客户确认（冻结）+ 员工复核（含风控闸门）"两步人工。

**Q6：冻结/持仓更新时序怎么保证一致？**
答：同一个 AsyncSession 事务、API 层统一 commit、账户行 FOR UPDATE、金额 Decimal。执行顺序固定：扣冻结→executing→持仓 upsert→幂等建 Trade→executed→资产快照→MoneyFlow→风控。

**Q7（加分）：草稿确认和订单确认区别？**
答：草稿确认只做令牌校验+重跑预检+幂等建单，不冻结；订单确认才冻结并推入 pending_review。两段确认间允许客户反悔（草稿过期或取消订单）。

## 3. 认证授权 RBAC + 权限版本化缓存 + Subject Scope

**核心文件**：`app/services/auth_service.py`、`auth_seed.py`、`permission_scoped_cache.py`、`subject_scope.py`、`app/common/security/auth.py`、`app/models/auth.py`、`app/api/admin.py`

### 3.1 认证

- **Argon2 哈希**：`auth_service.py:17-24`，模块级 `PasswordHasher`；校验时捕获 InvalidHashError/VerificationError 统一返回 False（防枚举）。
- **注册**：员工必须带 company_code 且等于 `settings.employee_registration_code`；customer → customer 角色，employee → employee_pending（零权限）。
- **登录**：用户名 + active + 密码三重校验；refresh token = `secrets.token_urlsafe(64)`，**DB 只存 sha256**。
- **JWT**：HS256，payload 含 sub/username/roles/is_super_admin/type/exp。
- **校验**：`current_user`（`common/security/auth.py:12-21`）**每次请求都从数据库重载用户+角色+权限**并校验 active——JWT 只是"身份+过期"的无状态凭证，权限以数据库当前值为准。
- **刷新轮换**：刷新时旧行置 revoked_at 再签发新 token——重放已轮换旧 token 会 401，天然支持重用检测。

### 3.2 RBAC 模型

- 五表：users / roles / permissions / user_roles / role_permissions（`models/auth.py`）。
- 权限矩阵 = `docs/RBAC_PERMISSION_MATRIX.md`（规范）+ `auth_seed.py` 的 `PERMISSIONS`(25码)/`ROLE_PERMISSIONS`(实现)。
- 10 个角色：customer/customer_service/customer_manager/advisor/product_manager/risk_manager/operations/auditor/super_admin/employee_pending。
- 鉴权依赖注入：`require_permission` / `require_staff_permission`（额外拒 customer）/ `require_advisor_permission`（必须 advisor 角色 + 权限）。
- 管理端接口：改角色/改权限 → 写审计 + **逐个 bump_permission_context_version**；super_admin 角色权限固定不可改；不能给自己移除 super_admin。

### 3.3 Subject Scope（"投顾/客户经理只能访问被授权客户"）

- `CustomerAdvisorAuthorization` 表（`models/auth.py:57-72`）：customer_id/advisor_id + 业务约束（allowed_actions/product_scope/max_single_amount/max_daily_amount/risk_level_ceiling）+ 有效期。
- `SubjectScopeService.authorized_subject_ids`（`subject_scope.py:13-31`）：super_admin 返回空集=无限制；advisor/customer_manager 查授权表取 customer_id 集合。
- **防越权根本机制**：`DataAnalysisAgent.bind_template_parameters`（`data_analysis_agent.py:116-151`）把 SQL 的 subject 参数**服务端改写为授权闭包**——客户传什么 id 都绕不过，因为最终查询参数是服务端算的。
- 授权变更经 Outbox 事件（`authorization.subject_scope_invalidate`）事务内持久化，可重试。

### 3.4 权限版本化缓存（`permission_scoped_cache.py`）

- Key = `wm:{namespace}:pc-{指纹}:sc-{范围指纹}`；指纹 = 规范化 JSON + SHA-256 取前 24 位。
- 版本键 `wm:permission-context-version:{user_id}` / `wm:subject-scope-version:{user_id}`，角色/权限/授权变更时 INCR 递增 → 指纹变 → 旧 key 逻辑不可达靠 TTL 回收（不需要扫描删除 key）。
- **设计意图**：①缓存是纯优化，失败返回 None 走实时查询，授权永不依赖缓存；②双重保险（指纹含实时角色码是安全底线，版本号是急切失效）；③INCR 原子无竞态；④失效粒度精确到用户。

### 3.5 面试高频问答

**Q1：JWT 里已有 roles，为什么每次请求还要查库？**
答：JWT 只承担身份+过期，授权永远以数据库为唯一事实源。每次请求重载用户/角色/权限并校验 active，使角色/权限/禁用变更即时生效、撤销立即生效。代价是多一次查询，但权限表小且有索引，收益远大于成本。

**Q2：权限改了缓存怎么失效？为什么用版本号不删 key？**
答：key 含指纹（角色码+权限码+data_scope_version），变更时对受影响用户 INCR 版本号→指纹变→旧 key 逻辑不可达靠 TTL 回收。选版本号因为 O(1)、INCR 原子无竞态、粒度精确；且即使 INCR 失败指纹仍含实时角色码，安全不依赖缓存。

**Q3：怎么保证投顾只能看被授权客户、无法越权？**
答：三层。①路由依赖注入（角色+权限门）；②SubjectScopeService 从授权表算 authorized_subject_ids；③最关键——数据分析时把 SQL 的 subject 参数服务端改写为授权集合，请求里出现的越权客户标识直接被拒。

**Q4：Redis 挂了系统还安全吗？**
答：能。缓存是纯优化，get 失败返回 None 走实时查询、set 失败返回 False，授权检查全部来自数据库实时计算。Redis 故障的代价只是性能下降，不改变任何授权结果。

**Q5：Refresh Token 怎么防重用/泄露？**
答：只存哈希；每次刷新必轮换（旧行 revoked_at）；可撤销；30 天过期缩小暴露窗口。

**Q6：员工能注册成高权限角色吗？**
答：不能。注册只分配 customer 或 employee_pending；员工必须提供注册码，且默认零权限；正式角色只能由管理员分配（要求 admin:write + ensure_admin 双通道，且禁止给自己移除 super_admin）。

## 4. RAG 知识库 + 受控 NL2SQL + 数据目录

**核心文件**：`app/services/knowledge_ingestion.py`、`knowledge_retrieval.py`、`customer_rag_service.py`、`customer_rag_answer.py`、`app/repositories/knowledge.py`、`app/infrastructure/vector_store/*`、`app/services/nl2sql_policy.py`、`data_analysis_agent.py`、`data_catalog_service.py`、`data_catalog_embedding.py`

### 4.1 RAG 完整链路（真实闭环）

```
上传 → outbox 事件 knowledge.document_created → outbox_worker → stream:wealth:ingestion
 → knowledge_worker 消费 → ingest_document
 → 解析(docx/plain_text) → 切块(size=1000, overlap=120, step=880)
 → Qwen embed(1024维, 逐条, 重试3次, batch=4)
 → 存 pgvector VECTOR(1024)
 → 检索 search_hybrid(PG全文 ts_rank_cd + cosine + RRF 融合, top_k=5)
 → 置信度 min_score=0.0001(低→low_confidence→转人工)
 → 生成(只按[引用N]回答, temperature=0.1)
```

- **Embedding 模型名要如实**：代码默认 `qwen3.7-text-embedding`（`settings.py:33`），`.env.example` 声明 `text-embedding-v4`，实际 `.env` 未覆盖 → 运行态为默认值。两者都是 Qwen/DashScope 系，**1024 维硬约束**（维度不符直接抛 ValueError）。
- **混合检索**：`search_hybrid`（`knowledge.py:136-199`）——文本腿 PG FTS + 向量腿 cosine，各取 max(top_k*4,20) 候选，RRF `1/(60+rank)` 融合取 top_k。**不是独立 BM25**，文本腿就是 PG 内置 FTS，中文语义靠向量腿。
- **为什么 min_score=0.0001**：分数是 RRF 融合值（单腿最高约 0.016），不是余弦相似度；0.0001 是滤掉"两条腿都没召回"的 0 分项。真正拒答条件是没有任何≥阈值的引用。
- **降级**：embedding 失败自动降级 ILIKE 文本检索，`retrieval_mode` 在 API 响应里如实标注（`hybrid-ftS-pgvector` / `text-ilike-fallback`）。
- **Scope 隔离**：`KnowledgeScope(knowledge_base_ids/categories/permission_levels)`，空元组=通配；`public_customer` / `internal_advisor` 两档；下推成 SQL 行级 IN 过滤 + 四重激活过滤。

### 4.2 版本化/增量（真实 vs 规划）

- ✅ **真实**：版本递增（version_no+1）、`activate_version` 原子切换（旧版本标 superseded、文档 current_version_id 指向新版）、chunk 级 embedding 复用（按 content_hash 命中复用旧向量，只对变化 chunk 调 embedding，返回 reused/embedded 计数）。
- ⚠️ **边界**：省的是最贵的 embedding 调用，但**仍物理写入全套 chunk 行**（版本必须完整可回溯）。文档级"内容没变跳过整篇"去重**未实现**——主动讲这个更可信。

### 4.3 VectorStore Port/Adapter

- `VectorStore` Protocol（upsert/search/delete）→ `PgVectorStore` + `MilvusVectorStore` 双实现，`factory` 按 `VECTOR_STORE_BACKEND` 切换。
- ⚠️ **诚实点**：当前在线混合检索直接走 pgvector SQL（因为 RRF+全文+权限过滤需同库 JOIN）；Milvus adapter 是可配置替代后端，不是当前生产路径。

### 4.4 受控 NL2SQL（三重校验真实存在）

`DataAnalysisAgent.analyze_template_attempt`（`data_analysis_agent.py:259-301`）：
1. **模板白名单**：is_active + is_approved（人工审核过）+ 角色匹配 + `validate_readonly_template`（SELECT/WITH 开头、禁 `;`/注释/DDL/DML/pg_sleep 等、长度≤20000）。
2. **参数契约**（`bind_template_parameters`）：数量≤12、字符串≤256、整数|值|≤1000000、limit 1..100、日期范围≤366 天；`authorized_scope_only` 参数只接受授权 subject 集合内 ID。
3. **目录引用范围**（`validate_catalog_allowlist`）：正则提取 SQL 引用表/列（剥参数+字符串字面量）→ 要求 ⊆ 模板声明 ⊆ 活跃可查询目录（且非敏感列），角色策略与表策略相交。
- 执行形态：SQLAlchemy 绑定参数（无字符串拼接）+ 外层 `LIMIT :__result_limit` 双重限行 + `fetchmany(100)` + 失败先 rollback。
- **指标通道**：5 个批准指标，SQL 代码写死，每指标独立权限位，客户角色直接拒绝。
- ⚠️ **关键护栏**：`data_catalog_service.py:188` 硬编码 `"nl2sql_ready": False` + 护栏声明——"目录召回 + 模板执行是现状；模型自由生成 SQL 被明确关闭，待 AST 校验/行级范围/只读执行/审计四件套就绪才放开"。
- **数据目录**：domain/table/column/relation/example/revision 六表，表/列/示例带 embedding(VECTOR(1024))，检索文本+向量混合 + 角色 JSONB contains 过滤 + retrieval_mode 可观测。

### 4.5 面试高频问答

**Q1：检索分数这么低，置信度判断是不是形同虚设？**
答：不是。分数是 RRF 融合值不是余弦相似度，不能用 0.5/0.7 阈值；0.0001 滤掉的是两条腿都没召回的 0 分项，真正拒答条件是没有任何≥阈值的引用，此时转人工建工单。检索前 embedding 失败还会显式降级，形成完整兜底。

**Q2：混合检索怎么做？**
答：文本腿 PG 全文 ts_rank_cd，向量腿 pgvector cosine，各取候选后 RRF(1/(60+rank)) 融合取 top_k。同一 SQL 里 JOIN 文档/版本表做权限+激活版本过滤。没有独立 BM25，中文语义靠向量腿。

**Q3：增量更新是真实的吗？**
答：真实的但讲清边界：版本递增 + activate_version 原子切换 + chunk 级 embedding 复用（省最贵的 API 调用）；但新版本仍物理写全套 chunk 行。文档级"内容没变跳过"未实现。

**Q4：pgvector 和 Milvus 怎么共存？为什么主要用 pgvector？**
答：统一 VectorStore Protocol，factory 按环境变量切换。pgvector 在线做混合检索（需同库 JOIN 全文+权限），Milvus 是可配置替代后端，不是当前生产路径。

**Q5：NL2SQL 怎么防注入、保证只读？**
答：四层——入口只收自然语言（直接 SELECT 都拒）、模板白名单+只读结构校验、目录引用范围双重白名单、SQLAlchemy 绑定参数+外层 LIMIT+失败 rollback。

**Q6：数据目录怎么为自然语言分析服务？权限怎么隔离？**
答：把表/列/示例/关系元数据 embedding 化，文本+向量混合召回；权限在数据层用 allowed_roles_json JSONB contains 过滤，域/表/列/示例四级各有权限；检索结果附 sql_template 喂给 DataAnalysisAgent 做三重校验；且不放开自由 SQL（nl2sql_ready=False）。

## 5. 分层记忆 + 异步 Outbox/Redis Streams/Worker

**核心文件**：`app/services/memory_service.py`、`app/models/memory.py`、`app/services/task_service.py`、`notification_service.py`、`app/models/outbox.py`、`workers/*`

### 5.1 记忆实现现状（⚠️ 区分已实现 vs 规划）

- **短期（Redis）**：key=`customer:memory:short:{customer_id}:{conversation_id}`，TTL 30 分钟，存澄清上下文/待执行计划/转人工状态。**已真实接入 Agent 链路**。
- **长期（PG）**：`CustomerMemory`（记忆卡片，部分唯一索引保证同 key 只有一条 active）+ `CustomerMemoryEvent`（事件审计），单事务 upsert。**表+服务已实现，但无任何调用方——Agent 链路零接入**。
- **L0-L3 分层**：L0 原始流水 ✅ 已实现（会话/消息/审计）；L1 记忆卡片 ✅ 表+服务已实现（但"版本化卡片"是规划，当前是覆盖更新）；L2/L3/Gen3 ❌ 纯规划。
- ⚠️ **答辩要点**：记忆三件套（短期读写、长期 upsert、事件审计）已实现；Agent 只接了短期；长期与 L2/L3/共享记忆是明确的规划项（有文档化分阶段决策）。

### 5.2 Outbox 模式

- 表：`outbox_event`（event_type/aggregate/payload_json/status: pending|published|dead/attempt/error）。
- **同事务写入**：5 个产出方（task/notification/advisor_authorization/knowledge/data_catalog）业务+outbox 一起 commit，保证"业务成功⇒事件必落库"。
- **消费**：`outbox_worker` 用 `SELECT...FOR UPDATE SKIP_LOCKED` 认领（多实例并发安全），attempt+1 落库 → 发布到 Redis Stream（按 event_type 前缀路由）→ 成功标 published。
- **至少一次**：publish 与 mark_published 是两个事务，崩溃会重复投递 → 下游幂等消费（先查后插 + 唯一索引兜底）。
- **重试/死信**：attempt ≥ max_attempts(3) → dead；dead 可在 `/admin/outbox-events` 人工 retry；任务终态发到 `stream:wealth:dead-letter`。

### 5.3 Redis Streams（真实消费组）

`app/tasks/streams.py`：`XGROUP CREATE` 建组、`XREADGROUP ... BLOCK 5000` 阻塞消费、`XACK`、`XPENDING_RANGE + XCLAIM(min_idle=30000)` 崩溃恢复、`MAXLEN ~10000`。
- **只有 outbox_worker 是 DB 轮询**，其余 worker 全走 Redis Streams 消费组。

### 5.4 Worker 体系

| Worker | 模式 | 职责 |
|---|---|---|
| runner(tasks) | 流 | 通用任务执行器（注意：`TaskExecutor.execute` 目前是占位，不按 task_type 分发）|
| notification | 流 | 客服通知幂等落库 |
| knowledge | 流 | 知识入库（解析/切块/embedding/activate_version）|
| authorization | 流 | 授权变更 → bump subject scope 版本 |
| aml_scheduler | 定时 | 每日 AML 扫描（UTC 时间匹配 + slot 去重）|
| customer_service_timeout | 定时 | 客服会话超时（心跳/等待超时）|

- `AsyncTask` 状态机：queued → running → success/failed/dead；每个 worker 独立进程 `asyncio.run(main())`。

### 5.5 面试高频问答

**Q1：记忆体系分几层？哪些真落地了？**
答：物理两层——Redis 短期会话记忆（已接入 Agent）+ PG 长期记忆（CustomerMemory 表+服务已实现，但链路未接）。方法论 L0-L3 里 L0/L1 已落地，L2/L3/Gen3 是明确规划。

**Q2：短期和长期各解决什么？为什么不能只用一种？**
答：短期解决同会话上下文连续性（澄清补参/次数控制/待执行计划/转人工门控），要快、随会话清理，用 Redis+TTL；长期解决跨会话客户事实留档（只写客户确认参数/偏好/非敏感事实，带审计），是受控 PG 表。一个管"这轮聊到哪"，一个管"这客户已知什么"。

**Q3：Outbox 怎么保证"业务成功事件必达、且不丢"？**
答：同事务写入 + 可靠的发布者（FOR UPDATE SKIP_LOCKED 认领 + attempt 落库 + 成功标 published）+ 至少一次+幂等兜底（publish 与 mark 分事务，重复投递由下游幂等键+唯一索引去重）。

**Q4：失败重试和死信怎么设计？**
答：两级。Outbox 层 attempt≥3 置 dead，dead 可人工 retry；任务/流层 AsyncTask 状态机 failed 可重试、终态发 dead-letter 流；Redis Stream 消费失败不 ack，30 秒后 XCLAIM 由同组接管（崩溃恢复）。

**Q5：Redis Streams 消费和轮询有什么区别？**
答：标准消费组模式：XGROUP 建组、XREADGROUP 阻塞拉取（不是空转轮询）、XACK；消费组可负载均衡、未 ack 消息在 PEL 由 XCLAIM 恢复。全系统只有 outbox_worker 是 DB 轮询（因为 outbox 表本身是关系型持久化队列）。

**Q6：为什么引入整套异步机制，不直接同步调 embedding/通知？**
答：延迟（embedding 很慢会拖垮主链路）、可靠性（同步失败污染业务事务、Pub/Sub 丢消息；outbox 同事务保证不丢、Streams 持久化保证可达、幂等键保证不乱）、可运维（独立进程独立伸缩、事件前缀分流、outbox 表自带审计、dead 可重试）。

## 6. 贯穿全项目的核心设计原则（背下来）

1. **确定性优先、LLM 仅咨询**：意图/路由/工具全规则化，LLM 默认关闭且只读。
2. **后端为最终边界**：前端隐藏只是体验，每个受保护 API 都做服务端鉴权；JWT claims 不可信，权限以库为准。
3. **权限与数据范围分层**：操作级（依赖注入）+ 数据级（SubjectScope 服务端改写 SQL 参数），不把过滤做在 ORM 模型层。
4. **AI 永不直接改钱**：草稿→确认→人工复核，确认令牌=签名证据，全链路审计。
5. **业务事实表 > 记忆 > RAG**：余额/持仓/风评/订单以业务库为唯一权威来源，记忆/RAG 只做上下文补充。
6. **可靠异步 = Outbox 同事务 + Redis Streams 消费组 + 幂等 + 死信**，不要分布式事务。
7. **有界 ReAct / 受控 NL2SQL**：自由执行面归零，所有可执行路径可静态审查。
