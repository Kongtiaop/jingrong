## 2.1 项目整体介绍

**Q2.1-1 请挑选一个你深度参与、技术难度最高、亮点最多的项目，从产品价值、技术架构、难点攻克三个维度展开介绍。**
答：讲 **智能财富管理多Agent平台**。
- **产品价值**：面向客户/投顾/客服/风控/运营，覆盖客服问答、产品推荐、风险评估、订单/工单查询、自然语言申购。核心定位是"AI 辅助决策、确定性规则兜底"，AI 不直接动钱、不绕过权限和风控。
- **技术架构**：Vue3 前端 → FastAPI 模块化单体 → Service 业务层 → Port/Repository + Infrastructure 适配层 → PostgreSQL(+pgvector)/Redis/Qwen；异步用 Outbox + Redis Streams + Worker。
- **难点攻克**：①AI 代客下单合规——用"自然语言→草稿→15分钟一次性确认令牌→幂等建单→员工复核+风控闸门"闭环，AI 只生成提案；②权限越权——RBAC + SubjectScope + 权限版本化缓存，SQL 参数服务端改写为授权闭包；③可靠异步——Outbox 同事务 + Redis Streams 消费组 + XCLAIM 崩溃恢复 + 死信重试。

**Q2.1-3 一句话概括你的主导项目。**
答：用 FastAPI + LangChain/LangGraph + PostgreSQL/pgvector + Redis 构建了一个多 Agent 财富管理平台，让客户能用自然语言完成产品推荐、风险评估和受控下单，内部人员能做受控数据分析——所有 AI 动作都被权限、适当性、确认令牌、幂等和审计约束在安全边界内。

**Q2.1-5 完整梳理从用户发起提问到最终内容输出的全链路数据流，说明每层模块作用。**
答：用户输入 → `api/customer_service.py`（鉴权、capability 前置过滤）→ `CustomerAgentExecutionService`（加载短期记忆→人工接管门→意图规划 `CustomerIntentPlanner`→LLM影子/回退→`route_for_plan`→澄清状态机）→ `CustomerTaskExecutor`（多任务 DAG 并行 + 有界 ReAct）→ `CustomerReadTools`/`CustomerQueryRouter`（工具白名单 + 带 customer_id 的确定性事实查询，或走 RAG）→ 结果汇总 `summarize` → 审计写 `AuditLog` → `save_short_term` 存短期记忆 → 返回结构化响应。

**Q2.1-6 使用 LangChain 和 LangGraph 落地业务系统的过程中，最有心得、最有亮点的设计是什么？**
答：**"确定性编排 + 有界执行"的安全架构**。我们定义了 LangGraph Supervisor 骨架和 Agent 端口协议作为基座，但当前执行用**自研确定性编排器**（意图路由 + DAG 任务执行 + ReAct 预算 + 工具白名单）。亮点是：把"权限先于路由、范围先于检索、规则先于建议、确认先于执行、幂等先于恢复、审计贯穿"这套纪律写进了代码——LLM 输出永远只是"建议解释"，不是执行授权。

**Q2.1-10 项目做了多级权限隔离，向量库层面的权限隔离是如何实现的？**
答：两层。①**知识域 Scope**：`KnowledgeScope(knowledge_base_ids/categories/permission_levels)`，`public_customer`/`internal_advisor` 两档，下推成 SQL 行级 `IN` 过滤 + 激活版本四重过滤；②**数据范围**：客户/持仓/订单/风险等事实查询在 `CustomerQueryRouter` 里硬编码 customer_id 条件，数据分析的 SQL subject 参数在服务端改写为授权闭包（`data_analysis_agent.py`），客户传什么 id 都绕不过。

**Q2.1-13 项目用户量级大概多少？**
答（诚实版）：当前是**可运行的 MVP/原型系统**，面向内部演示与业务验证，不是已上线的生产平台，所以我没有编造线上 DAU/请求量。代码有 E2E 和并发测试证明正确性，但量级数据需要真实压测后才敢报。

**Q2.1-16 站在你的角度，如何为业务流程做提效？业务场景中如何合理嵌入 AI 能力？**
答：原则是**"该 AI 的让 AI 做、该规则的让规则做"**。能确定性判断的（权限、适当性、状态机、幂等）走规则；需要理解和解释的（客服问答、产品解释、推荐、草稿生成）走 AI；高风险动作永远落在"AI 出草稿→规则校验→人工确认"的回环里。这样 AI 提效但不失控。

## 2.6 金融/投研/智能投顾场景

**Q2.6-1 智能投顾Agent平台的业务背景、你核心负责的工作、落地后的业务价值分别是什么？**
答：

- **价值**：客服高频咨询自动化、投顾报告草稿提速、风险实时扫描、取数从排期到秒级出图，且所有 AI 动作可审计、不越权、不直接动钱。

**Q2.6-6 基于LangGraph搭建的LM网关五道合规防线具体是哪五层？金融场景五层风控体系完整设计是什么？**

2. **权限/角色门**：`require_permission/require_staff_permission/require_advisor_permission` 依赖注入。

4. **适当性/风控**：`SuitabilityService`（风险等级 C1-C5/客户类型/资产门槛）+ 交易前 `_blocking_risk_alert` 风控闸门。
5. **确认 + 审计 + 幂等**：一次性确认令牌、`AuditLog` 全链路、唯一索引幂等兜底。

**Q2.6-10 金融场景下，如何从技术与业务角度度量Agent架构的好坏？**
答：技术侧看**越权访问事件数=0、自由执行被拒、幂等冲突、可追溯性（审计完整）、可测试性**；业务侧看**合规拒绝正确率、澄清后成功率、人工转接信息完整度、自动执行事故数=0**。核心是"AI 不越权、可解释、可审计"比"回答流畅"更重要。

**Q2.6-14 财务智能审核中，大模型参与到什么程度？是否会让模型直接决定审核通过或驳回？**
答：**不会**。模型只做"意图理解、参数补充、解释、出草稿"；最终是否通过由确定性规则/服务裁决（适当性、风控、订单状态机）。必要时加人工复核节点——AI 初审 + 规则终审 + 人工兜底，符合金融合规。

## 3. Agent 架构与编排

### 3.1 Agent 基础概念

**Q3.1-1 Agent 的定义？核心组件有哪些？**
答：Agent 是能感知环境、基于目标做决策、通过工具采取行动并反思迭代的智能体。核心组件：LLM（推理核心）+ 工具集（行动能力）+ 记忆（上下文/长期事实）+ 规划器（任务拆解）+ 执行循环（ReAct）+ 安全边界（权限/预算/审计）。

**Q3.1-2 智能体与传统聊天机器人、普通机器学习模型的区别？**
答：聊天机器人是"单轮问→答"、无自主行动；普通 ML 模型做单点预测/分类；Agent 是**有目标、能规划、能调工具、能多轮迭代、能对状态负责**的闭环系统。

**Q3.1-3 解释 Agent「感知-决策-行动」闭环。**
答：感知=接收用户输入/工具返回/环境状态；决策=LLM 判断当前该推理还是调工具、下一步做什么；行动=执行工具调用或输出答案；再回到感知观察结果，循环直到达成目标或达到预算上限。本项目用 `CustomerTaskExecutor` 的 ReAct 循环实现：Plan→Tool Call→Observation→Check→Reflect。

**Q3.1-5 是否了解 ReAct、Plan-and-Execute 和 Reflection？Plan-and-Execute 与 ReAct 差异？怎么选？**
答：了解。**ReAct**=思考-行动-观察交替，边做边改，适合工具调用、需要探索的任务。**Plan-and-Execute**=先整体规划再逐步执行（可异步），适合任务明确、步骤可预见的场景。**Reflection**=对自身输出反思修正。差异：ReAct 迭代快但可能发散；Plan-and-Execute 规划清晰但对变化响应慢。本项目对有界知识问答用类 ReAct（预算 3/3），对多任务用类 Plan-and-Execute（DAG 调度）。

**Q3.1-8 top-p、top-k、温度参数控制什么？**
答：都是采样参数。温度越高越随机；top-k 只从概率最高的 k 个 token 里采样；top-p 从累计概率达 p 的最小 token 集采样。温度偏多样性，top-k/top-p 偏截断低概率 token，可组合使用。

**Q3.1-10 为什么要用智能体实现业务需求，用传统脚本不可以吗？Agent 和直接写脚本的区别？**
答：脚本是"写死的确定性流程"，适合固定、可预期任务；Agent 的 LLM 能理解模糊自然语言、动态决策、调用多个工具应对未知输入。但**能用脚本的就不该用 Agent**——本项目核心就是"能规则化的走规则，Agent 只负责需要理解的层"，这是性价比和可控性双赢。

### 3.2 ReAct 框架

**Q3.2-1 ReAct 完整原理、适用场景？**
答：ReAct 让模型交替输出 Thought（推理）→ Action（调工具）→ Observation（观察结果），把推理和行动结合，减少幻觉、能逐步修正。适用：知识问答、工具调用、需要多步验证的任务。

**Q3.2-3 ReAct 中 Thought/Action/Observation 循环如何实现？大模型节点和工具执行节点分别负责什么？**
答：大模型节点（LLM）负责"思考+决定动作或答案"；工具执行节点负责真正调用 `CustomerReadTools`/`CustomerQueryRouter` 并返回结果给模型观察。本项目在 `CustomerTaskExecutor` 里循环 `MAX_REACT_ITERATIONS=3`、`MAX_REACT_TOOL_CALLS=3`。

**Q3.2-5 如何避免 ReAct 一直循环无法结束？**
答：三招：①**迭代/工具上限**（我们 3/3）；②**退出条件**——模型输出最终答案或明确无法继续；③**低置信度转人工/澄清**，不让模型死循环试探。本项目首轮 low_confidence 只允许一次查询改写，第二次直接转人工。

**Q3.2-6 为什么不使用 LangChain，选择自研 ReAct？自研的完整流程、循环最大限制是多少？**
答：因为金融场景要**可审计、可测试、权限/scope 逐点可控**，LangChain 的 AgentExecutor 是通用黑盒，预算和权限钩子难精细化。自研流程：意图规划→路由→进入 ReAct 循环（Plan→Tool→Observe→Check→Reflect）→汇总审计；循环上限 `MAX_REACT_ITERATIONS=3`、`MAX_REACT_TOOL_CALLS=3`，工具名白名单固定 8 个。

### 3.3 多 Agent 协同

**Q3.3-1 多个智能体如何设计？如何协同、信息如何传递、流程如何编排？**
答：用 Supervisor + 领域 Agent 模式。Supervisor（`CustomerAgentExecutionService`）负责意图识别和路由，把请求分发到客服/投顾/风控/数据分析/业务 Agent。信息通过**结构化 `IntentTask`/`TaskExecutionResult`** 传递；多任务用 DAG + `depends_on` 依赖编排并行执行（`CustomerTaskExecutor`，max_parallel_tasks=4）。

**Q3.3-2 有没有做多智能体 A2A 协作？是单运行时 LangGraph 编排子 Agent，还是分布式多运行时？**
答（诚实版）：当前是**单进程内的确定性编排**（Supervisor + 任务执行器），不是分布式多运行时 A2A。已定义 Agent 端口协议作为演进基座，但没有引入跨进程 Agent 通信协议。

**Q3.3-5 多个 Agent 并行执行时，如何解决协同冲突？如何保证结果一致性？**
答：①**结果不做自由合并**——各 Agent 产出结构化结果，由 Supervisor 汇总，业务事实以确定性服务为准；②**规则优先**——`IntentPolicyResolver` 单向合并，规则压过模型；③**审计**——每个 Agent 结果写 `AuditLog`，冲突可追溯。

**Q3.3-9 多个 Agent 是串行还是并行？为什么？**
答：看依赖。`CustomerTaskExecutor` 按 DAG 拓扑：无依赖的任务**并行**（asyncio.gather，max 4），有 `depends_on` 的（如"推荐+申购"里申购依赖推荐）**串行**等依赖完成，依赖死锁标 blocked 防止挂死。

**Q3.3-11 系统中实现了多少个独立 Agent？职责分别是什么？**
答：能力注册表里 9 项能力（`agent_capabilities.py`）——客户可见 4 个：CustomerServiceAgent（客服问答）、CustomerRecommendationCapability（产品推荐）、CustomerTradeDraftCapability（自然语言申购草稿）、CustomerRiskExplanationCapability（风险解释）；内部 5 个：DataAnalysisAgent（受控数据分析）、AdvisorAgent（投顾）、RiskAgent（风控）、BusinessAgent（业务）、AdminAgent（后台管理）。

**Q3.3-16 路由到不同 Agent 的判断依据？不同 Agent 配置了什么工具？**
答：判断依据=**意图规划 + 优先级路由**。`CustomerIntentPlanner` 用关键词正则识别意图，`route_for_plan` 按 `ROUTE_PRIORITY` 选最高路由。客服用 `search_customer_knowledge`（RAG）；业务事实用 `CustomerReadTools` 固定 8 个白名单工具（get_my_workorder_status/order_status/risk/asset/product_status 等）；数据分析用批准模板/指标，不拼自由 SQL。

**Q3.3-17 如果 Agent 数量从几个扩展到几十个，架构会有什么瓶颈？10-20 个如何编排？**
答：瓶颈：①提示词膨胀（工具/意图全塞）；②意图路由误判率上升；③上下文传递混乱。应对：**多级路由**（先粗分类再细分领域）、**工具按需加载**（意图→加载对应领域工具）、**能力注册表 + 权限矩阵**统一管理、**结构化中间结果**标准化传递。避免全量工具/全量意图进上下文。

### 3.4 LangGraph 编排

**Q3.4-1 你实现 AI Agent 采用什么框架？为什么选 LangGraph 而不是 LangChain 原生 AgentExecutor 或自研？**
答（诚实版）：我们**定义了 LangGraph Supervisor 骨架和 Agent 端口协议作为基座，但当前执行用自研确定性编排器**。选型的取舍：LangGraph 的 StateGraph/checkpoint 适合复杂有状态多 Agent 编排和断点恢复，是 P3/P4 演进方向；但金融场景当前要**可审计、可测试、预算/权限逐点可控**，确定性管线更直接。所以是"协议用 LangGraph 定，执行用自研落地"，后续复杂场景再上真图。

**Q3.4-3 LangGraph 架构在多 Agent 场景的核心优势？**
答：状态图显式化（节点/边/条件路由）、支持循环与并行、checkpoint 持久化支持断点恢复、可观测性（流式事件）、相比自由代码更结构化和可维护。

**Q3.4-6 LangGraph 的 State 包含哪些核心字段？实际存储哪些业务数据？**
答：状态图 `AgentState`（`app/schemas/agents.py`）包含 message 历史、当前节点、迭代计数、中间结果、工具调用记录、上下文元数据等。业务数据不直接全量放 state，事实以业务库为准，state 只存结构化中间结果和引用。

**Q3.4-10 使用 LangGraph 过程中遇到过哪些问题？**
答（诚实版）：当前生产执行是自研确定性管线，`graph.py` 是占位骨架。所以实际遇到的问题更多在**确定性编排**上：多意图依赖死锁、ReAct 循环失控、澄清死循环——分别用 DAG 拓扑 + blocked、迭代/工具上限、澄清 2 次强制转人工解决。

**Q3.4-15 LangGraph 中如何实现类目动态路由？多层路由架构怎么设计？**
答：动态路由=条件边/`Command` 根据状态决定下一节点。本项目对应的多层路由：`CustomerIntentPlanner` 意图层 → `route_for_plan` 优先级层 → `CustomerQueryRouter` 业务事实层（能读库的走库、否则落回 RAG）。目的是缩小数据库暴露面、让"能查的事实"与"需检索的知识"分离。

### 3.5 工作流编排

**Q3.5-1 客服Agent的工作流由哪些节点组成？理解、决策、执行、守护、响应节点分别负责什么？**
答（对应本项目 `CustomerAgentExecutionService.execute` 12 步）：理解=意图规划+实体抽取；决策=路由+策略校验；执行=`CustomerTaskExecutor` 多任务调度+ReAct；守护=人工接管门/澄清计数/能力前置过滤/预算限制；响应=结果汇总+审计+写短期记忆。

**Q3.5-5 执行节点如何处理多个并发任务？无依赖能否并发？有依赖如何保证串行？**
答：`CustomerTaskExecutor` 拓扑调度——每轮取"依赖全部完成的 ready 任务"，无依赖任务 `asyncio.gather` 并发（max_parallel_tasks=4）；有 `depends_on` 的任务等依赖完成才进 ready 批，天然串行；无 ready 项（死锁）标 blocked。

**Q3.5-10 工作流中循环次数限制、安全校验节点的作用？**
答：循环上限（ReAct 3/3）防模型死循环消耗 token 和算力；安全校验节点（权限/scope/适当性/风控闸门）在关键动作前拦截，解决"性能失控 + 越权执行"两类问题。

### 3.6 状态管理与断点恢复

**Q3.6-1 Agent 断点续跑如何实现？运行状态如何持久化与恢复？**
答（诚实版）：本项目**尚未实现**完整断点续跑——它是 P4 计划。当前有基础设施：`AsyncTask`（任务状态机 queued→running→success/failed/dead）+ Outbox + Redis Streams（`XCLAIM` 崩溃恢复）。P4 规划复用这套做"安全快照 + 恢复前重校验权限"。计划书明确不先上全局 LangGraph Checkpointer。

**Q3.6-2 为什么选 Redis 保存工作流状态？快照存什么？**
答：Redis 快、适合会话级临时状态（短期记忆 `customer:memory:short:{customer_id}:{conversation_id}`，TTL 30 分钟，存澄清上下文/待执行计划/转人工状态）。业务事实不存 Redis，以 PostgreSQL 为准。长期/可恢复状态应落库（AsyncTask/PG）。

**Q3.6-7 如何保证任务状态不丢失？Redis 故障如何不中断业务？**
答：短期状态允许丢失（可重建）；**业务事实和任务状态落 PG**（`AsyncTask`），Redis 只是缓存/队列。Redis 故障的代价是缓存失效和队列中断，但业务数据不丢；流消费靠 `XCLAIM` 恢复，outbox 靠 `FOR UPDATE SKIP_LOCKED` 认领。

**Q3.6-8 系统如何管理判断任务状态？唯一标识是什么字段？**
答：任务唯一标识 `AsyncTask.id` + `idempotency_key`（唯一索引）；会话用 `conversation_id`；订单用 `order_id`；工单用 `work_order_id`。状态机集中在各状态字段（AsyncTask.status / Order.status / CustomerServiceSession.status）并由领域服务统一迁移。

### 3.7 意图识别与路由

**Q3.7-1 意图识别怎么做？一句话多个意图如何处理？**
答：`CustomerIntentPlanner` 用关键词正则表 `_patterns`（17 组 intent→marker→route→confidence）识别。多意图：一次产出多个 `IntentTask`，带 `depends_on` 依赖；执行器 DAG 并行，汇总时按任务拼接答案。模板层多意图归为 `T8_MULTI_INTENT`。

**Q3.7-6 置信度怎么计算？是靠大模型给的吗？Supervisor 有兜底机制吗？**
答：当前以**规则置信度**为主（`_patterns` 里给 confidence），LLM 回退默认关闭。兜底：规则未命中→unknown 任务+澄清；澄清 2 次→转人工；LLM 影子模式只作参考、异常时规则规划器保持权威。

**Q3.7-8 意图识别完全依赖大模型，还是结合了规则？为什么不全交给大模型？**
答：**规则为主、LLM 兜底可选**。原因：①规则可审计、可测试、延迟低；②金融场景误判代价高；③LLM 有幻觉和不可确定性。规则能覆盖明确/高风险表达（订单号/工单号/申购/转人工），复杂自然语言才需要 LLM，且走 allowlist + 单向合并防越权。

**Q3.7-14 意图识别两大主流方案？如何优化？**
答：①**规则/模板**（关键词、正则、Few-shot）——确定性强、可解释；②**LLM 分类/生成**——覆盖复杂表达但不可控。优化：规则+LLM 混合、明确优先级（规则压过模型）、意图模板化（T1-T10）、评测集持续回归。

**Q3.7-16 Agent 返回结果置信度过低时，路由如何处理？**
答：低置信度（RAG 无有效引用）→ `low_confidence` → 只重试一次查询改写 → 仍失败转人工建工单（`CustomerRagHandoffService`），不给"编造答案"。整体 `needs_clarification`/`handoff` 兜底。

### 3.8 Agent 运行时与消息处理

**Q3.8-6 循环场景最大循环次数、中断条件怎么设计？追问次数和边界怎么控制？**
答：ReAct 循环上限 3/3；澄清追问上限 2 次（`clarification_count>=2` 强制转人工）；`pending_intent_plan` 支持追问后合并重新规划。边界控制保证不无限循环、不无限追问。

**Q3.8-8 工具调用前是否会通过钩子校验参数合规？参数边界是枚举还是 few-shot？**
答：会。工具是**白名单**（固定 8 个名，外部直接 tool_not_allowed）；数据分析的参数走**Schema 契约**（`bind_template_parameters`：数量/长度/limit/日期范围硬校验 + `authorized_scope_only` 只收授权 subject）。参数边界用代码硬约束 + 少量模板，不依赖 few-shot。

**Q3.8-10 模型提取字段缺失时如何处理？关键信息缺失会主动追问吗？追问有次数限制吗？**
答：会。缺失产品/金额等关键交易参数 → `needs_clarification` + `missing_fields`，提示"关键交易参数必须由客户明确提供，系统不会猜测"。追问次数限制 2 次，超过转人工。

**Q3.8-12 Agent 运行产生的数据哪些持久化到数据库？如何实现用户间数据隔离？**
答：持久化的有：`NaturalLanguageOrderDraft`（草稿）、`Order`/`Trade`（订单成交）、`AuditLog`（审计）、`CustomerMemory`（长期记忆）、`CustomerServiceSession`（会话）。隔离靠：查询硬编码 customer_id 作用域 + `SubjectScopeService` 授权闭包 + RBAC 权限门。

**Q3.8-18 Agent 记忆模块怎么设计？上下文与记忆如何组装？**
答：短期（Redis）+ 长期（PG `CustomerMemory`）。短期存澄清上下文/待执行计划/转人工状态；长期存客户确认的参数/偏好/非敏感事实（带事件审计）。组装：`load_short_term` 取会话状态→注入执行上下文→结合当前 query；业务事实不读记忆，以业务库为准。

**Q3.8-22 如何限制 Agent 的越权行为？**
答：五层——能力注册表前置过滤、RBAC 权限依赖、SubjectScope 数据范围（SQL 参数服务端改写）、工具白名单 + 只读、ReAct 预算 + 审计。交易类意图永不执行（executed=False + 页面深链）。

### 3.9 Agent 场景设计题

**Q3.9-6 金融合规交易 Agent 如何设计？**
答（对应本项目）：意图识别→参数澄清（不猜）→适当性/风控/额度预检→订单草稿（不冻结）→用户明确确认（一次性令牌）→风险分级二次认证/人工审核→幂等下单→Outbox+审计。模型只生成草稿和解释，资金动作由确定性服务在显式确认后触发。

**Q3.9-15 有没有遇到过某个场景，你认为不应该交给 AI 来做？**
答：有。**最终的资金划扣、订单成交、风险等级变更、绕过适当性/风控**这些"不可逆/高影响"动作绝不该由 AI 自主决定。AI 可以出草稿、解释、建议，但最终确认和执行权必须收回到确定性服务 + 人工。这也是本项目贯穿的设计原则。

## 4. RAG 知识库与检索

### 4.1 RAG 整体设计

**Q4.1-1 解释 RAG 核心流程及作用。**
答：检索增强生成——先从知识库检索相关证据，再让 LLM 基于证据回答，降低幻觉、支持引用溯源。本项目流程：上传→切块→Qwen embedding→pgvector 存储→混合检索→置信度过滤→引用式生成→低置信转人工。

**Q4.1-2 你的 RAG 系统整体设计与完整流程？落地遇到过哪些难点，如何解决？**
答：完整链路见 Q4.1-1。难点：①检索分数语义（RRF 融合值，阈值不能用余弦相似度标准）——用 min_score 滤 0 分项 + 无有效引用即拒答；②中文召回——同义词扩展 + 向量腿扛语义；③权限隔离——KnowledgeScope 下推 SQL 行级过滤；④文档版本化——chunk hash 复用 embedding 省成本。

**Q4.1-3 你们的 RAG 是基于开源框架搭建，还是完全自研？**
答（诚实版）：**核心检索自研**——`KnowledgeRepository.search_hybrid` 直接调 PG 全文 + pgvector 做 RRF 融合。LangChain 只是可选外壳（`langchain_retriever.py`），不是检索依赖。这样权限/版本过滤能在同库 JOIN 里做。

**Q4.1-7 RAG 召回率、准确率是多少？如何衡量 RAG 回答质量？**
答（诚实版）：本项目有 `AGENT_RAG_EVALUATION_GUIDE` 和 `nl2sql_eval` 评测，但**线上指标（召回率/准确率）需要真实评测集跑出后才有数**，我没有编造具体百分比。衡量维度：Hit@k、引用正确率、忠实度、拒答正确率、转人工率、延迟。

**Q4.1-9 描述完整 RAG 工作流：文档解析、清洗、切片到检索召回、生成回答全链路。**
答：上传（校验格式/大小）→ outbox 事件 → knowledge_worker 消费 → `ingest_document`（docx/纯文本解析）→ `_chunks`（size=1000, overlap=120, step=880）→ Qwen embed（1024 维，逐条，重试3次）→ 存 pgvector → `search_hybrid`（PG FTS + cosine + RRF，top_k=5）→ 置信度过滤（min_score）→ `customer_rag_answer` 只按 `[引用N]` 生成（temperature=0.1）→ 低置信转人工。

### 4.2 文档解析与预处理

**Q4.2-1 支持哪些格式解析？不同格式分别用什么方案？**
答（本项目）：`ingest_document` 支持 `.txt/.md/.docx`。docx 用 python-docx 逐段取文本；txt/md 按 UTF-8 读取。**本项目没有用 MinerU/BGE**（那是简历里另一个 RAG 项目的方案）；当前是纯文本+docx 解析。若被追问"为什么没支持 PDF/扫描件"——如实说当前 MVP 限定格式，复杂解析是迭代方向。

**Q4.2-9 商品实体和 SKU 信息如何识别保存？**
答：这不是本财富项目的场景，略过。（若被问，简述：通过实体识别/结构化抽取，落到业务表，不做纯模型猜测。）

### 4.3 Chunking/切片策略

**Q4.3-1 Chunking 原理？切片策略？用什么分词器？**
答：把长文档切成有语义完整性的小块，便于向量召回。本项目用**字符级固定窗口滑动**：size=1000、overlap=120、step=880（`knowledge_ingestion._chunks`），每块先 rstrip 再 strip。不是标题感知/语义切块。

**Q4.3-3 除了固定标记/标题切分，还了解哪些策略？什么是递归切分、父子 Chunk、QA Chunking？**
答：递归切分=按分隔符层级（段落→句→词）递归切到目标大小；父子 Chunk=父块留完整上下文、子块做检索单元，召回子块时关联父块；QA Chunking=把文本转成问答对再向量化。本项目当前用固定窗口，父子/QA 是优化方向。

**Q4.3-7 分块大小怎么决定？超长段落如何处理？重叠窗口如何设计？**
答：分块大小要匹配 embedding 和 LLM 的上下文，并平衡语义完整与召回粒度。本项目 size=1000、overlap=120（约 12% 重叠），重叠避免切在语义边界。超长段落会被滑动窗口切分（由固定窗口自然处理，但语义可能被切散——这是已知取舍，优化方向是结构感知切块）。

**Q4.3-11 存入 Milvus 的长期对话文本切片策略？切块大小、overlap 是多少？**
答（诚实版）：本项目在线检索走 pgvector，Milvus 是可切换后端。文本切块统一 size=1000/overlap=120；长期对话记忆的切片是 P3 规划，尚未落地。

### 4.4 向量数据库

**Q4.4-1 使用的向量数据库？为什么选它？**
答：主用 **PostgreSQL + pgvector**。原因：①与业务数据**同库同事务**，混合检索（向量+全文）和权限/版本过滤能在同一 SQL JOIN 里做；②少一套运维组件。Milvus 通过 VectorStore Port/Adapter 作为可切换后端（P5 性能对比用）。

**Q4.4-6 用什么向量模型做 Embedding？**
答：Qwen/DashScope 系 embedding（`text-embedding-v4` / `qwen3.7-text-embedding` 可配），**统一 1024 维硬约束**（`QwenProvider.embed` 校验维度，不符抛错）。

**Q4.4-10 向量数据库宕机如何处理？**
答：本项目 embedding/向量检索失败会**自动降级**：`search_hybrid` 失败降级 `search_text`（ILIKE 关键词），`retrieval_mode` 在响应里如实标注（`embedding_degraded/text-fallback`）。pgvector 与业务同库，宕机即数据库故障，走 DB 高可用/备份恢复。

### 4.5 检索策略

**Q4.5-1 知识库召回完整流程？单路还是多路？**
答：**混合检索（两路）**：文本腿 PG 全文 `ts_rank_cd` + 向量腿 pgvector cosine，各取 max(top_k*4,20) 候选后 RRF 融合取 top_k=5。不是单路语义。

**Q4.5-2 混合检索完整流程？为什么比单用稠密或稀疏更合适？**
答：先两路各自召回候选→RRF 融合重排→取 top_k。稠密（向量）抓语义相关但可能漏精确词；稀疏/关键词抓精确匹配但不懂语义。混合互补：精确词召回 + 语义泛化，覆盖更全。

**Q4.5-3 稠密检索和稀疏检索各解决什么问题？什么是 BM25？**
答：稠密=语义相似度，解决"说法不同但意思相同"；稀疏=词频统计（BM25 是关键词加权排序），解决"精确关键词匹配"和专有名词。本项目文本腿用 PG 内置 FTS（simple 配置），不引入独立 BM25。

**Q4.5-6 多路召回结果如何处理？重排用什么模型？重排核心作用？**
答：本项目用 **RRF**（`1/(60+rank)`）融合两路排序，不依赖跨模型分数可比性。当前没上独立 Cross-Encoder rerank（重排模型是优化方向）；重排核心作用是把召回里的候选按更精准的相关性精排，提升 Top-k 质量。

**Q4.5-12 为什么采用向量检索+BM25 的混合召回？**
答：单一检索有盲区——纯向量会漏精确专有名词（政策编号、产品名），纯关键词不懂语义（同义表达）。混合让两者互补，再用 RRF 融合，兼顾召回率和准确率。

**Q4.5-23 多路召回有没有做过消融实验？**
答（诚实版）：`scripts/compare_vector_backends.py` 等脚本做过后端对比，但**没有系统化的多路消融实验**——它是迭代优化方向，需建立统一评测集后做。

### 4.6 RRF 融合与重排

**Q4.6-1 什么是 RRF？如何融合？得分怎么算？**
答：RRF（Reciprocal Rank Fusion）= 对每个文档在多路结果里的排名取倒数并求和：`score = Σ 1/(k + rank)`，本项目 k=60。融合后按总分降序取 top_k。不依赖各路分数尺度可比。

**Q4.6-2 为什么排名越靠前得分越高？为什么 RRF 比相似度加权平均更合适？**
答：排名靠前 rank 小，1/(60+rank) 大，得分高。RRF 只用**排名**不用原始相似度分数——因为不同检索通道（FTS 分数、cosine）分数尺度不同、不可直接加权平均；RRF 把多路统一到"排名"这个可比维度，鲁棒且实现简单。

**Q4.6-3 不同检索模型的分数尺度不同会产生什么问题？**
答：直接加权平均会让"分数偏高"的那路主导结果，失去另一路价值；RRF 用排名规避了这个尺度问题。

**Q4.6-4 Rerank 模型在流程里做什么？为什么召回后要做初排+重排两阶段？不直接全量用重排？**
答：初排（召回）用轻量双路扩召回面保证覆盖；重排用更准的 Cross-Encoder 精排提升 top-k 质量。不直接全量重排是因为重排模型对每对 query-doc 计算代价高，只在召回后的小候选集上做，兼顾质量与延迟。本项目当前用 RRF 做精排，Cross-Encoder 是优化方向。

### 4.7 Embedding 模型

**Q4.7-1 什么是 Embedding 文本向量化？**
答：把文本映射成高维稠密向量，语义相近的文本向量距离近，用于语义检索/相似度计算。本项目用 Qwen embedding 出 1024 维向量存 pgvector。

**Q4.7-8 向量维度越高是否一定语义更强？为什么有些是降维不是升维？**
答：不是。维度增加提升表达力但有上限，过高会过拟合噪音、增加存储和计算成本。Embedding 相比 one-hot/词袋是**降维**（把高维稀疏的 token 空间压缩成语义稠密向量），维度是精度与成本的权衡。

### 4.8 RAG 优化

**Q4.8-1 RAG 优化你有哪些经验和步骤？**
答：全链路：①解析/切块（结构感知、父子块）；②召回（多路、query 改写、同义词扩展）；③融合/重排（RRF、Cross-Encoder）；④生成（引用约束、temperature）；⑤兜底（低置信转人工、Bad Case 回收进回归集）。本项目已落地：同义词扩展、混合检索+RRF、低置信转人工、chunk hash 复用。

**Q4.8-5 项目上线初期召回不准确，从全链路拆解做了哪些优化？**
答：从五处拆：①切块——固定窗口改结构感知；②Query 理解——中文同义词扩展（`normalize_customer_query`）；③召回——纯向量改混合+RRF；④过滤——无有效引用拒答而非硬答；⑤兜底——低置信转人工 + Bad Case 回归集。

**Q4.8-10 知识库检索响应耗时较长，从交互和技术层面怎么优化？**
答：技术：缓存（权限感知缓存 60s TTL）、索引（pgvector + FTS）、限制召回候选数、降级文本检索。交互：异步/流式返回、低置信快速转人工而非干等。

### 4.10 GraphRAG 与知识图谱

**Q4.10-1 GraphRAG 解决什么问题？Neo4j 存哪些关系？**
答（诚实版）：本项目 **Neo4j/GraphRAG 未落地**（requirements 里是 Optional P5 依赖）。了解其价值：解决多跳关系推理（客户→持仓→产品→行业）、实体关系类问题，补充纯 RAG 无法做的结构化关联分析。若被问：说明它是规划项，当前用关系型+向量已覆盖。

### 4.11 权限感知 RAG

**Q4.11-1 RAG 里怎么做权限（敏感数据隔离）？**
答：本项目两层：①`KnowledgeScope`（knowledge_base/categories/permission_level 三维度）下推成 SQL 行级 `IN` 过滤，`public_customer`/`internal_advisor` 分档；②叠加激活版本 + deleted 过滤。产品推荐等实时数据不走 RAG，直接查业务表并过适当性校验。

**Q4.11-3 涉密、非涉密文档共存同一向量库，双层安全兜底校验机制？检索结果如何二次过滤？**
答：双层：①**检索前**——Scope 下推 SQL `IN` 过滤，无权数据根本不进候选集；②**检索后**——二次校验引用文档的 `permission_level`，无权即过滤/拒答。业务事实（余额/持仓）则完全不进向量库，直接查业务表。

### 4.12 其他 RAG 相关

**Q4.12-5 怎么衡量 RAG 知识库答得好不好？如何评定 Top5 质量？**
答：看命中率（正确 Top-k 是否召回）、引用正确率、忠实度（回答是否只用引用）、拒答正确率、低置信转人工率、延迟。Top5 质量看：是否覆盖真实答案、是否多相关、是否含无关/越权内容。

**Q4.12-8 低置信度判定阈值如何确定？是测试集调优吗？**
答：本项目 `min_score=0.0001` 是 **RRF 融合分语义**下的过滤阈值（滤掉两路都没召回的 0 分项），不是余弦相似度阈值。真正的拒答条件是"没有任何≥阈值引用"。阈值调优应基于评测集逐步验证，这是迭代方向。

**Q4.12-9 低置信度触发转人工时，会向人工客服携带哪些上下文信息？**
答：`CustomerRagHandoffService.handoff` 会建工单 + 建 `CustomerServiceSession(status=waiting_human, mode=human, handoff_reason=rag_low_confidence)`，携带意图/query/检索状态，客户回答追加"已为您转接人工，工单号…"。

**Q4.12-18 如果系统回答错误，如何定位问题？Bad Case 如何分类？**
答：从五环节定位：解析/切块→检索→融合→生成→兜底。用 `retrieval_mode`（hybrid/text-fallback）和 `evidence_status` 判断是哪一环降级。Bad Case 分类：检索缺失、引用错误、生成幻觉、越权、拒答误判——回收进回归集持续验证。

## 5. 大模型基础（概念部分）

### 5.1 Transformer 架构（概念）

**Q5.1-1 Transformer 注意力机制、自注意力是什么？**
答：自注意力让每个 token 通过 Query/Key/Value 计算与序列内其他 token 的相关权重，加权聚合上下文，捕捉长距离依赖。多头注意力和用多个子空间。

**Q5.1-3 Transformer 为什么能替代 RNN/CNN 成为主流？**
答：①并行计算（不像 RNN 串行）；②直接建模长距离依赖（RNN 有梯度消失/遗忘）；③可扩展（scaling law）。代价是 O(n²) 注意力，靠 KV Cache、稀疏注意力缓解。

**Q5.1-4 Encoder-Decoder 与 Decoder-only 架构区别？**
答：Encoder 双向看全上下文做理解（BERT 类），Decoder 单向（掩码）自回归生成（GPT 类）。Decoder-only 用因果掩码保证只能看前文，当前主流生成模型多为此；Encoder-Decoder 适合序列到序列（翻译、摘要）。

**Q5.1-8 从自注意力解释 KV Cache 为什么能降低重复计算？**
答：生成是逐 token 自回归，已生成 token 的 Key/Value 无需重算。KV Cache 把历史 K/V 缓存，每步只算新 token 的 K/V 和注意力，避免重复计算 O(n²)，大幅提速。代价是显存占用（PagedAttention 缓解）。

**Q5.1-14 PagedAttention 核心理念？与传统 KV 缓存管理区别？**
答：把 KV Cache 按固定块（page）管理，类似操作系统虚拟内存分页，减少碎片、提高显存利用率，支持共享（beam search 分叉）和高效调度。vLLM 的核心。

### 5.2 模型微调（概念 + 本项目边界）

**Q5.2-1 LoRA 原理？如何选高效微调方法？**
答：LoRA 冻结原权重，只训练低秩分解的增量矩阵（A×B），参数量极小、显存省、可插拔切换多个任务。选型：数据少/要快速迭代用 LoRA/QLoRA；要全能力用全量微调（成本高）；要通用用 RAG+Prompt 而非微调。

**Q5.2-18 接手新项目，如何判断用微调、RAG 还是 Agent？选型依据？**
答：**能用 RAG 的用 RAG**（知识外挂、可更新、可溯源）；**需要格式/能力固化才微调**（结构化输出、特定风格、领域术语，且数据够）；**需要多步推理+工具调用用 Agent**。成本：RAG 最低、Agent 次之、微调最高。三者可组合。本项目主要用 RAG + Agent，没做微调（模型能力用 Prompt/RAG 满足）。

### 5.3 模型蒸馏与量化（概念）

**Q5.3-1 蒸馏原理？**
答：用大模型（Teacher）的输出软标签/逻辑蒸馏到小模型（Student），让小模型学大模型的知识分布，达到接近精度但更小更快。

### 5.4 模型选型

**Q5.4-3 DeepSeek R1 与 V3 区别？DeepSeek V4 上下文多少？128K 上下文概念？**
答：R1 是推理模型（带思维链、强数学/推理）；V3 是通用模型（更快、成本低）。128K 上下文≈单次能容纳约 20 万+汉字/大段文档。若不确定 V4 具体上下文，如实说不确定具体版本号，但理解上下文窗口概念。

**Q5.4-4 为什么选 Qwen3 而不是 DeepSeek 或其他？**
答：本项目用 Qwen/DashScope：统一接入、embedding+LLM 一套、API 稳定、中文强、文本向量 1024 维与 pgvector 契合。选型考虑：任务适配、中文能力、生态、成本、稳定性。

**Q5.4-7 金融请求拦截二分类小模型选用 0.9B→1.5B 的原因？**
答（通用思路）：拦截类任务简单直接，小模型够用、延迟低、成本低、易部署；参数量提升带来准确率边际收益但成本上升，1.5B 是精度/成本平衡点。

**Q5.4-23 不同参数量模型分别应用在什么场景？小参数量有什么优势？**
答：小模型（≤1.5B）用于简单分类/拦截/关键词，快而省；中模型（7B-14B）通用生成；大模型（32B+）复杂推理/长文。小模型优势：延迟低、显存小、可边缘/本地部署、成本低。

### 5.5 推理优化（概念）

**Q5.5-1 模型推理速度慢的全套优化方案？**
答：①工程层——KV Cache、PagedAttention、批处理（continuous batching）、量化（INT8/INT4）、算子融合；②调度——大小模型分流（简单用小、难用大）；③架构层——蒸馏小模型、流式输出减少首 token 延迟；④缓存——语义缓存命中复用。

**Q5.5-7 vLLM 的 PagedAttention 核心理念？**
答：分页管理 KV Cache，减少显存碎片、支持跨请求共享、提高吞吐和并发。详见 Q5.1-14。

### 5.6 模型效果与幻觉治理

**Q5.6-4 通常用哪些方法减少幻觉？**
答：①RAG 引用约束（只按证据答、无依据拒答）；②低置信转人工；③结构化约束（Schema、temperature 调低）；④提示词强制"资料不足明说"；⑤评测/回归集。本项目五者都用到。

**Q5.6-7 平台从产品层面有哪些手段缓解幻觉？**
答：引用溯源展示、拒答+转人工兜底、证据门禁（无引用不生成）、人工复核节点、Bad Case 回收闭环。让"答错"变成"可拒答、可转人工、可追溯"。

**Q5.6-12 提示词约束条件失效了怎么办？**
答：不依赖提示词做安全底线——用**代码级硬约束**兜底（白名单、Schema 校验、规则、权限、审计）。提示词失效时：改用确定性校验、增加 Structured Output/JSON Schema、把关键规则下沉到服务层而非 Prompt。

## 6. 提示词工程

**Q6-1 什么是提示词工程？与传统特征工程异同？**
答：提示词工程=设计输入给 LLM 的指令/上下文/示例，引导稳定输出。传统特征工程=人工构造 ML 输入特征。二者都影响"模型输入质量"，但提示词调的是语言指令而非数值特征。

**Q6-2 怎么优化提示词？写提示词主要有哪几部分组成？**
答：角色+任务+上下文/知识+约束/边界+输出格式+示例（few-shot）。本项目 RAG 提示词核心：只按 `[引用N]` 回答、禁止编造/承诺收益/执行交易、资料不足明说并建议转人工。

**Q6-4 提示词调优核心方法、优化迭代思路？分哪些板块？**
答：板块：角色设定、任务定义、证据来源、约束条件、输出格式、降级策略。迭代：Bad Case→定位环节（检索/生成）→改对应板块→回归集验证，避免改一个坏一类。

**Q6-8 强制合规提示词如何实现？解决大模型上下文过长时忘记输出警示话语的问题？**
答：不依赖模型"自觉记着"——用**系统提示词固定位置 + 结构化输出字段 + 服务端校验**。关键合规标识（如 `must_not_submit_without_verified_customer_confirmation`）作为结构化约束注入，并在 `IntentPolicyResolver` 层强制，而非靠模型在长上下文里记住。

**Q6-10 如何构建意图分类的提示词模板？**
答：先定义意图分类体系（T1-T10），给每个类别示例，用 Structured Output/JSON Schema 约束输出，配合规则置信度做兜底（本项目 LLM 回退默认关，规则为主）。

**Q6-13 如何保证对话历史+系统提示词+RAG 知识不超 LLM 上下文窗口？**
答：①只给必要证据（top_k 控制）；②历史裁剪/摘要（短期记忆只存关键状态）；③分段注入；④监控 token 用量（token meter）。本项目 RAG 只回传 top_k=5 引用，短期记忆只存结构化状态而非全文。

## 7. 记忆机制

### 7.1 记忆分层架构

**Q7.1-1 Agent 上下文记忆如何实现？短期、长期方案是什么？**
答：**短期=Redis**（`customer:memory:short:{customer_id}:{conversation_id}`，TTL 30 分钟，存澄清上下文/待执行计划/转人工状态）；**长期=PostgreSQL**（`CustomerMemory` 记忆卡片 + `CustomerMemoryEvent` 事件审计，单事务 upsert）。已实现三件套，Agent 当前只接入短期。

**Q7.1-5 Agent 长期记忆完整实现方案？**
答：长期用 PG `CustomerMemory`，只写客户确认的参数（confirmed_parameter）、服务偏好、非敏感会话事实，带 source/confidence/status/expires_at + 事件审计，部分唯一索引保证同 key 一条 active。**注意：链路尚未接入 Agent（P3 计划）**。

**Q7.1-6 四层记忆是哪四层？用户画像一般在结构化层，长期记忆怎么做？**
答：方法论 L0-L3：L0 原始流水（会话/消息/审计）、L1 记忆卡片（CustomerMemory）、L2 场景档案、L3 长期用户画像。本项目 L0/L1 已落地，L2/L3 规划。用户画像走业务表/结构化数据，长期记忆只存受控事实，不替代业务表。

**Q7.1-10 简历中提到的"分层记忆机制"具体如何设计实现？**
答（对应本项目）：短期（Redis）管会话连续性——澄清补参、待执行计划、转人工门控；长期（PG）管跨会话事实——客户确认的参数/偏好，带事件审计。设计边界：**业务事实表永远高于记忆**，余额/持仓/风评不以记忆为最终依据。L2/L3 是规划项。

**Q7.1-14 记忆与会话数据存储在什么数据库？**
答：短期记忆和会话缓存→Redis；长期记忆（CustomerMemory/CustomerMemoryEvent）→PostgreSQL；会话消息→PostgreSQL（customer_service_message 是事实源）。

### 7.2 记忆更新与冲突处理

**Q7.2-2 更新记忆时不物理删除，采用逻辑删除的实现？用什么元数据溯源？**
答：`CustomerMemory.status`（active/软失效）+ `CustomerMemoryEvent`（event_type=upsert，payload JSON）记录每次变更，可追溯来源事件、时间、写入 Agent。

**Q7.2-4 可信度+时间衰减无法维护真实场景时怎么办？**
答：金融场景**不过度依赖记忆可信度/时间衰减**——关键事实一律读业务表，记忆只做上下文补充；低置信/过期记忆检索时不参与高风险决策。冲突仲裁有明确边界：用户陈述最多以"待验证"短期记忆存在，业务库更新后才升为权威事实。

**Q7.2-7 相同场景重复请求，会直接沿用历史结论，还是同时走完整空上下文链路兜底？**
答：**历史记忆只作上下文补充，不替代当前执行**。业务事实（余额/持仓/风评/订单）始终重新从业务库读取；记忆只是减少重复询问，不用于高风险决策兜底。

**Q7.2-9 多租户架构下如何实现不同用户之间的记忆隔离？**
答：短期记忆 key 含 `{customer_id}`，长期记忆 `CustomerMemory.customer_id` 过滤 + 查询硬编码 customer_id；共享读取需重新校验 SubjectScope。隔离靠"key 粒度高 + 查询作用域 + 权限校验"。

### 7.3 上下文管理

**Q7.3-3 当上下文过长时如何处理？如何避免超出模型限制？**
答：只注入必要信息（top_k 证据 + 结构化状态）、历史摘要/裁剪、分段注入、token 监控。本项目短期记忆只存关键状态字段，RAG 只回传 top_k=5 引用。

**Q7.3-4 多轮长对话易上下文 Token 溢出，采用哪些记忆管控方案？**
答：短期状态化（不存全文只存结构）、澄清上下文合并（original_query+本次）、转人工兜底、RAG 引用精简。不把整段历史塞进上下文，避免噪音和 token 膨胀。

## 8. Text2SQL / NL2SQL / NL2API / MCP

### 8.1 Text2SQL / NL2SQL

**Q8.1-1 什么是 Text2SQL？项目里有没有用到？**
答：把自然语言查询转成 SQL。本项目用到，但走**受控路线**——不是让模型自由生成 SQL，而是"数据目录召回 + 批准模板 + 参数契约 + 只读执行"，`nl2sql_ready=False` 明确关闭自由 SQL。

**Q8.1-3 生成 SQL 关联几张表？是否把全部 Schema 放进 Prompt？**
答：本项目**不把全部 Schema 塞 Prompt**——用**数据目录（Data Catalog）**动态召回相关表/列，命中后再加载。避免 Prompt 超长、避免模型乱关联。

**Q8.1-5 NL2SQL 核心挑战？不同实现方案对比？**
答：挑战=Schema 语义鸿沟、多表关联、参数安全、防注入。方案：①自由生成（灵活但危险）；②模板+参数（安全但受限）；③目录约束型（本项目：目录召回+模板白名单+参数契约，安全与灵活折中）；④SQL IR（模型出结构化计划、服务端编译，演进方向）。

**Q8.1-9 表、字段多，如何避免 Prompt 超长（渐进式查表）？**
答：用数据目录**渐进式召回**——先粗召回候选表，命中后再查该表的列明细，不一次性全量注入。本项目 `DataCatalogService` 先召回表→限表内检索列→拉关系/示例。

**Q8.1-13 是否做 SQL 语法树校验？不做会有什么问题？**
答：会。`validate_readonly_template` 做结构只读校验（SELECT/WITH 开头、禁 DDL/DML/分号/注释/pg_sleep/长度≤20000），`_extract_references` 静态解析引用表/列。不做语法校验的风险：注入、越权表字段、报错 SQL、非法执行。

**Q8.1-18 如何保证 AI 查询数据准确性？AI 生成表格时编造数据怎么办？**
答：①数据来自确定性 SQL/业务表，非模型记忆；②只读执行+绑定参数+外层 LIMIT，杜绝模型拼 SQL；③结果只透传查询结果，不允许模型"补全"数据；④query_plan 标记 read_only/free_sql=False 供审计。

**Q8.1-20 NL2SQL 如何注入租户隔离条件，确保跨租户数据不可越权访问？**
答：`authorized_scope_only` 参数——subject 从授权集合（`SubjectScopeService.authorized_subject_ids`）服务端绑定，SQL 的 subject 参数改写为授权闭包；请求里出现越权客户 ID 显式 `unauthorized_subject` 拒绝。跨租户隔离在数据层强制，不依赖模型。

**Q8.1-22 SQL 生成的安全校验机制？白名单/拦截非法语句如何实现？**
答：四层——①入口只收自然语言（直接 SELECT 都拒）；②模板白名单（approved+角色）；③目录引用范围（引用表/列 ⊆ 声明 ⊆ 活跃可查询目录且非敏感）；④执行层绑定参数+外层 LIMIT+失败 rollback。拦截：BLOCKED_SQL 正则禁 DDL/DML/分号/注释等。

**Q8.1-25 NL2SQL 完整链路：自然语言如何一步步转化为可执行的安全 SQL？**
答：自然语言 → `evaluate_query_safety`（防 SQL 注入）→ 数据目录召回候选模板 → 模板白名单（approved+角色+只读校验）→ 参数契约绑定（含 subject 授权闭包）→ 目录引用范围校验 → 外层 LIMIT 包裹 → SQLAlchemy 绑定参数执行 → 失败 rollback → 结构化结果+query_plan。

**Q8.1-29 系统对用户追问，一般设置多少次追问上限？**
答：意图澄清 2 次转人工（`clarification_count`）；数据分析参数缺失用 `clarification_for_parameter_reason` 生成澄清话术，subject 多义时要求明确授权主体，不硬猜。

### 8.2 NL2API

**Q8.2-5 API 返回结果需要二次确认的交互流程怎么设计？**
答（对应本项目下单）：NL→草稿（不执行）→展示确认页（产品/金额/适当性/风险）→用户勾选风险声明+确认令牌→服务端重跑预检→确定性建单→后续状态机。二次确认=用户显式同意 + 令牌校验 + 幂等，防误操作和重复提交。

### 8.3 MCP 协议

**Q8.3-3 MCP 与 Function Calling、Tool Calling 区别？**
答：Function/Tool Calling 是模型层约定（模型输出工具名+参数）；MCP 是**跨进程/跨应用的标准协议**（Client-Server），让模型工具能标准化连接外部系统，解决"工具散落、难以复用"的问题。MCP 规范了工具发现、调用、权限的标准接口。

**Q8.3-5 普通 Tool 也能发 HTTP 调天气接口，为什么还要 MCP？MCP 新增价值？**
答：普通 Tool 是应用内自封装，不可复用、不可跨应用；MCP 提供**标准协议**——统一的工具发现（list）、调用（call）、认证、schema，让工具成为可共享的标准能力，生态互通，多个 Agent/应用可复用同一 MCP Server。本项目当前用自研 Tool，MCP 是了解项/演进方向。

**Q8.3-7 你是否接触过 MCP 和 Harness Engineering？如何理解从 Prompt → Context → Harness 的演进？**
答：理解这个演进：**Prompt Engineering**（调指令）→ **Context Engineering**（管好喂给模型的上下文/记忆/知识）→ **Harness Engineering**（把模型约束进一个含工具、权限、校验、审计、降级、评测的"外骨骼"系统，模型只是其中一个组件）。本项目就是典型的 Harness——模型只是理解/解释引擎，权限/风控/确认/审计都在 harness 层。

**Q8.3-14 举一个你实际设计开发的 MCP 工具？**
答（诚实版）：本项目用的是**自研 Tool + 工具白名单**（`CustomerReadTools` 8 个工具），没有实现 MCP Server。可举例说明自研工具的 schema（名称/描述/参数）和权限门禁，说明这是 Tool 而非 MCP。

**Q8.3-20 怎么理解 MCP 协议？MCP 如何解决传统 Function Calling 的局限性？**
答：Function Calling 局限=工具定义散落在应用里、无标准发现/认证/复用。MCP 用 Client-Server + JSON-RPC 标准化工具生命周期，工具可发现、可认证、可跨应用复用，解决工具生态碎片化。

## 11. 安全合规与权限隔离

### 11.1 数据权限隔离

**Q11.1-1 系统权限控制（安全域）如何实现？从代码层面说明不同角色的权限校验逻辑。**
答：RBAC 五表（users/roles/permissions/user_roles/role_permissions）。代码层面：FastAPI 依赖注入 `require_permission / require_staff_permission / require_advisor_permission`——`current_user` 每次请求从 DB 重载用户+角色+权限，校验权限码集合，缺权 403；`is_super_admin` 直接放行。数据范围由 `SubjectScopeService` 单独控制（授权客户集合）。

**Q11.1-2 普通用户和管理员如何区分权限？如何保证只能访问自己权限范围内的数据？**
答：权限码区分（customer 角色只有 customer:*，管理员有 admin:*）；操作级用权限依赖注入，数据级用 SubjectScope 授权闭包 + 查询硬编码 user/customer 作用域。管理员改权限后 bump 缓存版本号，旧缓存失效。

**Q11.1-6 涉密、非涉密文档共存同一向量库，双层安全兜底校验机制？**
答：同 Q4.11-3：检索前 Scope 下推 SQL 过滤 + 检索后二次校验引用权限；业务敏感事实不进向量库。

**Q11.1-9 内部问答机器人如何防止用户越权查询敏感数据？**
答：①操作级权限门；②数据级 customer_id 作用域 + SubjectScope；③RAG 知识 Scope 隔离；④数据分析 subject 参数服务端改写；⑤工具白名单 + 只读。前端隐藏只是体验，后端才是边界。

**Q11.1-10 仅用白名单做权限控制是否过于简单？还有哪些层级防护？**
答：是。白名单只是第一层。本项目有：RBAC 权限码、SubjectScope 数据范围、RAG 知识 Scope、SQL 参数服务端改写、权限版本化缓存、确认令牌+幂等、全链路审计——多层纵深防御。

**Q11.1-11 用户声称自己是管理员/老板时，如何核验身份权限？**
答：不信任用户自称——JWT 只作身份凭证，每次请求从 DB 重载真实角色/权限；`is_super_admin` 是 users 表字段 + super_admin 角色双通道，且权限以数据库当前值为准。身份用 Argon2 密码/刷新令牌轮换校验。

### 11.2 风控与合规

**Q11.2-1 针对金融场景的合规性与可追溯性需求，架构上做了哪些针对性技术方案？**
答：①**确认令牌**——一次性、只存哈希、常量时间比较，作为客户签名证据；②**订单状态机 + order_status_history**——每次迁移留痕可审计；③**AuditLog** 贯穿 create_draft/confirm_draft/权限变更/Agent 调用；④**适当性/风控闸门**——`SuitabilityService` + `_blocking_risk_alert` 拦截；⑤**幂等**——唯一索引防重复下单；⑥**业务事实表优先**——模型不覆盖余额/持仓/风评。

**Q11.2-3 完整介绍你设计的五层安全合规拦截链路，每层技术实现、拦截目标？**
答：同 Q2.6-6：①能力注册表前置过滤（谁能触发 Agent）；②RBAC 权限依赖注入（能不能做这个操作）；③SubjectScope 数据范围（能做哪些客户）；④适当性/风控（适不适合做）；⑤确认令牌+幂等+审计（合规落地、可追溯）。逐层拦截，越权/越范围/不适配/无确认都在到达执行前被挡。

### 11.3 安全防护与越狱

**Q11.3-1 怎么做大模型安全性问题处理？**
答：①提示词注入检测（多链路）；②结构化输出约束；③规则引擎兜底（不依赖模型自主防御）；④低置信/高风险转人工；⑤服务端强校验（权限/scope/幂等）作为最后防线；⑥审计。核心：**模型防御只是辅助，安全底线在 harness 层（规则+权限+校验）**。

**Q11.3-4 Prompt 注入检测如何实现？为什么要在多个链路节点都做注入检测？**
答：因为注入可能发生在输入、检索内容、工具返回等多个入口，单一节点检测会漏。本项目在 `data_analysis_agent` 对 SQL 参数、RAG 对输入做安全校验（`evaluate_query_safety` 拒 SQL-shaped 输入），并在多个环节用规则兜底。金融场景宁可多检测不可漏。

**Q11.3-6 如何限制大模型越权操作、规避高危数据库操作？仅靠提示词控制吗？**
答：不靠提示词。用**服务端硬约束**：只读执行（readonly 校验）、白名单、绑定参数、外层 LIMIT、权限/scope、失败 rollback。提示词只是第一层，真正的安全在代码。

**Q11.3-9 在什么条件下 AI 可以执行实际动作？哪些操作不能交给 AI？**
答：AI 只在"用户显式确认 + 规则校验通过 + 在授权范围内"时，通过确定性服务执行受控动作（如下单草稿确认）。**不能交给 AI 的**：直接资金划扣、绕过适当性/风控、改风险等级、跨用户越权、不可逆高影响操作——这些必须人工 + 确定性服务。

### 11.5 Agent 安全

**Q11.5-2 工作流中循环次数限制、安全校验节点的作用？**
答：循环上限（ReAct 3/3、澄清 2 次）防死循环消耗 token 和卡死；安全校验节点（权限/scope/适当性/风控/令牌）在关键动作前拦截越权和违规执行。

**Q11.5-4 SQL 生成安全校验机制？白名单/拦截非法语句的实现？**
答：同 Q8.1-22 四层。拦截用 `BLOCKED_SQL` 正则（禁 DDL/DML/分号/注释/pg_sleep/into 等）+ 只读校验 + 目录引用范围 + 绑定参数。

## 14. 测试与效果评估

**Q14.1-1 RAG 怎么做自动化测评？**
答：用标准问答对评测集（question + 预期答案 + 证据标注），跑召回（Hit@k、MRR）和生成（忠实度、引用正确率、拒答正确率），自动化比对。本项目有 `AGENT_RAG_EVALUATION_GUIDE`、`nl2sql_eval_cases.json`、`scripts/test_knowledge_chunk_incremental.py` 等。

**Q14.1-4 Top-K 检索结果用什么指标评估？**
答：Hit@k（正确文档是否在 top-k）、MRR（第一个正确结果排名）、NDCG（带位置加权）。K 值调优用评测集验证不同 K 的命中率与延迟平衡。

**Q14.1-10 你怎么判断 RAG 系统有没有变好？看哪些指标？**
答：召回（Hit@k、MRR）、引用正确率、忠实度、拒答正确率、低置信转人工率、延迟 P95、token 成本。用同一评测集做前后对比，避免主观感觉。

**Q14.2-3 你的 Agent 和 RAG 是怎么测试的？**
答：分层：单元测试（意图规划、模板解析、幂等、状态机）、HTTP 回归（`scripts/test_*_http.py`，覆盖权限/越权/幂等/澄清）、Redis/Worker 回归（outbox、XCLAIM、死信）、前端 Playwright E2E（`frontend/e2e`，覆盖 AgentBubble 下单/推荐/转人工）、并发测试（`test_http_concurrency`）。

**Q14.2-4 你的测试集怎么获取？怎么确定测试集全面？**
答：来源=真实业务场景 + Bad Case 回收 + 边界构造（越权、多意图、否定、歧义、低置信）。全面性靠：按意图/路由/权限/风险/交易各类别覆盖矩阵化 + 持续补 Bad Case 进回归集。诚实说：需要随迭代扩充，当前覆盖核心链路。

**Q14.2-8 如何验证状态流转是否正确，避免死循环？**
答：状态机单一权威迁移表（`Order.transition`）+ 非法迁移抛错 + 状态历史断言；多任务 DAG 用 blocked 防死锁；ReAct 用迭代/工具上限；测试断言非法迁移被拒、依赖死锁不挂死。

**Q14.3-2 怎么解决召回率低？**
答：全链路调优——Query 改写/同义词扩展、多路召回（混合+RRF）、切块优化（结构感知/父子块）、重排（Cross-Encoder）、消融验证各通路的贡献。先定位是哪一环（Bad Case 分类）再对症。

**Q14.3-4 低置信度判定阈值如何确定？是测试集调优吗？**
答：本项目 `min_score=0.0001` 是 RRF 融合分的过滤阈值（滤 0 分项），真正的拒答条件是无任何有效引用。阈值调优应基于评测集逐步验证，这是迭代方向。

**Q14.3-7 系统"自信度"如何定义？通过哪些维度衡量？**
答：本项目置信度主要来自：RAG 证据状态（evidence_status：sufficient/partial/not_found/low_confidence）+ 检索是否命中有效引用。规则意图给 confidence。不依赖模型"自己说多自信"作为业务判断依据。

**Q14.3-11 Agent 上新之前，如何测试验收性能和效果？**
答：功能验收（意图/路由/工具/越权/转人工各场景 HTTP+E2E）+ 安全性验收（越权用例阻断率=100%、危险 SQL 被拒）+ 性能（P95 延迟）+ 回归（不劣化已有场景）。核心门槛：越权事件 0、自动执行事故 0、可审计完整。

## 附：核心叙事——"本项目 = Harness Engineering 的落地"（30 秒版 + 追问接法）

> 这是全项目最值得反复讲的**一句话叙事**：你不是"把模型放前面让它自由发挥"，而是**把模型装进一个 harness**。

### 因果主线：不是"套概念"，是"金融逼出来的"

> 金融 AI 的第一性需求不是"模型多聪明"，而是**强一致、强监察、强控制**——这三条不可妥协的刚需，恰恰是 harness 的内核。我的项目不是追着趋势做，是金融场景把这套约束逼出来的，后来才发现它正是行业说的 Harness Engineering。

| 金融刚需 | 项目里的落地 | 在 harness 里叫 |
|---|---|---|
| **强一致** | 订单唯一索引幂等、`Decimal` 金额、状态机 `transition`、Outbox 同事务 | 状态与一致性控制 |
| **强监察** | `AuditLog` 贯穿、`order_status_history`、`trace_id`、确认令牌哈希留痕 | 可观测与审计 |
| **强控制** | RBAC、SubjectScope 服务端改写 SQL、确认令牌、ReAct 预算、工具白名单 | 权限与边界 |

**为什么是金融先长出这些**：金融里一个越权查询、一次重复下单、一条不可追溯的 AI 操作，代价是实打实的钱 + 合规事故 + 追责，所以金融没法赌"模型自觉"，只能把每一层都做成确定性约束。

**补充 nuance（让话更严谨）**：harness 不只是金融独有——任何要上生产、要兜责任的 AI（医疗、政务、支付、客服）都需要 harness；金融只是把这条需求压到最极端，是"canary"（金丝雀），在这里做出来的约束方案有普遍参考价值。

**最顺的一句话**："金融 AI 的第一性需求不是'模型多聪明'，而是强一致、强监察、强控制。我所有的设计——幂等、审计、权限、确认、兜底——都是这三条逼出来的，也就是后来行业说的 Harness Engineering。"

### 30 秒答辩版

> "我的系统本质是一个 **Harness**——模型只是里面负责'理解、解释、出草稿'的一个组件，真正决定系统可靠性的是包在它外面的那层确定性外骨骼。权限、适当性、风控、确认令牌、幂等、审计这些'该硬的地方'全部用代码在 harness 层兜住，LLM 的输出永远只是'建议'，不是'执行授权'。所以我的工作重点不是'让 AI 更聪明'，而是'让 AI 在不该动的地方绝对不动'。"

### 被追问时的接法

**Q1：你这个 harness 是自己写的还是用的现成框架？**
答：**自研**的。核心是 `CustomerAgentExecutionService` 这条确定性编排管线 + 规则守卫，不是 LangGraph/AutoGen 那种现成 harness。我们定义了 LangGraph 的 Supervisor 骨架和 Agent 端口协议作为演进基座，但当前执行用自研编排，因为金融场景要权限/预算/审计逐点可控，现成 harness 是通用黑盒、难精细化。

**Q2：Harness 和普通"后端封装模型"有什么区别？**
答：普通封装只是把模型 API 包一层；Harness 是把模型放进一个**带权限、工具治理、校验、记忆、降级、观测、评测、审计的完整闭环**。我的项目每一层都有：工具白名单+只读、ReAct 预算、SubjectScope 数据范围、确认令牌+幂等、低置信转人工、AuditLog、HTTP/并发/E2E 回归。

**Q3：模型在这里的权重是不是太小了，那还要大模型干嘛？**
答：模型承担**理解、解释、生成**这些规则做不了的部分——意图理解、产品解释、推荐话术、草稿生成、复杂查询澄清。规则负责**裁决**。分工是"模型负责理解、规则负责执行与边界"，这正是金融场景的取舍：让模型做它擅长的理解，把风险动作交给确定性代码。

**Q4：怎么证明这个 harness 有效？**
答：用"越权/事故数"这类硬指标——越权访问用例阻断率 100%、危险 SQL 全被拒、重复下单被唯一索引拦截、所有关键事件可审计追溯；加上越权/幂等/并发/低置信转人工的 HTTP 和 E2E 回归集。

### 一句话收尾（可作自我介绍开场）

> "我做的是 **软 AI、硬底座**——大模型负责软性的理解与解释，我负责把所有该硬的地方（权限、风控、确认、幂等、审计）用 harness 兜死。这套'可控 AI'的工程思路，是我和大多数只调 Agent 的人最大的区别。"

## 附：渐进式披露 RAG + 与 Claude Opus 5 对齐（强业界背书）+ NL2SQL 起源

> 这是一条**有业界背书的差异化叙事**：Claude Opus 5 系统提示词里的记忆文件系统，和我做的渐进式披露 RAG 是同一套思路，只是使用方向不同。而且这套思路是我**先在做 NL2SQL 时想到、再统一推到 RAG** 的。

### 一句话版本

> "我的知识库 RAG 用的是渐进式披露——分库预筛 + metadata 目录 + 结构感知 + 精确读取，先目录、按需打开、只读相关。Claude Opus 5 的系统提示词就把同一套思路用在记忆文件系统上，是行业验证过的范式；我的差异是把它用在文档检索，而且它是我先做 NL2SQL（数据目录渐进式召回 Schema）时想到、再统一推到 RAG 的——同一个'先目录、按需加载'原则，在不同场景反复落地。"

### 起源故事（NL2SQL → RAG，这是最加分的点）

1. **先在 NL2SQL 里遇到**：数据库几十张表，不能把全部 Schema 塞进 Prompt。我用**数据目录（Data Catalog）渐进式召回**——先粗召回候选表 → 命中后再查该表列明细 → 再拉关系/示例，不一次性全量注入。本质是"先目录、按需加载"。
2. **后来推到 RAG**：做知识库检索时发现是同一个问题——文档很多，不能把全部内容塞进上下文。于是把 NL2SQL 的"目录→按需加载"搬到 RAG：先看文档 metadata 目录 → 命中再做结构感知读大纲 → 最后精确读取正文。
3. **结论**："渐进式披露"不是某个场景的招数，而是我**在 NL2SQL 先想明白、再统一到 RAG** 的底层原则——"先看目录、按需展开、只读相关"。

### 与 Claude Opus 5 的对比（强业界背书）

| Opus 5 记忆文件系统 | 我的渐进式披露 RAG |
|---|---|
| 先给**目录**（路径+摘要+别名+来源） | 先给**文档清单**（metadata+标题+摘要+分类） |
| 只有相关才 `memory_read` 读正文 | 只有命中才"结构感知→精确读取" |
| 摘要写得有检索价值 | 摘要写得有检索价值 |
| 短文件直接读 | 短文档跳过结构感知直接读 |
| 分库/目录决定要不要打开 | 分库预筛 + 元数据决定要不要打开 |

**为什么有背书价值**：Anthropic 把渐进式披露写进 Claude 旗舰模型（Opus 5）的系统提示词，记忆部分 800 行都在讲这个——说明它是被头部公司验证过的、可落地的上下文工程范式，不是小众技巧。我的用法是"**同一思路、不同方向**"：Opus 用于记忆管理，我用于文档检索。

### 我 RAG 的落地细节（答辩可展开）

1. **分库预筛**：知识按业务域拆库，检索先定位"该查哪个库/分类"，无关库不进候选（也是第一道权限边界）。
2. **metadata 目录**：每文档维护标题/摘要/别名/分类，检索只在目录层做，不读正文。
3. **结构感知**：命中后先读大纲（章节层级），定位答案可能的位置，不整篇进上下文。
4. **精确读取**：按定位直读原文对应片段，答案绑定 文档→章节→页码，可溯源。
5. **自适应**：短文档/非结构化文档字数太少 → 跳过结构感知直接读取，省一跳。
6. **工具化**：把"文档搜索/结构感知/读取"封装为三个受控工具，用接口顺序强制渐进链路（呼应 Opus"能用接口结构保证，就别只靠提示词"）。

### 可能的追问接法

**Q：你这个和普通向量检索 RAG 有什么区别？**
答：普通 RAG 靠"向量相似度撞 chunk"，一次召回 top-k 塞进上下文；我做的是"按结构定位后直读原文"——分库预筛 + metadata 目录 + 结构感知 + 精确读取，召回更确定、上下文更干净、可溯源到章节/页码。对结构清晰的长文档尤其准。

**Q：为什么和 Opus 5 这么像？是不是抄的？**
答：不是抄，是**殊途同归**。我是从 NL2SQL 的"不能全量塞 Schema，要目录渐进式加载"推导出来的，天然长成这样；后来发现 Claude 旗舰模型也把同样原则用在记忆文件系统上，等于**行业验证了我的思路**——这反而说明方法是对的、有普适性。

**Q：短文档跳过结构感知，会不会漏信息？**
答：不会。短文档本身没有可导航的结构，直接读全文反而更快更全；跳过结构感知是省掉无效的一跳，不是省掉读取。判断依据是字数/结构复杂度阈值。
