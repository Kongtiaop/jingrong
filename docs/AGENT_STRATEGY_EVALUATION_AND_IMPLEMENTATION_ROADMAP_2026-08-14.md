## 1. 执行摘要

三份方案提出的方向与当前财富管理平台的安全架构一致：系统应服务于**内部运营分析、客服与人工协同、投顾准备、风险解释和受控业务办理**，而不是把大模型直接用于无确认的自动交易或无边界的数据访问。

当前项目已经完成了若干关键基础：

- Supervisor / Router + Lightweight Planner 的多 Agent 入口；
- Agent 能力前置权限过滤；
- CustomerService、DataAnalysis、Advisor、Risk、Business、Admin 等职责边界；
- `PermissionScopedCache`、`SubjectScopeService` 与授权范围版本化；
- 授权范围的领域服务、事务内 Outbox、Redis Streams Worker、pending/XCLAIM 回归；
- DataAnalysisAgent 的批准模板、目录白名单、参数边界、只读执行和受控澄清；
- 真实 FastAPI / PostgreSQL / Redis 回归；
- Chrome for Testing 真实数据客服/Agent E2E：15 项通过。

因此，系统已具备采纳三份方案的基础，但不具备同时全量实施的条件。最优路线是：

```text
P2：受控分析产品化与评估门禁
P3：最小共享工作记忆
P4：按真实业务工作流实施长时恢复
```

## 2. 当前能力基线与缺口

| 能力域 | 当前已具备 | 当前缺口 | 对三份方案的意义 |
|---|---|---|---|
| Agent 编排 | 权限前置 Router、轻量计划、bounded ReAct、受控工作流 | 复杂跨 Agent 上下文没有统一共享模型 | 共享记忆可在 P3 补齐 |
| 权限与范围 | RBAC、subject scope、权限缓存版本、目录过滤 | 前端菜单尚未完全 permission-driven | 共享/恢复读取必须继承现有上下文 |
| 分析安全 | 批准模板、静态/动态白名单、参数边界、拒绝与澄清 | SQL IR、AST、成本门禁尚未完成 | P2 主线，不能被记忆/恢复工程打断 |
| 异步可靠性 | AsyncTask、Outbox、Redis Streams、Worker、dead/retry、pending/XCLAIM | Agent 任务级快照与跨步骤恢复未统一 | P4 可在现有能力上演进 |
| 客服协同 | 转人工、会话状态、通知、WebSocket、E2E | 客户/投顾/风控间的审计化上下文摘要不统一 | P3 共享工作记忆的首批场景 |
| 评估与测试 | HTTP 六维基线、权限/缓存/Outbox/Worker/E2E 回归 | CI 工件、发布门槛、有无记忆对照尚未形成 | P2/P3 实施前置条件 |

## 3. 方案一：多 Agent 共享记忆设计方案

### 3.1 方案价值判断

**价值等级：高；建议采纳，但延后至 P3。**

该方案正确识别了客服、投顾、风控、分析和业务 Agent 之间存在记忆孤岛。财富管理业务中，以下流程确实需要受控的上下文传递：

```text
客户咨询
→ 客服确认意图与资料缺口
→ 投顾准备建议草稿
→ 风控读取已确认风险事实
→ 业务 Agent 进入受控办理或人工确认
```

如果没有共享工作记忆，各 Agent 会重复询问、重复检索，或把上下文非结构化地塞进 prompt，难以审计。

### 3.2 当前不宜全量实施的原因

文档提出模型扩展、统一写入/检索 API、聚合 Worker、组织级记忆、向量检索和多 Agent 全量接入。此范围对当前阶段过大，主要风险是：

- 记忆读取越过当次 permission context 或 subject scope；
- 复制客户资产、交易、风控等原始敏感数据；
- 过期偏好或历史判断影响当前合规决策；
- Agent 间共享未确认事实；
- 聚合 Worker 产生难以解释的组织级结论；
- 在尚无无记忆基线时，无法判断共享记忆是否真的提升效果。

### 3.3 P3 最小共享工作记忆 MVP

P3 只实现“工作记忆”，不实现全量长期知识库或组织级认知。

#### 允许写入

| 类型 | 示例 | 要求 |
|---|---|---|
| 已确认意图摘要 | “客户询问持仓风险，未要求交易” | 必须标记确认状态 |
| 任务状态 | “投顾草稿待客户确认” | 仅保存状态与引用 ID |
| 非敏感结果摘要 | “适当性规则不匹配，原因引用 rule_id” | 不复制资产/交易明细 |
| 人工交接摘要 | “客服已收集的补充材料清单” | 来源消息/工单可追溯 |

#### 禁止写入

```text
模型私有推理链
完整 prompt 或检索正文
原始资产、持仓、交易、风险证据副本
未确认的事实或模型猜测
可让后续读取绕过权限的结果快照
```

#### 最小数据模型

```text
memory_id
memory_type
scope_type                 # conversation / customer / authorized_subject / agent_private
conversation_id
subject_id_reference       # 只存受控引用，不跨范围展开
producer_agent
summary
source_event_id
permission_context_fingerprint
subject_scope_version
status                     # confirmed / superseded / revoked / expired
expires_at
created_at
```

### 3.4 P3 实施步骤

1. 冻结 P2 无记忆基线与六维评估报告；
2. 定义 `SharedWorkingMemoryService`，只允许服务层写入；
3. 使用 `PermissionContext` 和 `SubjectScopeService` 作为读写前置条件；
4. 首先接入客服转人工摘要与投顾准备摘要两个场景；
5. 写入审计、TTL、撤销/覆盖语义；
6. 对同一测试集执行无记忆与有记忆对照；
7. 若语义准确率、澄清率或人工转接效率没有可验证改善，不扩大接入范围。

### 3.5 P3 验收标准

- 跨用户、跨角色、跨 subject 的记忆不可读取；
- 权限变更或 subject scope 变更后旧记忆不再命中；
- 每条共享记忆可追溯来源事件和写入 Agent；
- 删除、过期、撤销后不能继续用于 prompt；
- 有/无记忆评估报告可复现；
- 不持久化模型推理链与原始敏感数据。

## 4. 方案二：财富管理 AI 系统业务方向验证与实施建议

### 4.1 方案价值判断

**价值等级：最高；立即采纳为产品优先级依据。**

技术能力必须映射到财富管理的可验证业务价值。当前系统适合优先服务以下业务方向：

| 业务方向 | 建议优先级 | 当前基础 | 下一步 |
|---|---:|---|---|
| 内部运营分析 | 高 | DataAnalysisAgent、目录、模板、权限缓存 | P2 完善澄清、图表、CI 门禁 |
| 客服与人工协同 | 高 | 会话、通知、WebSocket、15 项 E2E | 指标化服务质量与交接摘要 |
| 投顾准备 | 高 | 客户授权、适当性、草稿、subject scope | P3 引入受控工作记忆 |
| 风险解释与处置 | 高 | 风险预警、AML、工单、审计 | 强化解释证据与恢复工作流 |
| 受控业务办理 | 中高 | needs_confirmation、跳转、权限/风控 | 保持人工确认和幂等边界 |
| 自动交易/自动执行 | 低 | 不应作为近期目标 | 明确禁止绕过确认 |
| 黑盒营销推荐 | 中低 | 仅有适当性基础 | 先做可解释规则和证据 |

### 4.2 当前产品原则

```text
AI 可以解释、检索、归纳、辅助准备、发起受控流程；
AI 不得在无确认、无风控、无审计的条件下直接执行交易或扩展数据访问范围。
```

### 4.3 P2 业务实施步骤

1. 完成 DataAnalysisAgent 的多主体澄清与前端结构化呈现；
2. 让表格/图表/查询计划/拒绝原因可被内部人员理解；
3. 将 NL2SQL 六维报告持久化为 CI 工件；
4. 为客服、投顾、风险和分析结果增加可审计的业务指标；
5. 以“减少人工重复查询、减少无效转接、提高解释可追溯性”为验收目标，而非只看模型回答流畅度。

### 4.4 建议业务指标

| 指标 | 目标用途 |
|---|---|
| 合规拒绝正确率 | 安全拒绝不应被误判为故障 |
| 澄清后成功率 | 衡量受控澄清是否减少重复人工沟通 |
| 人工转接前信息完整度 | 衡量客服摘要质量 |
| 投顾准备耗时 | 衡量共享工作记忆价值 |
| 风险事件解释可追溯率 | 衡量引用、规则和审计完整性 |
| 自动执行事故数 | 必须为 0 |

## 5. 方案三：长时运行 Agent 断点续跑设计方案

### 5.1 方案价值判断

**价值等级：中高；建议 P4 渐进实施。**

方案的分层恢复思想正确：

```text
会话级恢复
任务级恢复
批次级恢复
外部等待恢复
```

系统已有可复用基础：

- `AsyncTask` 状态与重试；
- Outbox 与 Redis Streams；
- Worker dead/retry、pending/XCLAIM；
- AML 批次补跑；
- WorkOrder 和 CustomerServiceSession 状态机；
- 授权范围事件的可靠消费；
- Redis 短期会话记忆。

### 5.2 当前不直接实施全量 Checkpointer 的原因

- 多数当前 Agent 请求仍为秒级同步任务；
- CustomerTaskExecutor 并非统一 LangGraph 工作流；
- 持久化 checkpoint 容易包含 prompt、检索内容和业务数据；
- 没有足够明确的长时业务场景与恢复 SLA；
- 一次性引入全量 checkpoint 会让权限变化、幂等、外部回调、重复执行和审计复杂度陡增。

### 5.3 P4 优先场景

| 场景 | 现有基础 | P4 增量 |
|---|---|---|
| AML 批次扫描 | AmlBatchRun、补跑 | 统一 Agent 任务快照/恢复引用 |
| 知识导入/向量化 | Worker、Outbox | 步骤级状态与失败恢复 |
| 人工审批等待 | WorkOrder 状态机 | 外部等待令牌与恢复入口 |
| 客服转人工等待 | CustomerServiceSession | 统一交接/恢复摘要 |
| 风险调查报告 | 风控、工单、审计 | 长时多步骤任务状态机 |
| 投顾诊断草稿 | 适当性、授权客户 | 可恢复草稿步骤，不能自动执行 |

### 5.4 P4 最小恢复快照

```text
workflow_id
workflow_type
step_name
status
input_fingerprint
permission_context_fingerprint
subject_scope_version
completed_output_references
idempotency_key
resume_token_reference
expires_at
```

不保存：

```text
完整模型推理链
原始客户数据副本
可直接重放的敏感请求体
脱离当前权限的结果缓存
```

### 5.5 P4 实施步骤

1. 选择一个真实长时工作流，优先 AML 或知识导入；
2. 定义步骤状态、幂等键、恢复条件与失败上限；
3. 复用 AsyncTask + Outbox + Worker，不先引入全局 LangGraph Checkpointer；
4. 对外部等待使用状态机 + 回调 token，不阻塞 Worker；
5. 权限/subject scope 变更后，恢复前重新校验或拒绝恢复；
6. 完成 worker 崩溃、重复回调、超时、重放、权限变化的回归；
7. 再评估是否将 LangGraph Checkpointer 引入特定长时 Agent。

### 5.6 P4 验收标准

- 已完成步骤不重复执行；
- 外部写操作有幂等键；
- Worker 崩溃后可从安全断点恢复；
- 权限变化后不能以旧快照越权恢复；
- 外部等待不占用 Worker；
- 所有恢复、失败和重放写入审计；
- 恢复路径与正常路径均有 HTTP / Redis / Worker 回归。

## 6. 推荐实施总路线

```text
当前 P2
│
├─ 1. 完成多主体 subject 澄清
├─ 2. 前端结构化澄清、表格、图表、查询计划展示
├─ 3. Schema / Few-shot / 枚举缓存迁移到 PermissionScopedCache
├─ 4. 六维评估报告 CI 工件和发布门槛
└─ 5. 冻结无记忆基线

P3：最小共享工作记忆

├─ 客服转人工摘要
├─ 投顾准备摘要
├─ 权限、subject scope、TTL、审计
└─ 有/无记忆对照评估

P4：长时任务恢复
│
├─ AML / 知识导入 / 人工等待

├─ 幂等、恢复、权限变化测试
└─ 仅在需要时引入特定 LangGraph Checkpointer
```

## 8. 风险与否决条件

下列情况出现时，必须暂停或回退对应阶段：

| 阶段 | 否决条件 |
|---|---|
| P2 | 出现自由 SQL、越权目录/字段、跨用户缓存命中或安全事故数大于 0 |
| P3 | 共享记忆读取绕过权限/subject scope、无法删除/撤销、评估无收益 |
| P4 | 恢复会重复外部写操作、权限变化后仍能恢复旧结果、Worker 长时间阻塞 |

---

## 9. 结论

三份方案共同指向同一个正确方向：财富管理 AI 必须以**权限、范围、审计、确认、幂等和可恢复性**为基础，而不是以模型自由度为中心。

当前最优决策是：

```text
先把 P2 的受控分析、评估和前端闭环做扎实；
再用 P3 的最小共享工作记忆减少跨 Agent 重复沟通；
最后在 P4 针对真实长时工作流引入恢复能力。
```

这条路线既能保留三份文档的长期价值，也能避免在当前阶段过早引入不可控复杂度。
