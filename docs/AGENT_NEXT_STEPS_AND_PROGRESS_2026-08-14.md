# 财富管理 AI 系统下一阶段行动方案与当前进度

> **文档用途**：统一项目当前进度、阶段决策、实施顺序、验收口径和风险门槛。  
> **编制日期**：2026 年 8 月 14 日  
> **信息来源**：《多 Agent 共享记忆设计方案》《财富管理 AI 系统：业务方向验证与实施建议》《长时运行 Agent 断点续跑设计方案》、`docs/PLAN.md`、`docs/ISSUES.md` 及当前实施记录。  
> **当前总决策**：先完成 P2“受控分析产品化、评估与前端闭环”，再实施 P3“最小共享工作记忆”，最后在 P4 围绕真实业务工作流实施“断点续跑”。不并行上全量共享记忆和全局 Checkpointer。

---

## 1. 一页结论

系统的正确定位不是“让大模型自由交易或自由查询数据”，而是建设一个以**权限、数据范围、规则、人工确认、审计、幂等和可恢复性**为底座的财富管理 AI 协作系统。

接下来必须遵循以下顺序：

```text
当前：P2 受控数据分析与产品闭环
        ↓
P3：最小共享工作记忆（先解决跨 Agent 协作摘要）
        ↓
P4：长时任务断点续跑（先选真实工作流试点）
        ↓
后续：扩展投后诊断、策略模板、人机协同和市场/投研能力
```

核心原则：

1. **先收敛业务价值，再扩大 Agent 能力。** 优先实现“推荐/建议可进入受控办理、投后诊断、人机协同”等可验证价值。
2. **先完成安全与评估基线，再共享上下文。** 共享记忆不得成为绕过权限、复制敏感数据或传播未确认判断的通道。
3. **先复用现有异步可靠性设施，再引入复杂恢复框架。** `AsyncTask + Outbox + Redis Streams + 状态机` 是 P4 的第一基础，不直接全局引入 LangGraph Checkpointer。
4. **模型负责理解、解释、规划和生成草稿；规则与受控服务负责权限、适当性、风控、交易和状态变更。**

## 2. 当前进度总览

### 2.1 已形成的系统基础

| 能力域 | 已完成或已验证的基础 | 当前意义 |
|---|---|---|
| Agent 编排 | Supervisor / Router、轻量 Planner、bounded ReAct、受控工作流边界 | 可以在统一入口下按权限路由客服、分析、投顾、风控和业务能力 |
| Agent 职责划分 | CustomerService、DataAnalysis、Advisor、Risk、Business、Admin 等角色边界已定义 | 避免把高风险操作放进自由对话 Agent |
| 权限与数据范围 | RBAC、Agent 能力前置过滤、`SubjectScopeService`、`PermissionScopedCache`、授权范围版本化 | 为客户经理/投顾授权客户范围、缓存隔离和后续共享记忆奠定基础 |
| 数据分析安全 | 批准模板、静态/动态目录白名单、参数边界、只读执行、拒绝与结构化澄清路线 | P2 的核心安全能力已具备，仍需产品化和评估固化 |
| 异步可靠性 | AsyncTask、事务内 Outbox、Redis Streams、Worker、重试/死信、pending/XCLAIM 相关能力 | P4 可在既有基础上实现任务快照与恢复，不必推倒重来 |
| 客服协同 | 转人工、会话状态、通知、WebSocket、工单补充材料/附件等闭环已持续建设 | P3 最适合从客服转人工摘要切入 |
| 回归验证 | FastAPI / PostgreSQL / Redis 的真实联调，多类权限与 Worker 回归；真实数据客服/Agent E2E 已有 15 项通过记录 | 已从纯单元阶段进入“后端、Worker、前端”共同验收阶段 |

### 2.2 当前阶段判断

- **P0/P1 基础设施与主业务骨架**：已具备可运行基础，仍保留生产化强化项。
- **P2 受控分析产品化**：当前主线，尚未完成，必须优先收尾。
- **P3 共享记忆**：设计已完成，实施尚未开始；仅推进最小工作记忆 MVP。
- **P4 断点续跑**：设计已完成，实施尚未开始；应先以一个真实长时流程为试点。
- **业务方向扩展**：应围绕“可执行建议、投后诊断、场景策略、人机协同、市场分析”分层推进，而非同时铺开。

### 3.1 P2：受控数据分析产品化（最高优先级）

| 编号 | 待办 | 目标与验收 |

| P2-2 | 前端结构化澄清展示 | 将参数缺失、参数越界、目录拒绝、权限拒绝等状态以明确文案、允许范围和下一步操作展示，不能以模糊失败或无关兜底结果替代。 |

| P2-6 | 评估集补齐 | 将参数澄清、目录拒绝、权限拒绝、subject 多义、正常模板执行等案例纳入统一数据集。 |

**P2 完成定义**：用户能在有权限的范围内自然语言提出分析需求；系统能安全选用批准模板、在必要时澄清；页面能呈现结果与解释；安全/权限/缓存/性能门槛能通过自动化评估证明。

### 3.2 与历史 ISSUE 的关系

历史 `PLAN.md` 与 `ISSUES.md` 中存在大量阶段性 `IN_PROGRESS` 记录，其中不少已被后续进度覆盖或已经完成。下一步不应按旧 ISSUE 的数量平均推进，而应做一次状态清理：

1. 将已由后续记录验证完成的历史项更新为 `RESOLVED` 并附验证证据；
2. 将仍有现实影响的项映射到 P2/P3/P4 的唯一待办编号；
3. 对开发环境、依赖下载、生产安全加固等非当前主线问题，单列为“发布前条件”，避免干扰功能主线；
4. 每完成一项，补充代码位置、回归命令/结果和未覆盖风险。

## 4. P3：最小共享工作记忆实施计划

### 4.1 P3 的目标和边界

P3 要解决的是跨 Agent 重复询问、重复检索、人工交接信息丢失的问题；**不是**建设全量组织知识库，也不是把全部对话、客户数据和模型推理内容复制到共享库。

首个场景建议：

```text
客服识别诉求/资料缺口
→ 写入可审计的交接摘要
→ 人工客服或投顾读取摘要继续处理
→ 风控/业务仅在权限允许时读取所需状态与引用
```

### 4.2 MVP 可写入与禁止写入

**允许写入：**

- 已确认的客户意图摘要；
- 当前任务/工单状态及引用 ID；
- 非敏感的规则结果摘要与 `rule_id`；
- 人工交接事项、资料缺口和来源消息/工单引用。

**禁止写入：**

- 模型私有推理链、完整 prompt、原始检索正文；
- 资产、持仓、交易、风险证据等原始敏感数据副本；
- 未确认的模型推断作为事实；
- 脱离当前权限上下文仍可使用的长期缓存结果。

### 4.3 P3 分步执行

1. **冻结无记忆基线**：以 P2 评估集记录当前任务成功率、澄清率、人工转接完整性、越权事件数、平均轮数。
2. **定义最小 Schema**：至少包含 `memory_type`、`scope`、`source_agent`、`source_ref`、`confirmation_status`、`permission_context_fingerprint`、`subject_scope_version`、`ttl/expires_at`、`audit_ref`。
3. **建立统一写入 API**：所有 Agent 通过统一服务写入；服务负责数据分类、脱敏、TTL、去重、审计和权限检查。
4. **建立统一检索 API**：读取时重新校验当前 RBAC、Agent capability、subject scope 和 TTL；检索结果只返回必要摘要与引用。
5. **接入首个场景**：先做客服转人工/工单交接摘要，再考虑投顾准备摘要。
6. **实现撤销与覆盖**：客户资料更新、授权撤销、人工纠正、TTL 到期均可使记忆失效或降级。
7. **进行有/无记忆对照评估**：只有在效率或交接质量有可量化收益且没有权限问题时，才扩大范围。

### 4.4 P3 验收门槛

- 共享记忆不会绕过 permission context 或 subject scope；
- 任一读写都有来源、时间、Agent、引用和审计记录；
- 可撤销、可到期、可覆盖；
- 敏感原始业务数据和模型推理链不进入共享池；
- 对照评估显示客服转人工或投顾准备的重复询问减少、信息完整性提升；
- 共享读取越权事件为 0。

## 5. P4：长时运行 Agent 断点续跑实施计划

### 5.1 目标和策略

P4 解决 Worker 崩溃、外部等待、批处理失败、人工审批等待等场景的安全恢复问题。第一原则是：**已完成步骤不可重复执行，外部写操作必须幂等，恢复前必须重新校验权限。**

第一阶段不全局启用 LangGraph Checkpointer，而是复用现有：

```text
AsyncTask + Outbox + Redis Streams + Worker + 状态机 + 审计
```

### 5.2 试点选择顺序

建议按风险和基础设施成熟度排序：

1. **知识导入/向量化任务**：已有 Worker 和多步骤处理，适合验证步骤级状态与恢复；
2. **AML 批次扫描**：已有批次/补跑基础，适合验证客户级断点和幂等；
3. **人工审批或客服转人工等待**：适合验证外部等待令牌和回调唤醒；
4. **投顾诊断草稿/风险调查报告**：可恢复草稿步骤，但不得自动执行高风险动作。

### 5.3 最小恢复快照

```text
workflow_id
workflow_type
step_name
status
input_fingerprint
permission_context_fingerprint
subject_scope_version
completed_output_references
idempotency_key
resume_token_reference
expires_at
```

不保存完整模型推理链、原始客户数据副本、可脱离权限重放的敏感请求体或结果缓存。

### 5.4 P4 分步执行

1. 选择一个试点并明确 SLA、最大运行时长、失败上限和人工介入点；
2. 为每一步定义状态、输入指纹、输出引用和幂等键；
3. 在任务状态变更时持久化安全快照；
4. Worker 启动或定时恢复程序扫描可恢复任务；
5. 恢复前重新校验角色、Agent 能力、subject scope 和相关业务状态；
6. 对外部等待设计回调 token/状态机，不能阻塞 Worker；
7. 覆盖崩溃、重复投递、重复回调、超时、权限变化、人工取消和过期重放等测试；
8. 试点稳定后，再评估是否仅对特定 LangGraph 流程引入持久化 Checkpointer。

### 5.5 P4 验收门槛

- Worker 崩溃后从安全断点恢复；
- 已完成步骤与外部写操作不重复执行；
- 权限或授权范围变化后，旧快照不能越权恢复；
- 外部等待不占用 Worker；
- 恢复、失败、取消和重放全部审计可追溯；
- 正常路径和恢复路径均有 HTTP、Redis、Worker 回归。

## 6. 业务能力扩展路线

在 P2/P3/P4 稳定后，按业务价值推进以下方向：

| 优先级 | 方向 | 推荐首个交付 | 关键边界 |
|---|---|---|---|
| P0（业务价值） | 推荐 → 可执行策略 | 建议草稿、适当性结果、风险提示、跳转受控业务流程 | AI 不直接下单；适当性和风控由规则/服务裁决 |
| P1 | 投后诊断 | 客户资产/风险/偏离诊断报告草稿 | 使用授权范围内数据，诊断结论需证据和可解释性 |
| P2 | 策略模板 + 场景化投资 | 目标导向模板、风险等级匹配、方案对比 | 不能将营销偏好伪装成适当性结论 |
| P2 | 人机协同 | 客服/投顾/风控交接、审批和补件闭环 | 人工确认点和工单状态机必须清晰 |
| P3 | 市场分析 + 投研 | 市场分析卡片、研究摘要和风险提示 | 不将一般信息包装成个性化投资建议 |

## 8. 质量门槛、风险与暂停条件

| 阶段 | 必须持续满足 | 触发暂停/回退的条件 |
|---|---|---|
| P2 | 无自由 SQL；目录/字段/subject scope 均受控；缓存隔离；结果可解释 | 出现越权查询、跨用户缓存命中、敏感字段泄露或安全事故 |
| P3 | 读写均经过权限与范围校验；可撤销/过期；有无记忆评估可比较 | 共享记忆绕过权限、无法删除/撤销、敏感数据复制、评估无实际收益 |
| P4 | 幂等、可恢复、重新鉴权、外部等待非阻塞 | 恢复导致重复外部写操作、权限变化后仍可恢复旧结果、Worker 长时间阻塞 |

## 11. 结语

当前系统已经跨过“只有单一聊天能力”的阶段，具备向受控多 Agent 财富管理平台演进的关键基础。后续成功与否不取决于增加多少 Agent 或增加多少记忆，而取决于是否始终保持以下纪律：

```text
权限先于路由；
范围先于检索；
规则先于建议；
确认先于执行；
幂等先于恢复；
审计贯穿读写与状态变化。
```

据此，近期唯一主线是扎实完成 P2；P3 和 P4 按最小可验证范围渐进落地，避免过早扩展复杂度。

## 12. 交易自动化路线：自然语言下单的合规受控闭环

### 12.1 决策结论

系统应将“推荐产品后，用户通过自然语言发起交易”纳入后续业务主线，但严格定义为：**AI 辅助的受控交易自动化**，而不是 AI 无确认自主交易。

允许的业务模式是：AI 理解客户的交易意图、收集并校验参数、生成订单草稿、解释适当性和风险结果；只有在用户明确确认、身份与风险门禁通过后，由确定性的订单/交易服务提交订单。

统一边界如下：

> AI 不拥有无确认、无规则约束的自主下单权；但可以在用户授权和明确确认后，将自然语言意图转化为受控订单草稿，并调用确定性交易服务完成执行。

### 12.2 标准交易链路

```text
用户自然语言提出交易意图
  ↓
Supervisor / BusinessAgent 识别交易类型和必填参数
  ↓
缺参数时返回结构化澄清
  - 产品
  - 买入 / 赎回 / 转换等交易方向
  - 金额或份额
  - 资金账户或持仓账户
  - 交易规则需要的期限、分红方式等参数
  ↓
确定性预检
  - 产品状态与交易窗口
  - 客户适当性与风险等级
  - 风险预警、限额、持仓/余额、AML/黑名单等
  - 账户权限与客户确认资格
  ↓
生成订单草稿（不执行）
  ↓
展示确认页
  - 产品、风险等级、金额/份额、费用和确认规则
  - 适当性结果、风险提示和预警/人工审核原因
  - 撤销/不可撤销规则及草稿有效期
  ↓
用户明确确认
  ↓
按风险/金额分级执行二次认证或人工审核
  ↓
确定性 Order Service 创建并提交订单
  ↓
幂等处理、风控复核、Outbox 事件、审计日志、订单状态通知
```

### 12.3 Agent 与确定性服务的职责边界

| 环节 | AI / Agent 可做事项 | 必须由确定性服务或规则负责的事项 |
|---|---|---|
| 意图理解 | 识别“申购、赎回、转换、撤单、查询订单”等意图 | 对交易类型、账户权限和业务状态作最终判定 |
| 参数收集 | 提示缺少的产品、金额、份额、账户等参数；展示受控选项 | 不得猜测或擅自填入关键交易参数 |
| 推荐与解释 | 展示产品对比、风险说明、适当性提示和建议草稿 | 不得承诺收益，不得覆盖适当性/风控结论 |
| 合规预检 | 编排并解释规则服务结果 | 适当性、额度、AML、黑名单、交易窗口、产品状态的最终裁决 |
| 用户确认 | 组织确认摘要、解释风险和下一步 | 确认令牌签发、有效期、二次认证、撤销规则 |
| 订单执行 | 在确认后调用受控业务接口 | 订单创建、资金冻结/扣划、提交、撤销、状态迁移、重试与补偿 |
| 状态通知 | 解释订单状态、提醒补件或人工审核 | 订单事实写入、审计事件和最终状态维护 |

### 12.4 订单状态机建议

交易自动化必须以订单状态机而不是聊天上下文驱动。建议的最小状态包括：

```text
draft
→ collecting_parameters
→ precheck_pending
→ precheck_failed / needs_manual_review
→ awaiting_user_confirmation
→ confirmation_expired / user_cancelled
→ submitting
→ submitted
→ processing
→ confirmed / rejected / failed / cancelled
```

状态变化必须记录操作主体、订单草稿版本、规则/风险校验结果、确认信息、时间和关联审计记录。聊天会话只能影响草稿收集，不能绕过状态机直接修改业务事实。

### 12.5 必须实现的合规与安全控制

1. **确认与草稿强绑定**：用户确认须绑定订单草稿版本、关键参数哈希、适当性结果版本、风险规则版本和有效期；任一关键内容变化，旧确认立即失效。
2. **关键参数必须明确**：产品、交易方向、金额/份额、账户、赎回范围等，不得由模型自行猜测；可由用户输入、选择或在确认页逐项确认。
3. **提交前实时复检**：即使草稿预检通过，在提交前仍须重新校验余额/持仓、产品状态、交易窗口、额度、风险预警、适当性和 AML 状态。
4. **高风险分级控制**：高金额、风险等级临界、不适配但客户坚持、风险预警未闭环、异常频繁交易、跨账户操作等，须进入二次认证、人工审核或直接拒绝。
5. **幂等与防重复提交**：每笔订单生成 `idempotency_key`；确认、提交、重试、回调等操作均需防重。
6. **全程审计**：自然语言原始输入的最小必要留痕、意图解析结果、参数补充、规则校验、确认、认证、提交、重试、拒绝、人工介入及通知，均应有可追溯审计记录。
7. **不以模型结果代替规则结果**：模型可以说明“为什么被拒绝/需补充”，但不能自行解除风控、适当性、额度或 AML 限制。

### 12.6 实施顺序调整

交易自动化应作为 P2 后续最优先的业务闭环之一，与投后诊断、人机协同并列推进。建议路线调整为：

```text
当前 P2：受控数据分析、评估与前端闭环
  ↓
交易自动化 MVP：
自然语言交易意图
→ 参数澄清
→ 订单草稿
→ 适当性/风控预检
→ 用户确认/二次认证
→ 确定性下单与状态通知
  ↓
P3：共享工作记忆
（传递已确认的交易意图、补件事项、工单状态和人工交接摘要）
  ↓
P4：长时任务恢复
（交易审批等待、AML 复核、外部确认、失败重试等流程）
```

### 12.7 交易自动化 MVP 的交付清单

- [ ] 自然语言交易意图识别与交易类型路由；
- [ ] 结构化交易参数 schema、缺参澄清和受控选项展示；
- [ ] 订单草稿模型、版本控制与草稿有效期；
- [ ] 适当性、风控、额度、AML、产品状态、账户权限的预检聚合服务；
- [ ] 用户确认页与确认令牌；
- [ ] 风险/金额分级的二次认证和人工审核入口；
- [ ] 确定性下单服务、幂等键、提交前复检和 Outbox 事件；
- [ ] 订单状态机、通知、撤单/取消边界和审计日志；
- [ ] 正常、拒绝、超时、重复提交、规则变化、权限变化和 Worker 重试的端到端回归。

### 12.8 MVP 验收标准

- 用户可用自然语言发起申购、赎回或转换意图，并完成安全的参数补充；
- 系统只生成订单草稿，未经用户明确确认不能提交；
- 确认后仍执行实时合规与风险复检；
- 任一适当性、风控、额度、AML 或权限限制均能阻断执行并给出可解释原因；
- 相同确认或请求重复发送不会产生重复订单；
- 订单全生命周期与所有 AI 辅助步骤均可审计追溯；
- Agent 不能通过对话绕过订单状态机、确认流程或确定性领域服务。

## 13. 统一 Agent 窗口产品决策：客服、推荐与下单不再分散到侧边栏

### 13.1 决策（2026 年 8 月 14 日）

客户侧不再将“智能客服”与“AI 辅助申购”作为客户中心侧边栏中的独立业务模块。后续所有面向客户的 Agent 能力统一收敛到全局 **Agent 气泡窗口**：

```text
客户任意页面
→ 点击统一智能助手气泡
→ 对话中识别意图、澄清参数、调用受控 Agent / Service
→ 在同一窗口展示推荐、订单草稿、风险提示与确认组件
→ 用户明确确认后调用确定性业务服务
```

这意味着“客服”不是单独的页面或左侧菜单，而是统一 Agent 窗口中的一个能力；投顾推荐、风险解释、数据查询、业务办理和后续其他 Agent 同样在这个窗口内以路由结果和结构化卡片的形式呈现。

### 13.2 客户中心调整

- 删除客户中心侧边栏中的“智能客服”入口；
- 删除客户中心侧边栏中的“AI 辅助申购”入口；
- 不再在客户中心内展示独立的 `NaturalLanguageTradeView`；
- 保留客户中心的资产、订单、工单、业务办理、风险测评等事实型/管理型页面；
- 全局 `AgentBubble` 继续在客户已登录页面中提供统一入口。

### 13.3 统一窗口内的交互边界

| 能力 | 在 Agent 窗口中的表现 | 执行边界 |
|---|---|---|
| 客服知识与流程 | 文本回答、证据、转人工 | 只读检索与工单/人工协同 |
| 产品推荐 | 推荐卡片、适当性说明、风险提示 | 规则服务决定是否适配，模型只解释与组织 |
| 自然语言申购 | 参数澄清 → 订单草稿卡片 → 明确确认控件 | 确认后只创建订单，不能直接成交 |
| 风险解释 | 风险状态、限制原因、下一步建议 | 不允许 Agent 解除风控限制 |
| 订单/工单查询 | 结构化事实卡片、状态解释 | 仅查询当前客户授权数据 |
| 后续 Agent | 使用统一路由、同一会话和结构化响应渲染 | 必须通过 capability、权限、scope、审计和状态机 |

### 13.4 实施路线调整

此前独立的 AI 辅助申购页面作为前端原型保留代码参考，但不作为客户入口继续扩展。下一阶段改为：

1. 将 `AgentBubble` 的响应渲染升级为“消息 + 结构化 action card”；
2. 当 Supervisor/Biz Agent 识别到申购意图时，在气泡中调用现有自然语言草稿 API；
3. 在气泡中渲染草稿预览、适当性说明、风险提示、有效期与明确确认复选框；
4. 由气泡提交 `draft_id + confirmation_token + idempotency_key`，后端仍执行令牌校验和实时复检；
5. 产品推荐在同一窗口返回推荐卡片，用户点击“准备申购”后把已选产品带入草稿参数澄清；

## 14. 意图理解升级决策：标准模板 + 结构化大模型兜底 + 安全决策

### 14.1 当前问题

当前第一层意图识别以关键词、正则、显式实体提取和固定路由规则为主。该机制适合明确且高风险的表达，例如订单号、工单号、申购、赎回、转人工和明确金额；但不能单独覆盖真实客户的复杂自然语言。

当前已暴露的风险包括：

- 语序变化导致产品/金额实体解析不稳定；
- “推荐并下单”“先看不要直接买”“合适再帮我准备”等多意图、条件和否定表达难以只靠关键词覆盖；
- 指代、上下文、省略、模糊金额、风险偏好和期限约束无法可靠映射；
- 现有 E2E 主要覆盖规则容易命中的标准表达，测试通过不等于真实自然语言鲁棒。

### 14.2 目标架构

后续不废弃规则，而是采用以下混合架构：

```text
规则/模板高置信度识别
→ 结构化 LLM 意图兜底
→ 规则、模型、会话、权限合并决策
→ ExecutionPlan
→ 确定性服务/状态机/用户确认
```

分层职责：

1. **规则和标准模板**：识别订单号、工单号、金额、明确申购/赎回/人工等高风险表达；高置信度时直接进入受控模板。
2. **结构化 LLM 兜底**：仅在规则低置信、表达复杂、多意图、含指代/否定/条件或上下文依赖时启用；输出受 JSON Schema 约束的候选意图、实体、缺失参数、否定/确认信号和置信度。
3. **Intent Policy Resolver**：合并规则结果、模型候选、会话状态、客户记忆摘要、capability、RBAC、subject scope 和业务规则，输出可审计 ExecutionPlan。
4. **确定性执行层**：适当性、风控、订单、资金、确认、幂等、审计和状态机由领域服务完成，模型不能绕过。

### 14.3 标准任务模板

首批模板建议：

```text
T1 纯信息查询
T2 客户产品推荐
T3 推荐后准备申购
T4 明确申购草稿
T5 订单状态解释
T6 风险限制解释
T7 人工转接
T8 多意图查询 + 建议
T9 修改现有草稿
T10 取消/撤销草稿
```

例如 T3“推荐后准备申购”的明确边界：模型可识别客户风险偏好、金额、期限和“不要直接买”等约束；系统必须展示推荐、要求客户明确选产品、必要时澄清精确金额，随后才生成草稿。禁止自动选择产品、自动提交订单或覆盖适当性/风控结论。

### 14.4 结构化模型输出要求

模型只输出结构化理解，不输出可直接执行的业务命令，例如：

```json
{
  "primary_intent": "recommend_then_purchase_draft",
  "secondary_intents": ["risk_preference_expression"],
  "entities": {"amount": 1000, "product_name": null, "risk_preference": "low"},
  "constraints": ["must_not_submit_without_confirmation"],
  "missing_required_fields": ["selected_product"],
  "requires_clarification": true,
  "confidence": 0.87,
  "explicit_confirmation": false
}
```

模型输出必须经 Pydantic/JSON Schema 校验；模型理解不等于业务许可。

### 14.5 复杂自然语言评测集

后续评测不只测试关键词命中，而应覆盖：

- 语序变化；
- 省略与指代；
- 推荐 + 交易；
- 否定和条件；
- 多意图；
- 上下文依赖；
- 模糊金额、风险偏好、期限约束；
- 对抗性或越权请求。

每条样本至少验证：主/次意图、实体、否定条件、澄清、是否错误创建草稿、是否错误提交订单、权限范围、审计和风险提示。

### 14.6 实施顺序

```text
P2.1 建立复杂中文自然语言评测集
P2.2 建立标准任务模板和 StructuredIntent Schema
P2.3 建立规则置信度与 LLM fallback 接口
P2.4 建立 IntentPolicyResolver
P2.5 将复杂“推荐并下单”接入统一 ExecutionPlan
P2.6 将正确率、误执行率、错误澄清率、越权数纳入 CI
```

当前先实施 P2.1/P2.2，先建立可量化基线，再接入实际模型调用。
