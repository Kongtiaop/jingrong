# Agent 功能、业务映射与设计原因总览

- 写入时间：2026-08-13（Asia/Shanghai）
- 文档状态：当前实现与设计基线
- 适用范围：主 Agent、子 Agent、工具、数据目录、权限、缓存、评估与审计

## 1. 文档目的

本文集中说明系统中各 Agent 当前负责什么业务、为什么采用当前执行范式、解决了什么业务问题，以及哪些能力明确不能交给模型自由决定。

本文回答四个问题：

1. 用户请求会被哪个 Agent 处理？
2. 这个 Agent 为什么使用 ReAct、规则或工作流？
3. 它解决了什么业务痛点？
4. 它的权限、安全和人工接管边界是什么？

本文是功能与业务设计总览；具体实施计划、问题记录、测试命令和文件变更分别维护在：


## 2. 总体范式

当前系统采用：

> 权限感知的主 Agent 轻量 Plan + 分层子 Agent 执行 + 统一审计与评估。

整体链路：

```text
用户请求
  ↓
身份/角色/权限识别
  ↓
AgentCapabilityRegistry 过滤可用 Agent
  ↓
CustomerIntentPlanner 生成轻量 Plan
  ↓
每个任务标记 execution_mode
  ├─ bounded_react
  └─ controlled_workflow
  ↓
子 Agent / Tool 执行
  ↓
权限二次校验、数据范围校验、审计、结果汇总
  ↓
回答、澄清或人工接管
```

主 Agent 不直接持有高风险写操作能力。它负责理解、规划、路由和汇总；最终业务事实、权限、金额、适当性、风控和状态转换由后端确定性服务负责。

## 3. 执行模式分层

### 3.1 bounded_react：受限 ReAct

适用于低风险、只读、需要多跳检索或解释的任务。

约束：

- 最大 3 轮；
- 最大 3 次工具调用；
- 工具白名单；
- 默认只读；
- 只有低置信结果允许一次查询精炼；
- 必须携带 evidence 状态；
- 失败时澄清或转人工；
- 不记录模型私有思维链。

### 3.2 controlled_workflow：受控工作流

适用于数据分析执行、资金/订单/业务操作、风险处置、权限修改等高约束任务。

典型链路：

```text
权限
→ 参数
→ 规则
→ 风险检查
→ 用户确认/审批
→ 状态机
→ 幂等执行
→ 审计/Outbox
```

这些任务不采用自由 ReAct，因为必须可预测、可复现、可审批、可审计、可回滚。

### 3.3 Plan + Rules：决策辅助

适用于适当性判断、风险分级、产品匹配等任务。模型可以解释和组织证据，但最终结论由适当性服务、风险规则或评分服务输出。

## 4. Agent 总览

| Agent | 主要业务 | 当前执行模式 | 主要输出 | 禁止事项 |
|---|---|---|---|---|
| Supervisor / 主 Agent | 统一理解、权限过滤、轻量规划、路由、汇总 | Lightweight Plan | Plan、路由、澄清、汇总结果 | 不能绕过权限调用内部 Agent；不直接写资金/业务事实 |
| CustomerServiceAgent | 客服问答、政策/流程/公司信息、客户只读事实、人工转接 | bounded_react + 受控只读 Tool | 答案、证据、澄清、handoff | 不直接转账、赎回、下单、改库 |
| DataAnalysisAgent | 内部指标、批准模板、目录驱动分析 | controlled_workflow | 结构化结果、query_plan、chart_spec、审计 | 不执行自由 SQL、不查敏感字段、不越权 |
| AdvisorAgent | 投顾信息收集、产品解释、建议草案 | Plan + Rules / 受限只读推理 | 建议草案、证据、风险提示 | 不替代适当性规则、不直接下单 |
| RiskAgent | 风险解释、告警查询、风险分级和处置辅助 | Plan + Rules / controlled_workflow | 风险等级、理由、处置建议、工单 | 不绕过规则直接改变风险事实 |
| BusinessAgent | 转账、赎回、申购、下单等业务草稿和确认 | controlled_workflow | 草稿、确认请求、状态变化 | 不在客服对话中直接执行资金操作 |
| AdminAgent | 后台管理、角色、权限和配置维护 | controlled_workflow | 管理变更、审计事件 | 不允许普通用户使用；不能无审计修改权限 |

## 5. 主 Agent / Supervisor

### 业务问题

不同请求属于不同业务域：

```text
“风险预警有多少” → 风控/数据分析
“我要赎回” → 业务操作
“赎回需要什么条件” → 客服知识
“什么产品适合我” → 投顾/适当性
“订单什么时候确认” → 客户订单查询
```

### 设计原因

先做能力过滤再做语义路由：

```text
用户角色/权限
→ available_agents / denied_agents
→ 只在可用 Agent 白名单中路由
```

这样可以减少无效调用、避免内部 Agent 暴露、集中权限决策，并让审计可以解释“为什么没有调用某个 Agent”。

### 解决的业务问题

- 客户不能误用内部风控和数据分析能力；
- 一个入口可以承载客服、投顾、风控、业务和分析请求；
- 多任务请求可以拆分、排序并处理依赖；
- 参数不完整时可以澄清；
- 连续澄清失败可以转人工。

## 6. CustomerServiceAgent

### 业务范围

- 公司信息与公司业务；
- 产品政策、风险政策、办理流程；
- FAQ；
- 客户订单、工单、资产、风险限制等只读事实；
- 客服知识检索和人工转接。

### 为什么使用 bounded_react

客服问题经常需要多跳检索：

```text
检索政策
→ 发现缺少适用条件
→ 补充检索产品说明
→ 结合客户只读事实
→ 回答并提供证据
```

完全固定的单步路由难以覆盖这种情况，但自由 ReAct 又会带来无限循环、工具越权和成本不可控。因此采用有预算的只读 ReAct。

### 工具边界

当前只读工具包括：

```text
get_my_workorder_status
get_my_order_status
get_my_asset_summary
get_my_risk_restriction
get_product_status
search_customer_knowledge
explain_order_status
explain_workorder_status
```

### 解决的业务问题

- 客户可以用自然语言咨询政策和流程；
- 客服回答带知识证据；
- 查不到资料时不会编造，而是澄清或转人工；
- 客服可以导航到业务页面，但不会在对话中直接执行资金操作。

## 7. DataAnalysisAgent

### 业务范围

主要服务内部角色：

```text
风险管理
运营审核
客户经理
投顾
审计
超级管理员
```

典型问题：

```text
现在有多少风险预警？
待审核订单有多少？
本月待审核订单金额是多少？
查询客户过去三个月的净资产趋势。
查看尚未结案的高风险预警。
```

### 为什么不是自由 NL2SQL

自由 SQL 会引入：

- 表越权；
- 字段越权；
- 敏感信息泄漏；
- 写 SQL 或多语句执行；
- 全表扫描和高成本查询；
- 结果口径不可审计。

当前采用：

```text
自然语言
→ 已批准模板匹配
→ 数据目录文本/pgvector 召回
→ 模板表字段白名单
→ 目录动态候选白名单
→ 参数 Schema 校验
→ SELECT-only 校验
→ 只读执行 + LIMIT
→ query_plan/chart_spec/审计
```

### 数据目录的业务作用

`DataCatalogTable` 存储表的业务用途、粒度、使用指导和权限；`DataCatalogColumn` 存储字段业务含义、单位、敏感性、可查询性和聚合能力；`DataCatalogRelation` 存储连接关系；`DataCatalogExampleQuery` 存储批准问题和模板。

它将技术数据库翻译成业务语义层，避免模型只看到物理表名而误用数据。

### 解决的业务问题

- 内部人员可以用自然语言查询固定分析口径；
- 风险和运营人员可以快速获得只读指标；
- 表和字段使用口径可解释；
- 敏感字段、不可查询表和未批准模板自动拒绝；
- 结果包含图表规格，便于前端展示。

### 当前安全边界

- 客户不能调用 DataAnalysisAgent；
- 不执行用户直接提供的 SQL；
- 只允许 approved + active 模板；
- 表和字段必须通过模板白名单与目录白名单；
- 字段必须 queryable 且非 sensitive；
- 结果最多 100 行；
- 参数必须符合模板 `metadata_json.parameters`；
- 记录受控审计，不记录原始敏感 SQL/参数值。

## 8. AdvisorAgent

### 业务范围

- 读取客户风险等级、资产、持仓和产品资料；
- 解释产品特点和风险；
- 形成产品建议草案；
- 调用适当性规则服务进行匹配。

### 为什么不是让模型直接推荐

产品推荐涉及：

```text
客户风险等级
产品风险等级
投资期限
流动性
客户资产和经验
账户限制
```

这些条件必须由确定性适当性规则核验。模型负责解释和组织证据，不负责绕过规则决定“可以买什么”。

### 解决的业务问题

- 推荐结果可解释；
- 客户知道匹配/排除原因；
- 推荐不会直接创建订单；
- 适当性和交易执行解耦。

## 9. RiskAgent

### 业务范围

- 查询风险预警；
- 解释风险限制；
- 风险等级和规则说明；
- 生成处置建议或工单线索。

### 设计原因

风险等级、预警状态和处置结果需要规则、证据和人工复核。模型可以帮助检索与解释，但不能自行改变风险事实或关闭预警。

### 解决的业务问题

- 风险人员更快定位告警；
- 风险原因可解释；
- 处置动作有审计；
- 高风险动作保留人工确认。

## 10. BusinessAgent

### 业务范围

- 赎回；
- 转账；
- 下单/申购；
- 业务草稿、确认和状态查询。

### 设计原因

资金和交易动作必须走：

```text
草稿
→ 参数完整性
→ 适当性/风险检查
→ 用户确认
→ 幂等提交
→ 状态机
→ 审计/Outbox
```

当前客服入口只返回业务页面导航和确认提示：

```json
{
  "status": "needs_confirmation",
  "confirmation_required": true,
  "executed": false
}
```

### 解决的业务问题

- 客户可以自然语言表达办理意图；
- 系统不会在聊天中误执行资金操作；
- 业务页面负责金额、账户、产品和最终确认；
- 后端保留幂等、状态、审计和回滚边界。

## 11. AdminAgent

### 业务范围

- 用户、角色、权限管理；
- 数据目录维护；
- 审计查询；
- 配置与后台操作。

### 设计原因

权限修改会影响所有缓存、Agent 能力和数据范围，因此必须是管理员工作流，不能由普通对话 Agent 自由执行。

角色/权限更新后会递增：

```text
wm:permission-context-version:{user_id}
```

使权限敏感缓存生成新 key。

## 12. 权限与数据目录基础设施

### AgentCapabilityRegistry

负责 Agent 级别权限：

```text
available_agents
denied_agents
```

### PermissionScopedCache

负责缓存级别权限：

```text
PermissionContext
→ permission fingerprint
→ Redis key
```

缓存不是普通性能优化，而是数据访问链路的一部分。

### 数据目录

负责语义级别权限和治理：

```text
表用途
字段含义
敏感性
可查询性
角色
关系
批准示例
```

## 13. 审计与评估

### 审计

记录：

- Agent/模板执行或拒绝；
- 执行模式；
- 模板 ID；
- 受控拒绝原因；
- 权限缓存版本变更相关事件；
- bounded ReAct 工具调用摘要。

不记录：

- 模型私有思维链；
- 用户完整敏感问题；
- 完整 SQL 参数；
- 客户资产和检索正文。

### P2 六维评估

```text
语法正确率
语义准确率
拒答率
澄清触发率
P95 延迟
安全事故数
```

目前已具有离线与真实 HTTP 评估，覆盖正常分析、直接 SQL、危险 SQL、客户越权、歧义澄清、模板状态、目录表/字段状态和参数边界。

## 14. 当前已解决的问题


## 16. 设计原则总结

1. 权限先于 Agent 路由；
2. 低风险解释可以使用 bounded ReAct；
3. 高风险业务使用 controlled workflow；
4. 模型负责理解、规划和解释，不负责自行改变业务事实；
5. 数据目录是 NL2SQL 的语义和权限边界；
6. 缓存也必须权限感知；
7. 拒答、澄清、延迟和安全事故都必须可评估；
8. 先建立评估尺子，再接入记忆层个性化。


## 17. 2026-08-13：客户经理/投顾的授权客户范围

`authorized_scope_only` 参数现在不再只依赖当前用户 ID。`SubjectScopeService` 根据有效的 `CustomerAdvisorAuthorization` 读取授权客户集合，过滤有效期、状态和撤销时间；DataAnalysisAgent 只接受集合内的显式客户 subject，多客户集合未指定 subject 时要求澄清/拒绝。

这解决了“客户经理可以查看被分配客户，但不能查看未分配客户”的业务权限问题。
