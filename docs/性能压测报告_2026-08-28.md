# 性能压测报告（2026-08-28 · 本地单节点）

> 环境：HP123（Ryzen 9 8945HX / 32GB / RTX 5060 8GB），服务跑在 Docker，API `http://127.0.0.1:8010`（**单 uvicorn worker**），PG 16.14（5433）、Redis 6380。
> 工具：自研异步压测 `scripts/loadtest_api.py`（httpx, 100% Python，无第三方压测依赖）。
> 说明：这是**本地单节点基准**，不是生产集群压测；结论是"单节点正确性已验证、性能有明确瓶颈与优化方向"。

### 1.1 修正记录：之前"4 worker 无提升"是测错了实例

早前一轮"多 worker 无提升"的结论**不成立**——当时占 8010 的是 **p0 compose 的旧单 worker 容器**（`wealth-p0-api-1`，3 小时前创建、未带 `--workers 4` 与新代码），我压测到的是它，不是真正的 4-worker 实例。修正为：**真实 4 worker + 两项优化后，吞吐提升 2.5-4.3 倍，P50 大幅回落**。

> 教训：压测前必须确认被测实例就是目标配置（worker 数、代码版本、端口归属）。两个 compose（`docker-compose.yml` 与 `docker-compose.p0.yml`）共享 8010，容易测到旧实例。

## 2. 关键发现与瓶颈定位

### 2.1 单 uvicorn worker 是最大瓶颈
`docker-compose.yml` 的 API 启动命令是：
```yaml
command: ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```
**没有 `--workers`，即单进程单事件循环。** 这是吞吐天花板：DB 型端点 ~90-150 RPS，health 在 200 并发就饱和 ~420 RPS，高并发下 P95 明显劣化（排队/事件循环抢占）。

### 2.2 health 端点每次 ping PG+Redis，不是"纯健康检查"
`/api/v1/health` 走 `HealthService`，每次请求都探测 PostgreSQL + Redis 连通性——所以它并不"零成本"，200 并发时也会饱和。这解释了 health 在 200 并发 P95 达 1.5s。

### 2.5 根因：`profile/me` 每次请求 ~10 次串行 DB 往返（N+1 式）
`/profile/me` 不是一次查询，而是**每次请求串行执行约 10 次 DB 往返**（都 `await` 排队，延迟相加）：
1. **鉴权** `current_user`：从 DB 重载用户 + 角色 + 权限（selectinload）≈ 2-3 次；
2. `uow.profiles.get`：1 次；
3. `AssetSummaryService.latest_or_derived` → `calculate(revalue=True)`：
   - `revalue_user` 重估持仓（**读+写**，最贵）；
   - `account.get_by_user`、`holdings.sum_market_value`、`assets.latest`：3 次；
   - 当日快照查询：1 次；
   - **≈5-6 次，且 `calculate` 在快照查询之前无条件执行**——即使当日快照已存在也每次全量重算；
4. 持仓列表：1 次；
5. `_risk_operation_for_user`（account + risk_alert）：2 次。

**这就是单请求 ~117ms 的根因**，也是 `--workers` 加不上去提升的原因——瓶颈在串行 DB 往返，不在 CPU 计算。修复 = `latest_or_derived` **先查当日快照、有则复用**（砍掉每次重算的多次往返）+ health 缓存 + 多 worker。

### 2.3 recommendations 每次跑全产品适当性
`/api/v1/profile/me/recommendations` 对全部在售产品执行 `SuitabilityService` 计算，天然较重；30 并发即 ~94 RPS、P50 283ms。

### 2.4 高并发下 P95 劣化符合"单 worker + 连接池排队"
- 100 并发混合：P50 606ms / P95 1049ms（请求排队）
- health 200 并发：P50 293ms / P95 1517ms（事件循环饱和）

这属于**容量性劣化**（更多请求排队等待），不是正确性错误；0 错误说明请求最终都被处理。

## 3. 数据量扩展（已完成 50k）

通过 `scripts/loadtest_seed_large.py` 向 PG 灌入 **50,000** 个合成客户（users+profile+asset+risk），实测查询延迟：

| 查询 | 规模 | P50 | P95 |
|---|---|---|---|
| `GROUP BY customer_tier`（扫描 customer_profile） | 50k | 9.06ms | 11.97ms |
| `avg(total_asset)` 聚合 | 50k | 10.91ms | — |
| PK join 点查（profile+asset） | 50k | 0.44ms | 0.96ms |

**结论：数据量从 5k → 50k，查询不退化**——扫描类 10ms 级、索引点查 sub-ms，无执行计划劣化迹象（索引被正确使用）。

复现：`conda run -n langchain_env python -m scripts.loadtest_db_bench`

## 4. 优化建议（按杠杆大小 · 已按单机实测修正）

| 优先级 | 动作 | 预期收益 |
|---|---|---|
| **P0** | **减少每请求 DB 往返 / 缓存鉴权**（`profile/me` 单请求成本≈117ms 主要来自多次 DB + 鉴权重载用户） | 直接压下单请求延迟，最有效 |
| P0 | **health 减负**：去掉每次 PG/Redis ping，或降为进程存活检查 | health 从 ~420 RPS 上限释放 |
| P1 | **recommendations 缓存适当性结果**（短 TTL） | 重计算省掉，吞吐显著提升 |
| P1 | asyncpg 连接池调优（pool_size/overflow） | 减少高并发下 DB 连接排队 |
| P2 | **多 worker / 多节点**：`--workers 4` 已配并**单机实测有效**（混合 100 并发 RPS 151→625） | 已落地；更大规模需独立压测机/多节点 |
| P2 | 生产级：多节点 + 负载均衡 + 真实客户端分布 + 百万级数据 | 验证集群容量 |

## 5. 诚实结论

> **"单节点基准"：正确性已通过（0 错误），50k 数据量查询不退化（扫描 10ms 级、索引点查 sub-ms）。优化前单 worker：DB 型端点 ~90-150 RPS、health ~420 RPS。优化后（4 worker + health 缓存 + asset 快照复用）：混合 100 并发 RPS 151→625（4.1x）、P50 606→98ms；health 200 并发 RPS 421→1052（2.5x）、P95 1517→306ms；profile/me 50 并发 RPS 95→406（4.3x）、P50 457→46ms。真正杠杆是**多 worker + 减少每请求 DB 往返 + health 缓存**。生产级 QPS 仍需多节点确认。**

### 5.1 强幂等性（数据一致性 · 资金安全）已被压测验证

本系统"安全"的核心是**强幂等性**（防重复下单/防资金重复副作用），机制为**唯一索引兜底 + 行锁 + 确定性幂等键**三层，并发下验证通过：

- 并发幂等下单（TESTS.md TEST-0091/0092）：30 请求 0 失败，同一幂等键只产生 1 单，成功 201 / 竞争 409，**无重复订单、无 500**。
- MySQL 并发幂等（TEST-0100）：5 并发 → 仅 1 创建，其余 4 撞唯一索引抛 IntegrityError。
- 同一幂等键并发 HTTP 竞态（TEST-0203）：并发契约通过。

**结论**：系统在**吞吐**（优化后数倍提升）与**强幂等/数据一致性**（并发 0 重复）两个维度都有实测支撑——即"兼顾速度与强幂等"。

### 5.2 容量外推：50k 用户适配（工程估算，非实测）

按 50k 用户、20% DAU（≈10k 日活）、每人每天 30 请求、峰值小时占日流量 40% 且突发 ×3 反推，**峰值需求 ≈ 100 req/s**。

| 配置 | 估算混合 RPS | 相对 50k 需求 |
|---|---|---|
| 本地单节点（4 worker） | ~600（实测） | ~6x 富余 |
| 生产单节点（8 vCPU / 8 worker / SSD） | ~1200-2000（估算） | 12-20x 富余 |
| 生产 2-3 节点 + LB | ~2500-5000+（估算） | 25-50x 富余 |

> 边界：估算基于"吞吐≈核数×单核效率、瓶颈在 CPU/DB"，误差可 ±50%；生产会引入网络 RTT、TLS、真实客户端分布、更大数据量，实际值低于估算。**结论：对 50k 用户的小金融公司，单节点即足够且有富余。**
