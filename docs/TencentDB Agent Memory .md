# TencentDB Agent Memory 机制深度总结

## 零、三代Agent记忆架构速览





| 代际     | 名称       | 核心机制                                               | 解决了什么                 | 暴露了什么                           |
| -------- | ---------- | ------------------------------------------------------ | -------------------------- | ------------------------------------ |
| **Gen1** | RAG记忆    | 对话切块 → Embedding → Top‑K检索                       | 跨会话「想得起来」         | 无update语义、无冲突消解、无时间语义 |
| **Gen2** | 结构化记忆 | LLM抽取(主体, 属性, 值, 生效时间)，同key旧事实标记失效 | update、冲突消解、时间语义 | 事实是孤岛，跨实体多跳查询乏力       |
| **Gen3** | 记忆图谱   | 实体+关系边+事件，向量召回+图遍历+事件相似度三路并发   | 多跳推理、关系追溯、可解释 | 需要图存储和抽取算力，工程复杂度高   |

**关键洞察**：每次换代都在把「生成层的负担」前移到「记忆层」——Gen1把矛盾甩给模型现场判断；Gen2在写入时就把矛盾消解掉；Gen3更进一步，把实体关联在写入时建好。

## 一、核心定位：记忆系统 vs 向量检索

**关键结论：RAG（向量库）是“记忆的素材库”，不是记忆本身。**





| 维度     | RAG（Gen1）                | TencentDB Agent Memory（Gen2）    |
| -------- | -------------------------- | --------------------------------- |
| 存储单元 | 对话Chunk                  | 结构化事实卡片                    |
| 核心操作 | Insert + Search            | 写入 → 提炼 → 检索 → 更新         |
| 冲突处理 | ❌ 无，矛盾甩给模型         | ✅ 冲突仲裁（新增/跳过/覆盖/合并） |
| 时间语义 | ❌ 无，余弦相似度不认时效   | ✅ 双时态（valid_from/to）         |
| 更新语义 | ❌ 无，新记录只是“多了一条” | ✅ 同key旧事实标记失效             |

## 二、四层记忆金字塔（L0-L3）





| 层级   | 名称     | 内容                         | 更新策略                 | 类比           |
| ------ | -------- | ---------------------------- | ------------------------ | -------------- |
| **L0** | 原始流水 | 对话原文，一字不改           | 实时落盘（毫秒级）       | 录音笔/流水账  |
| **L1** | 记忆卡片 | 结构化事实（偏好/事件/规则） | 异步提炼（约6-10秒）     | 会议纪要便签   |
| **L2** | 场景档案 | 同一情境下的卡片打包         | 按情境组织，不按日期     | 项目专属文件夹 |
| **L3** | 人格摘要 | 稳定的用户画像               | 定时/事件触发（周/月级） | 用户简历       |

### L3的更新策略：定时 + 事件触发

**核心原则：分层隔离，各自采用不同更新策略。**





| 层级        | 更新频率               | 时效性要求 | 存放位置                  |
| ----------- | ---------------------- | ---------- | ------------------------- |
| L3 核心人格 | 周/月级 + 关键事件触发 | 低         | System Prompt（缓存友好） |
| L2 场景摘要 | 日级增量更新           | 中         | 场景档案                  |
| L1 原子事实 | 实时/事件触发          | 高         | 记忆卡片                  |
| L0 原始流水 | 实时写入               | 最高       | 数据库                    |

**Agent推理流程：先看L3定基调，再查L0/L1做决策。**

## 四、冲突仲裁与遗忘机制

### 冲突仲裁（两阶段）

1. **候选召回**：新卡片转语义指纹，找最近邻
2. **模型判断**：新卡片应 新增/跳过/更新/合并

**关键约束：模型只能看到召回到的候选，未召回的旧卡片等于不存在。**

### 长期记忆的“遗忘”策略

**核心原则：遗忘是检索降权，不是物理删除。**





| 策略           | 实现方式                                            |
| -------------- | --------------------------------------------------- |
| 存储层不遗忘   | L0原始流水永不删除，按时间分区归档                  |
| 检索层衰减     | `最终得分 = 相似度 × 时间衰减系数`（指数/对数衰减） |
| 场景层强制唤醒 | 风控、投诉、大额交易等场景绕过时间衰减，全量召回    |
| 关键数据永不丢 | L3核心画像永久保留，L2场景可汇总，L0/L1可归档       |

### 版本化（覆盖的替代方案）

**新记忆不覆盖旧记忆，而是为旧记录打上“过去式”标签（valid_to = now）。**

sql

```
-- 不是 UPDATE
-- 而是：
INSERT INTO customer_risk_assessment_history 
(user_id, risk_level, valid_from, valid_to)
VALUES 
(123, 'R3', '2024-01-01', '2026-08-10'),  -- 旧记录标记失效
(123, 'R4', '2026-08-11', NULL);           -- 新记录生效
```

## 六、记忆系统 vs 知识库：何时升级到哪一代

### 选型决策链





| 判断问题                       | 是 →                     | 否 →               |
| ------------------------------ | ------------------------ | ------------------ |
| 信息会被用户/环境更新吗？      | 需要记忆系统（至少Gen2） | Gen1（知识库）够用 |
| 存在“新信息应覆盖旧信息”吗？   | Gen2+                    | Gen1够用           |
| 有跨实体关联查询需求吗？       | 考虑Gen3                 | Gen2停住           |
| 日活对话量撑得起图谱抽取成本？ | Gen3可行                 | Gen2+向量兜底      |

### 三代适用场景速查





| 代际     | 适合谁         | 典型场景                                                     |
| -------- | -------------- | ------------------------------------------------------------ |
| **Gen1** | 知识库问答     | 产品文档、政策条款、历史工单检索                             |
| **Gen2** | Agent助手/客服 | 处理用户改口、偏好演化、时间敏感查询                         |
| **Gen3** | 记忆基础设施   | 跨实体多跳推理、关系追溯（如「这个用户和哪些订单、哪些投诉有关联」） |

### Gen1 → Gen2 的改动最小方案（1-2周落地）

1. 写入侧加LLM抽取步骤：产出(主体, 属性, 值, 生效时间)
2. 同key冲突时标记失效（valid_to打时间戳）
3. 检索侧改成两路：结构化事实查表 + 向量库兜底

## 七、关键设计原则总结

1. **RAG没死，只是回到了“检索零件”的位置** — 向量检索是记忆的一个动作，不是记忆本身
2. **“塞得下”≠“记得住”** — Chroma的194,480次调用证明，长上下文损害可靠性
3. **记忆=分层+时效+冲突消解** — 三个要素缺一不可
4. **遗忘=检索降权，不是物理删除** — 日常自然沉底，关键场景强制唤醒
5. **关键数据的“证据链”永远保留** — 版本化而非覆盖，支持审计追溯
