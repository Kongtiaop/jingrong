# Agent & RAG 数据飞轮：从规划到落地

> 本文基于腾讯技术工程《Agent 上线半年了——它比第一天聪明了吗？》文章核心理念，结合项目实际情况，整理的数据飞轮搭建方法论与落地路径。

## 一、飞轮的本质：改运行时，不改代码

### 1.1 飞轮到底在改什么

很多人以为飞轮是“系统自动改代码、自动微调模型”——这是误解。

**飞轮的真实本质是：在运行时层面持续优化系统的动态配置，让系统越用越好。**

代码和模型参数是固定的，飞轮不碰它们。飞轮修改的是：





| 修改对象            | 相当于什么         | 影响范围                | 修改方式      |
| ------------------- | ------------------ | ----------------------- | ------------- |
| Skill 文件          | Agent 的“操作手册” | 所有用到该 Skill 的任务 | 修改文件      |
| Prompt 模板         | Agent 的“指令”     | 该 Agent 的所有推理     | 修改配置库    |
| top_k / temperature | 检索和生成的“调参” | 该类型任务的执行        | 修改配置库    |
| Query 改写规则      | RAG 的“入口”       | 相关问题的检索          | 修改配置库    |
| 长期记忆            | Agent 的“经验库”   | 跨会话、跨 Agent 复用   | 记忆写入      |
| 知识库内容          | RAG 的“资料库”     | 检索命中范围            | 补充/修正文档 |

> **一句话：改的是 Skill/Prompt/记忆/配置，不是代码，不是模型参数。** 改完立即生效，错了立即回滚。

### 1.2 飞轮不能解决什么





| 问题类型       | 飞轮能解决吗 | 为什么                                 |
| -------------- | ------------ | -------------------------------------- |
| 检索策略不对   | ✅ 能         | 改 top_k、改权重、改 query 改写        |
| 知识缺失       | ✅ 能         | 补充文档、修正错误片段                 |
| 指令不清       | ✅ 能         | 改 Skill、改 Prompt                    |
| 口语表达没覆盖 | ✅ 能         | 加 Query 归一化、加同义映射            |
| 工具本身有 Bug | ❌ 不能       | API 返回的数据是错的，Skill 再改也没用 |
| 数据源有问题   | ❌ 不能       | 知识库里的文档本身就是错的             |
| 模型能力不足   | ❌ 不能       | 模型本身做不了复杂的逻辑推理           |
| 架构设计缺陷   | ❌ 不能       | 底层架构限制了能力上限                 |

> **核心原则：飞轮解决的是“已有能力没用好”的问题，系统本身没有的能力，飞轮创造不出来。**

## 二、飞轮如何让 RAG 变聪明：一个具体例子

### 初始状态

用户问：“我入职 3 年了，年假到底是多少天？”RAG 从公司制度文档中检索，模型把“累计工作年限”和“在本公司年限”混淆了，答成了 5 天（正确答案是 10 天）。失败类型标记为 `hallucination`，`expected_answer` 标注为 10 天。

### 飞轮的四层迭代（一行代码未改）

**第一轮：调整检索策略**
系统分析 Bad Case 发现“年假”类问题，top_k=5 时只有 1 个片段包含“10 天”。自动把该类问题 top_k 调到 10，增加“年限”关键词权重。下次用户再问，命中了“10 天”的文档。

**第二轮：补充知识片段**
系统发现多个“年假”类问题都缺少“累计工作年限”计算规则。管理员把缺失的规则片段补充进知识库。下次检索不仅命中了“10 天”，还命中了“3年对应10天”的具体计算依据。

**第三轮：动态 Prompt 注入**
系统发现回答年假问题时，模型容易混淆“入职年限”和“累计工作年限”。动态生成指令注入 Prompt：“回答年假问题时，请先区分'累计工作年限'和'在本公司年限'。” 下次回答时会先做区分再作答。

**第四轮：Query 归一化**
系统发现用户说“年假有几天”能答对，但“我能休几天假”答不对。自动把“我能休几天”归一化为“年假天数”再检索。下次用户问“我能休几天”，RAG 用归一化后的 query 搜到了正确答案。

**效果：同类问题 Bad Case 从每月 15 条降到 2 条。**

## 三、飞轮如何让 Agent 变聪明：一个具体例子

### 初始状态

客服 Agent 处理“查询订单状态”时，经常搞混“订单号”和“物流单号”，用户问“查一下我的订单状态”，Agent 有时候去查物流单号，查不到就乱答。

### 飞轮的四层迭代（一行代码未改）

**第一轮：修改 Skill 文件**

text

```
修改前：
"查询订单状态：使用订单号调用 order_api"

修改后：
"查询订单状态：
  1. 如果用户明确提供了订单号（格式：ORD-xxx），使用它
  2. 如果用户没有提供订单号，反问'请提供您的订单号'
  3. 不要使用物流单号替代订单号"
```

下次 Agent 处理同类问题时，Skill 文件给了它更明确的约束，不再乱猜。

**第二轮：动态 Prompt 注入**
系统发现用户说“我那个快递到哪了”，Agent 又去查物流了（其实用户在问订单状态）。动态生成指令注入 Prompt：“注意：用户提到'快递'时，优先询问'您是指订单状态还是物流信息？'，而非直接查物流。”

**第三轮：记忆沉淀**
经过多轮验证，系统把“用户说快递时先澄清”写入 L1 事实记忆：`{subject:"订单查询", attribute:"口语表达处理", value:"优先澄清而非猜测"}`。下次任意 Agent 遇到类似表达时，记忆系统会召回这条经验。

**第四轮：动态参数调整**
系统发现“查询订单”类任务经常需要 2-3 轮澄清才能拿到完整参数。自动调整：`max_iterations: 4→6`、`temperature: 0.7→0.3`。下次 Agent 用更低的 temperature 减少猜测，用更多的轮次确保澄清充分。

### 各齿职责





| 齿               | 职责               | 产出                   |
| ---------------- | ------------------ | ---------------------- |
| **信号（评测）** | 发现问题、判断好坏 | 失败模式分类、归因报告 |
| **积累（记忆）** | 沉淀经验、防止遗忘 | Skill/记忆/知识库更新  |
| **落地（修复）** | 生成候选、验证效果 | 配置库更新、灰度发布   |
| **控制（人机）** | 审核门控、安全回滚 | 通过/拒绝/回滚决策     |

## 五、从零到一的落地路线

### Phase 0：加固评测基础（1-2 周）

- 评测集三分法：train（诊断）/ val（筛选）/ test（最终验证）
- 失败模式自动归因：按类型分组（参数提取错误/工具调用失败/推理逻辑错误/知识缺失）
- 诊断信号结构化存入 Playbook

### Phase 1：半自动修复（2-4 周）

- Diff 模式生成修复候选（只改需要改的部分）
- 隔离环境自动验证（语法检查→回归测试→统计显著性→Playbook一致性）
- 五层安全门控，自动过滤低质变体

### Phase 2：飞轮运转（1-2 月）

- 灰度发布（10% 流量，7 天观测期）
- 自动回滚（P0 级退化一键回滚）
- 自动回流（新失败样本进入下一轮评测种子池）
- 异步 Dreaming（定期审阅历史会话，发现跨会话系统性模式）

## 八、核心原则

1. **评测的可信度 > 系统的复杂度。** 在搭任何自动化之前，先确保评测信号是准的。评测不可信的系统，自动化程度越高，犯错速度越快。
2. **飞轮解决的是“已有能力没用好”的问题。** 工具 Bug、数据源错误、模型能力不足——这些必须靠改代码/加工具/换模型解决，飞轮创造不出系统本身没有的能力。
3. **闭环的价值在于环节之间的衔接，而非单个环节的先进性。** 评测信号必须能流进记忆和 Skill 更新；Skill 更新后必须能被评测验证；验证结果必须能反哺下一轮进化。
4. **先跑通 Phase 0。** 一个能手动转一圈的粗糙飞轮，好过一个精美但静止的蓝图。
