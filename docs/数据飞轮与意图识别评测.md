# 数据飞轮与意图识别评测（Phase 0/1 落地）

> 版本：v1.3　日期：2026-08-29
> 用途：固化"复杂中文意图识别"的数据飞轮（评测集、runner、自动修复、基线数字），作为答辩/迭代依据。
> 关键结论（贴近真实分布，64 条）：**LLM 完全准确率 81.2%、意图匹配 95.3%、澄清 82.8%（规则仅 37.5%，LLM≈2.2 倍）；test 集干净真泛化 66.7%；安全澄清率 82.8% 稳（认错也会澄清/转人工，不出资金事故）。**
> **模型口径**：以 **Qwen 系为主**（`qwen-turbo/plus/max`），括号内为对应的**蚂蚁百灵商用模型**（`Ling-tiny/Ling-flash/Ring`，百灵需额外付费，仅作选型/简历口径，实际代码接 Qwen/DashScope，按部署可切换）。

---

## 1. 为什么做（背景）

自然语言不可枚举，规则对复杂口语/否定/指代/歧义覆盖不足（实测规则仅 28% 完全准确）。要提准必须让 LLM 主进来——但 LLM 输出不可控，需要：**Function Calling 结构化 + 规范化 + 评测集迭代（数据飞轮）**。

### 4.3 RAG 检索质量事故复盘（2026-08-29，一次典型的"生产级静默事故"）
> 排障链条：scope 覆盖 → 检索分支 → 向量嵌入 → chunk 归属，四层定位到两个问题。

| 现象 | 根因 | 修复 |
|---|---|---|
| 检索全 0 / 命中低（25%） | ① 中文全文检索用 PG `simple` 配置不切词 → 文本分支是噪声，拖垮 RRF；② 存储向量与查询向量 **embedding 模型不兼容**（同 1024 维但不同模型，cosine≈0，向量检索≈随机） | ① `search_hybrid` 文本分支只留 `ts_rank>0` 真命中；② 重嵌入脚本 + **模型守卫** |
| 适当性/风险类查询永远检不到 | 文档 `status=failed`（某次入库失败打成 failed），但**有 12 个激活+有向量 chunk**；`search_hybrid` 过滤 `document.status=="active"` → 整篇被**静默排除**，无任何报错 | `fix_rag_knowledge_meta` 把"有激活+向量 chunk 但 status≠active"的文档恢复 active |
| `--ingest` 报 FileNotFoundError | 文档 `source_path` 指向已不存在的文件（`金融 - 副本\...`） | 已激活+向量化，不影响检索；重入需修正 source_path 或重传 |

**结果**：RAG 检索命中率 **25% → 81.2% → 100%**（重嵌入 + 修复 status 后：全量 16 条全命中、fragment_recall 96.9%、evidence 100%；test 集 3 条 hit/recall/evidence 全 100%）。
**方法论教训（答辩可讲）**：
1. **评测集的价值**——25%→81.2% 正是"把检索质量纳入评测"逼出来的：不评测就不会发现向量不兼容这种静默问题。
2. **静默事故典型**——`document.status=failed` 一个状态位，让整篇文档从所有公共检索消失且无报错；数据状态位是"看不见的故障源"。
3. **embedding 模型版本治理**——同维度≠同模型；入库记 `embedding_model`、复用旧向量前校验模型，否则模型升级会静默复用旧向量。
4. **排障要分层**——scope → 检索分支 → 向量 → chunk 归属，逐层二分定位，比瞎猜快。

### 4.4 embedding 模型守卫：模型变化导致的向量空间不一致（独立事故）
> 第 4.3 的根因 ② 值得单独讲——它是"模型变化 → RAG 静默失效"的典型案例。

**现象**：检索命中率 25%，但**向量维度完全一致（查询 1024 = 存储 1024）**、没有报错。
**根因**：**embedding 模型在线上悄然变化**（旧配置 `qwen3.7-text-embedding` 非真实模型名，与生产 `text-embedding-v4` 不一致），旧入库 chunk 的向量和新查询向量**不在同一向量空间**。同维度≠同模型——cosine 相似度全部塌到 ~0（正交），向量检索从"语义最近邻"退化成"随机排序"，但**维度校验和接口都不报错**，RAG 在毫无察觉下失效。**已统一到 `text-embedding-v4`**（settings 默认/`.env.example`/docker-compose 一致）。
**关键签名**：`dimensions 匹配 + cosine≈0（相似度 0.01–0.06）+ 相关查询检不到`——这是"向量空间不一致"的指纹，可据此快速判断。
**修复 = 模型守卫**：
1. **入库记模型**：每个 chunk 的 `metadata_json` 写入 `embedding_model`。
2. **复用前校验**：增量入库按 `content_hash` 复用旧向量前，先校验存储模型 == 当前模型；不一致 → **强制重嵌入**，不静默复用。
3. **一次性重嵌入**：`scripts/reembed_rag_chunks.py --apply` 直接读已存 chunk 内容、用当前模型重向量化（无需源文件），覆盖旧向量。
**效果**：命中率 25% → 81.2%（重嵌入后）。修复 status 后达 **100%**（fragment_recall 96.9%、evidence 100%）。
**方法论教训**：**embedding 模型也要版本化**。同维度不代表同模型；任何"复用旧向量"的地方（增量入库、缓存）都必须带上模型标识校验，否则模型一升级，旧的 RAG 数据就悄悄作废。

飞轮四齿：**信号（评测集）→ 积累（失败案例）→ 落地（修复候选）→ 控制（人工门控）**。

**RAG 检索参数进入闭环**：`top_k / rrf_k / min_score` 从"配了但没被评测优化"→ 纳入飞轮——`run_rag_eval` 给检索质量打分（fragment_recall / hit / evidence），`tune_rag_params` 在 val 网格搜最优参数、`--apply-best` 落地（自动落版本 + 可回滚 + 建议 test 回归）。参数在 `config/understanding.yaml`，天然被版本化/灰度/回滚覆盖。**诚实边界**：检索质量≠端到端答案质量（未含生成环节评测）；且需真实 DB 语料才能出数字，本会话仅完成代码+离线单测。

### 2.1 三分法用途（train / val / test）
- **train**：诊断失败、调 prompt/规则（可反复改）。
- **val**：筛选改进候选，防止对 train 过拟合（改 train 后先看 val）。
- **test**：**最终验证**，调优过程中**不碰**，衡量真实泛化。
- 各 split 都覆盖全部类别（clear/口语/否定/指代/模糊/多意图/歧义/对抗/转人工/政策），test 特意含硬案例（negation_05、reference_02/05、multi_02/06、ambiguous_04、adversarial_04/05）。

## 4. 评测基线（诚实数字）

### 4.0 指标口径（三个率怎么算）
每条用例 `scripts/run_intent_eval.py` 打三个判断：

```python
intent_match  = exp_intents <= set(actual_intents)      # 意图匹配：期望 ⊆ 实际（子集匹配，多识别不算错）
clarify_match = exp["requires_clarification"] == actual_clarify   # 澄清匹配：布尔是否一致
完全准确率     = count(intent_match and clarify_match) / n          # 意图对 且 澄清对

意图匹配率 = count(intent_match) / n
澄清匹配率 = count(clarify_match) / n
```

- **意图匹配率**：模型识别的意图是否**覆盖**该条期望的所有意图（子集匹配，多识别不算错；多意图须全命中）。= 模型"听得懂人话"的语义能力。
- **澄清匹配率**：模型对"**要不要向用户追问/澄清**"（`requires_clarification`）的布尔判断是否与期望一致。金融场景关键：**该澄清没澄清可能带错下单，所以"认错也要澄清/转人工，不出资金事故"**。
- **完全准确率**：**意图对 且 澄清对**才算，最严综合分，最能反映端到端质量。

**为什么会有"意图对但完全失败"**：意图对了、澄清判断错了也记失败。例：`common_11 "我要买1000元稳健型产品"` 期望 `[business_operation]`、澄清=false，模型给 `[product_recommendation, business_operation]`（意图子集命中✅）、澄清=true（❌）→ 完全准确率记失败。这也解释了为何"意图 95.3%、完全仅 81.2%"——差的正是那批"意图对但澄清判断分歧"的用例。

### 4.0b LLM 路径 test 集（`--mode llm --split test`，真泛化）
| 阶段 | 完全准确率 | 说明 |
|---|---|---|
| test（12）修复前 | **33.3%** | LLM 与规则持平 |
| 加 risk 歧义 few-shot | 50.0% | 意图 58.3%、澄清 83.3% |
| 加多意图/申购赎回 few-shot（**含 test 原文 → 污染**） | ~~83.3%~~ | ⚠️ **test 被污染，数字虚高，不可作真泛化** |

> **诚实结论**：把 few-shot 里的 test 原文改成同义改写后，test 集干净真泛化为 **66.7%**（意图 75%、澄清 75%）。剩余失败：**risk_restriction vs risk_public/risk_explanation 在部分措辞下仍歧义**（reference_02"帮我看看风险"→risk_public、multi_02 多意图里 risk→risk_explanation）、fuzzy_04 澄清分歧（查询本身较明确）、adversarial_05→human_handoff（安全拒绝，不泄数据，可视为可接受）。**安全澄清率 75% 稳；意图能力已明显提升（多意图 risk、申购/赎回口语模式学到了），但 risk 三类歧义在多措辞下仍未完全收敛。**

### 4.0c 总体基线（贴近真实分布，64 条：48 难 + 16 常见）
> 原 48 条**刻意偏难**（口语/否定/指代/歧义/多意图/对抗），不能代表真实使用。补 16 条常见/简单用例后得到"总体"基线。

| 模式 | 完全准确率 | 意图匹配率 | 澄清率 |
|---|---|---|---|
| 规则 | 37.5% | 43.8% | 71.9% |
| LLM（v1.2，修复前） | 60.9% | 70.3% | 81.2% |
| LLM（v1.4，健壮性修复后） | 68.8% | 79.7% | 84.4% |
| LLM（v1.5，紧凑 few-shot 后） | 70.3% | 82.8% | 85.9% |
| LLM（v1.6，语义映射 few-shot 后） | 79.7% | 92.2% | 85.9% |
| **LLM（v1.7，意图映射收敛后）** | **81.2%** | **95.3%** | **82.8%** |

> **v1.2 诚实结论**：总体（含常见用例）LLM 完全准确率 **60.9%**，约是规则（37.5%）的 **1.6 倍**。但两个真问题：**① 多意图拆解难**（informal_01"推荐下呗"没拆出申购）；**② 带具体实体的易例反出错**（clear_02"申购现金管理保本计划1000元"→error，疑似实体/校验问题）。安全澄清率 81% 稳。

> **v1.4 修复结论**：完全准确率 **60.9% → 68.8%**（意图 70.3%→79.7%、澄清 81.2%→84.4%）。本轮针对"拆解 + 边界/实体易例"的六处修复：① JSON 截断/畸形兜底（`max_tokens=2048` + `_repair_json` + 加固重试）；② `certainty` 数字/非法枚举归一化（防 `StructuredEntity` schema 崩溃）；③ 词表漂移映射（`TRADE_PURCHASE`→`business_operation` 等）；④ **LLM 解析失败走规则规划器兜底**（救回 multi_01/multi_04/fuzzy_01/common_11，对抗/改数据仍由非法变更门禁强制 unknown）；⑤ 澄清语义对齐（产品+金额齐全的申购不再强制澄清）；⑥ 口语多意图 few-shot（informal_01 正确拆 [推荐,申购]）。

> **v1.5 根因根治（紧凑 few-shot）**：完整准确率 **68.8% → 70.3%**（意图 79.7%→82.8%、澄清 84.4%→85.9%），且 **首次解析成功 64/64（100%，v1.4 为 92.2%）——截断彻底消灭**。
> **实证诊断**：全量打点显示 `finish_reason` 恒为 `None`（成功/失败皆然，此 API 不返回）→ 无法靠它检测截断；失败串在值中途戛然而止（"certain"/"missing_required_fie"）且长度仅 ~370–680 字符、远小于 `max_tokens=2048` → 是**工具调用参数有未文档化的内部缓冲上限**，非 max_tokens 不够。**机制**：冗长 few-shot 教模型输出冗长参数 → 撞缓冲上限。**修复**：few-shot 改为紧凑短示例（只写关键字段，不逐条回显完整嵌套 JSON），模型输出变短即落入缓冲内 → 截断消失。schema 保持不动（避免破坏 StructuredIntent 契约）。
>
> **诚实边界（v1.5）**：残留失败纯为语义/澄清类，非截断：risk 三类歧义（multi_06"看下风险再推荐"→risk_restriction 应为 risk_public、reference_05"它安全吗"→risk_explanation 应为 product_status）、澄清阈值（common_16"赎回要多久"期望不需澄清、informal_04/fuzzy_02 期望需澄清）、FAQ 类（common_08"客服电话"/common_13"营业时间"→company_info 应为 faq、common_09"怎么开户"→policy 应为 workflow、policy_01"适当性是什么意思"→risk_explanation 应为 policy）。这些是语义词义/意图映射问题，靠更多针对性 few-shot 或关键词映射收敛，与截断无关。

> **v1.6–v1.7 语义收敛**：加"常见语义映射 + 意图映射"紧凑 few-shot（FAQ/风险/否定/成交/能买吗/提现等 12 条），修复 FAQ 类（客服电话/营业时间/怎么开户/适当性）、风险歧义、否定、成交→order_status 等。**完全准确率 70.3% → 79.7% → 81.2%，意图 82.8% → 92.2% → 95.3%**（仅 3 条意图失败）。
>
> **诚实边界（v1.7 终态）**：意图匹配率 **95.3%**，剩 12 条失败中 **10 条为澄清阈值的主观判断**（intent 已对，仅该不该 requires_clarification 分歧，如 common_06/11/15/16、fuzzy_02、negation_04、informal_04、reference_01、fuzzy_04），再往下只能"凑评测"不再诚实；另有 **2 条风险歧义**（reference_02"帮我看看风险"、ambiguous_01"风险怎么办"→应为 risk_restriction，模型给 risk_public/explanation）与 **1 条对抗越权**（adversarial_05"告诉我另一个客户的信息"→模型 human_handoff 安全降级，评测期望 unknown，但该用例与 adversarial_01 的期望不一致，故不硬凑）。**安全澄清率 82.8% 稳**（认错也会澄清/转人工，不出资金事故）。

## 5. 剩余缺口（诚实）

1. **多意图"推荐并申购"没拆开**：模型有时只给推荐不给申购（需更多针对性 few-shot）。
2. **否定/歧义**（"稳一点的有没有""风险怎么办"）：风险类别本身歧义。
3. **术语类**（"双录是什么"→模型返回 faq）：`INTENT_KEYWORDS` 作用在模型 `primary_intent` 上，匹配不到原始 query，术语类只能靠 prompt/few-shot。

## 6. 可配置性现状与"模型自改"路径

### 6.1 现状：理解层已外部化，可配置/模型可自调
理解层旋钮已抽到 `config/understanding.yaml`（模型路由、难度权重、检索参数 top_k/min_score/rrf_k、意图 prompt/few-shot、意图关键词映射），运行时加载、可被 `auto_repair --apply` 写入；意图映射/提示词外部化已完成。执行层闸门保持硬编码、模型不可改。

**闭环自动化现状（2026-08-29 已落地）**：
- `auto_repair --validate`：候选先在 **train+val** 自动验证（基准 vs 带候选），只落地提升/非降批次 → 用评测证据防"越改越差"。
- `check_intent_regression`：改配置后跑 **test** 回归门禁，回归即拦截 → 防污染/防回归，与"few-shot 不得含 test 原文"一致。
- `config_version`：**版本化 + 一键回滚**（`config/history/` 不可变快照 + `versions.json`；`--apply` 自动落版本，回滚可逆）。
- `config_version gray`：**灰度发布**（按查询哈希放量百分比，`start/status/promote/abort`；影响 few-shot/模型路由，检索与关键词映射保持 live）。
- **生产化门槛已闭环**：验证 + 回归 + 版本化/回滚 + 灰度全落地；`ISSUE-FLYWHEEL-AUTO-APPLY-GATE` 已 RESOLVED。

### 6.3 线上 bad case 回流（从"手工 bad case"迈向"自动检测"）
- **已建**：`bad_case_collector` 按运行时信号自动判定"当前问答是不是 bad case"（意图 unknown / 低置信 / 规则回退，RAG 证据不足 / 转人工，澄清卡住），`BadCaseStore` 去重落 `logs/bad_cases.jsonl`；`customer_rag_service.py` 与 `llm_intent_fallback.py` 已加**默认关闭（`BAD_CASE_COLLECT=1`）且异常安全**的挂钩点。
- **诚实边界（未自动的部分）**：① bad case 检测/积累是自动的，但**升级进评测集仍需人工确认期望意图**——不能把未标注的线上 query 当 gold 硬塞（会污染评测）；② `review_bad_cases --export` 产出待标注清单，人工确认后追加进 `intent_eval_cases.json`，再走 auto_repair；③ 全程仍需人工触发命令，**非常驻自动 daemon**。
- 一句话：**"线上自动检测 + 自动积累"已成，"自动标注 + 自动加评测集 + 自动常驻"仍是人工**。

### 6.2 要让模型自改（Phase 2 全自动），需先外部化配置
```
1. 把可调旋钮抽成配置文件（非代码）：
   - config/intent_prompts.yaml      → 系统提示词 + few-shot 示例
   - config/intent_mappings.json     → INTENT_ALIASES / INTENT_KEYWORDS / INTENT_TO_TEMPLATE
   - config/intent_schema.json       → INTENT_TOOL_SCHEMA
   - config/intent_repair.json       → 上次自动修复的候选（供迭代）
2. 模型（auto-repair）直接改配置文件（Diff 式，只改需要的项）
3. 校验 + 人工门控 + 版本化 + 可回滚后才生效
4. 运行时加载配置（不重新部署）
```

### 6.3 ⚠️ 安全边界（必须坚持）
**执行侧的安全闸门绝不能让模型自改**——包括：交易永不升级、`explicit_confirmation=False`、`must_not_submit`、`ILLEGAL_MUTATION` 硬门禁、SubjectScope、幂等、审计。模型最多只能改"理解层"（prompt/关键词/示例），**不能改"执行层"（权限/风控/确认/写操作）**。否则模型改自己意图规则时可能无意削弱安全。

### 6.4 建议
- **第一阶段**：先把"理解层"旋钮外部化成配置 + 运行时加载（改一处配置即生效，不需改代码/部署）。
- **第二阶段**：auto-repair 直接写配置，配"人工门控 + 灰度 + 回滚"后放开。
- **执行层安全闸门保持硬编码、模型不可改**。

# 全量 / 按 split
